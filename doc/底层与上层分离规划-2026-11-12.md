## 1. 问题陈述

子树（`zephyr_user`）当前把**三类**完全不同的东西平铺在同一个根目录下：

- **底层（与芯片耦合）**：`boards/` `dts/` `drivers/` `platform/` —— 遵循 Zephyr 规则（`module.yml`、`DEVICE_DT_DEFINE`、binding、`board.cmake`），直接调厂商 API。
- **中间层（类驱动 + 协议细节）**：`framework/drivers/` —— `Usb` / `UartDma` / `Can` / `Pwm` / `EthercatSlave` 这些类，含 USB 枚举、EtherCAT 邮箱等协议实现，但不碰厂商寄存器。
- **上层（业务）**：`framework/{algorithm,modules,topic,init,shell,cmd}` + `project/` —— 架构自有机制与业务。

**三者混在一层带来的实际后果**（不是审美问题）：

1. **依赖方向说不清**：`drivers/` 反过来 include `framework/` 的头（`log.hpp`、`usb_hal.hpp`、`ecat_esc.hpp`、`esf_dump.hpp`、`spec/ecat_registers.hpp`），底层依赖中间层，违反单向依赖。
2. **职责边界糊**：`framework/drivers/` 和根 `drivers/` 名字一样、都是"驱动"，只能靠 README 表格口头区分。新人第一眼分不出哪个该改。
3. **上层能看见中间细节**：当前虽然 `ethercat.hpp` / `usb.hpp` 已经只暴露类接口，但没有目录级约束——任何人在上层 `#include "ecat_mailbox.hpp"` 都能编过。
4. **拆不干净**：想让某个用户区只带上层、或让底层单独复用，做不到——三者共享同一套 CMake/Kconfig 装配假设。
5. **Kconfig 符号混层**：`DUST_FSMC` / `DUST_ENCODER`（底层）与 `DUST_DEV_PWM` / `DUST_COM_CAN`（中间层）都在 `framework/zephyr/Kconfig` 的 rsource 链上，没有层级区分。

**目标**（用户 2026-11-12 定）：**三层物理分离**——`zephyr/` 放与芯片耦合的全部，`midlayer/` 作为中间层类驱动与协议栈，`framework/`（六模块 + `project/`）是上层；**上层只看得到封装好的类驱动，看不到中间细节**。

**分两类**：

- **契约头（合理）**：`ecat_esc.hpp` / `usb_hal.hpp` / `esf_dump.hpp` —— 底层实现上层定义的纯虚接口，这是分层架构的标准做法（实现依赖抽象）。这 4 处**不是问题**，但要**明确它们属于"上下层共享的契约"，不属于任一方私有**。
- **实现依赖（问题）**：`log.hpp`（3 处，共 45 个 `DUST_LOG_*` 调用点）和 `spec/ecat_registers.hpp`（1 处）—— 底层为了打日志、为了拿寄存器偏移，去 include 上层的具体实现头。这是**真依赖**，必须断开。

### 2.3 中间层对底层的引用

实测只有 1 处：`framework/drivers/device/encoder/encoder.hpp:14` include 子树 `drivers/encoder/encoder.h`。

这是 2026-11-12 刚下沉的编码器：**C 实现在子树 `drivers/`，C++ 包装在 `framework/drivers/device/`，包装 include 实现**。这个方向（上层 include 底层）是对的，但它揭示了一个结构问题：**一个功能被拆成"底层实现 + 上层包装"两半，分别落在两个平级目录里，靠 include 缝合。**

### 2.4 各层的 Zephyr 耦合度

`framework/` 里直接 include `<zephyr/...>` 的文件共 **54 个**，分布：

| 模块 | 文件数 |
|---|---|
| `drivers/communication` | 13 |
| `modules/imu` | 7 |
| `drivers/device` | 7 |
| `shell/log` | 4 |
| `topic/*` | 5 |
| `modules/motors` | 2 |
| `init/*` | 6 |
| `cmd/*` | 4 |
| 其余 | 6 |

**这说明**：`framework/drivers/` 依赖 Zephyr API，但它依赖的是 **Zephyr 通用 API**（`pwm_set_dt` / `gpio_pin_set_dt` / `can_send`），不是厂商 API。

**关键区分（2026-11-12 按用户原则修正）**：

> 依赖 Zephyr 通用 API ≠ 与芯片耦合。
>
> - `framework/drivers/device/pwm/pwm.cpp` 调 `pwm_set_dt()` —— Zephyr 通用接口，换一块板照样编 → **中间层**
> - `drivers/usb/hal/hpm/usb_hal_hpm.cpp` 写 `regs->ENDPTCTRL[0]`、调 `usb_device_init()` —— HPM 专用 → **底层**
>
> 判据是"**有没有出现厂商/芯片专属符号**"，不是"有没有 include Zephyr 头"。

真正与硬件无关的上层是：`algorithm`（零硬件依赖）、`modules`（设备能力契约）、`topic`（数据契约）、`init`（生命周期）、`shell`（调试台）、`cmd`（横切工具）。

### 2.5 装配链的耦合

`project/CMakeLists.txt` 把两类东西混在一个列表里：

```cmake
set(ZEPHYR_EXTRA_MODULES
  "${FW_ROOT}"                        # 上层
  "${ZEPHYR_USER_DIR}/platform/cmsis" # 底层
  "${ZEPHYR_USER_DIR}/drivers"        # 底层
)
```

后面的 `add_subdirectory` 也是混着的（`framework/*` 七个 + `zephyr_user/drivers`）。

`framework/zephyr/Kconfig` 的 rsource 链同样混着：`drivers/Kconfig`（上层）之后没有根 `drivers/Kconfig`（底层，它由 `drivers/zephyr/module.yml` 单独加载）——**两个 "drivers/Kconfig" 通过两套不同机制加载**，没有任何地方能一眼看出全貌。

## 3. 分层定义：三层判据

### 3.1 核心原则（用户 2026-11-12 定）

> **上层只看得到封装好的类驱动，看不到中间细节。**
>
> 比如 USB 和 ECAT 的中间协议细节，上层不该看见。**HAL 放到底层，因为它与芯片耦合。**
>
> **`framework/drivers/communication/stream/usb/core` 这些才是中间层啊，这种协议栈上层不需要看，底层不合适，放到中间层。还有 ecat 也是一样。**

三条推论：

1. **协议栈（`usb/core`、`ethercat/core`）是中间层的本体**——上层不需要看，底层也不合适放（它不碰寄存器），只能放中间层。
2. **上层与协议栈之间还要再隔一道门面**：上层拿到的是 `Usb` / `EthercatSlave`，不是 `UsbCdcAcm` / `EcatMailbox` / `EcatCoe`。
3. **HAL 与芯片耦合 → 归底层**：`usb_hal_hpm` / `usb_hal_stm32` / `ecat_hal_hpm` 这些直接 include 厂商头、操作寄存器的实现，一律在底层。

### 3.2 中间层的三层内部结构（关键）

**中间层只放协议栈，不放驱动。** 用户 2026-11-12：「中间层你他妈把驱动放进去干什么？我他妈说放协议栈你他妈全放进去了？」

```text
上层  framework/{modules,algorithm,topic,init,shell,cmd,drivers} + framework/project/
   │
   │  驱动（Pwm/Output/Input/Encoder/Can/Spi/UartDma/Rs485/EcatPhy）在上层自己家
   │  协议栈的门面（usb.hpp / ethercat.hpp）也在上层 drivers/ 下
   ▼
┌─────────────────────────────────────────────────────────┐
│ 中间层  midlayer/  —— 只有协议栈                          │
│                                                          │
│  usb/                                                    │
│    usb.hpp          门面：Init / Read / Send              │
│    usb_rx_queue.hpp                                      │
│    core/            枚举 / CDC / 描述符 / 端点（1398 行）  │
│                                                          │
│  ethercat/                                               │
│    ethercat.hpp     门面：EthercatSlave<Rx,Tx>            │
│    core/            AL状态机 / 邮箱 / SDO / PDO（8252 行） │
│                                                          │
│  · 纯 C++，只碰 Zephyr 通用 API，零厂商符号               │
└─────────────────────────────────────────────────────────┘
   │  只 include zephyr/contract/（usb_hal.hpp / ecat_esc.hpp）
   ▼
底层  zephyr/
      ├── contract/   契约（纯虚，零 Zephyr 零厂商）
      └── drivers/    实现契约（usb_hal_hpm / usb_hal_stm32 / ecat_hal_hpm）
```

**实测对应关系**：

| 内容 | 未来路径 | 行数 | 归属 |
|---|---|---|---|
| USB 协议栈 | `midlayer/usb/core/`（1398） | 1398 | **中间层** |
| EtherCAT 协议栈 | `midlayer/ethercat/core/`（8252） | 8252 | **中间层** |
| 门面 | `midlayer/usb/usb.hpp`、`midlayer/ethercat/ethercat.hpp` | 约 200 | **中间层**（上层 include 它） |
| 契约 | `zephyr/contract/`（原 interface 目录） | 796 | **底层**（底层实现它） |
| 驱动 | `framework/drivers/device/`（1228）、`can/`+`spi/`（458）、`uart/`+`rs485/`（865）、`stream.hpp` | 2551 | **上层**（原地不动） |

**这条正是用户强调的点**：`usb/core` + `ethercat/core` = **9650 行**是中间层的全部内容——它们是协议栈，**上层不需要看，底层也不合适放**。驱动不是协议栈，不进 midlayer。

### 3.3 三层判据

| 层 | 判据 | 典型特征 | 上层能否看见 |
|---|---|---|---|
| **底层** | **与芯片耦合**：直接调厂商 API、操作寄存器、写 `DEVICE_DT_DEFINE`、定义 binding | `hpm_esc_*` / `HAL_PCD_*` / `stm32_ll_*` / `module.yml` / binding yaml / `board.cmake` | **完全看不见** |
| **中间层** | **有协议状态机**：把底层的字节流变成协议实现（枚举、握手、状态迁移、帧解析） | 纯 C++，依赖 Zephyr 通用 API，**不碰厂商 API**；**有状态机 / 有帧格式 / 有时序** | **只看见门面类**，看不见协议细节 |
| **上层** | **业务语义 + 类驱动**：算法、数据契约、生命周期、业务线程、外设类驱动 | 零硬件依赖（类驱动依赖 Zephyr 通用 API） | — |

**一句话区分**：

> 底层回答"**芯片怎么动**"，中间层回答"**协议怎么走**"，上层回答"**数据怎么用**"。

**关键分界（驱动 vs 协议栈）**：

| 对象 | 有协议状态机？ | 归属 |
|---|---|---|
| `usb/core`（枚举/CDC/描述符/端点） | **有**（USB 枚举状态机、SETUP 握手、端点状态） | 中间层 |
| `ethercat/core`（AL 状态机/邮箱/SDO/PDO） | **有**（AL 状态迁移、邮箱时序、SDO 分段） | 中间层 |
| `device/pwm`（`pwm_set_dt()` 转发） | 无 | 上层驱动 |
| `device/gpio`（`gpio_pin_set_dt()` 转发） | 无 | 上层驱动 |
| `communication/can`（`can_send()` 转发） | 无 | 上层驱动 |
| `communication/stream/uart`（DMA 收发） | 无（帧处理在业务侧） | 上层驱动 |

**关键结论**（2026-11-12 用户纠正后）：

- **中间层只放协议栈**：`usb/core`（1398）+ `ethercat/core`（8252）= **9650 行**，加上两个门面头约 200 行。
- **驱动留在上层**：`Pwm` / `Output` / `Input` / `Encoder` / `EcatPhy` / `Can` / `Spi` / `Stream` / `UartDma` / `Rs485` 全部留在 `framework/drivers/`，**一行不搬**。

### 4.4 优点与代价

**优点**：

- **三个平级目录 = 一眼看清分层**。打开仓库根就看到 `zephyr/ midlayer/ framework/`，不用读 README。
- **协议栈终于有独立位置**。`midlayer/usb/core/`（1398 行）和 `midlayer/ethercat/core/`（8252 行）这两个协议栈有了明确归属——不是底层（不碰寄存器），不是上层（上层不需要看）。
- **驱动和上层六模块几乎不动**。`framework/{algorithm,modules,topic,init,shell,cmd}` 和 `framework/drivers/{device,can,spi,stream}` 一行路径都没变。
- **依赖方向靠目录就能判**：`framework/` 只能 include `midlayer/` 的门面，`midlayer/` 只能 include `zephyr/contract/`，`zephyr/` 谁也不 include。

**代价（必须如实说明）**：

1. **`usb.hpp` / `ethercat.hpp` 的 include 路径要改**：从 `framework/drivers/communication/stream/usb` 变成 `midlayer/usb`，`framework/drivers/communication/ethercat` 变成 `midlayer/ethercat`。**这是纯 CMake include 路径调整，源码里的 `#include "usb.hpp"` 写法不变**。
2. **`framework/drivers` 这个子模块要重组**：把 `stream/usb/` 和 `ethercat/` 两个协议栈目录拆出去。**这是最大的决策点**——见 §8.2 第 9 条。
3. **`framework/project/CMakeLists.txt` 的路径改**：`FW_ROOT` 要加 `MIDLAYER_ROOT` / `ZEPHYR_ROOT`，`ZEPHYR_USER_DIR` 也要重新算（`project/` 从根目录进了 `framework/`，相对深度变了）。
4. **所有用户区（`E:\Zephyr\projects\*`）的 `project/CMakeLists.txt` 同步**：7 个工作区各带一份。
5. **文档全量重写**：`README.md`（架构总述）、`子树架构介绍.md`（11 节）、`framework/drivers/ARCHITECTURE.md`（24339 字节）、`midlayer/README.md`（新建）、`framework/*/README.md`（7 份）、`doc/zephyr_子树架构搭建指南.md`、`doc/zephyr_HPM_搭建指南.md`、`快速上手.md`。

### 5.3 共享契约（底层内部的 `contract/`）

**共享契约 = 纯虚基类 + 纯数据类型，零 Zephyr 依赖，零厂商依赖。** 当前符合的 6 个头，共 831 行：

| 头文件 | 行数 | 内容 | 当前位置 |
|---|---|---|---|
| `usb_hal.hpp` | 175 | USB 硬件抽象（纯虚） | `framework/drivers/communication/stream/usb/interface/` |
| `usb_types.hpp` | 174 | USB 数据类型 | 同上 |
| `ecat_esc.hpp` | 188 | ESC 能力契约（纯虚） | `framework/drivers/communication/ethercat/interface/` |
| `ecat_types.hpp` | 188 | EtherCAT 数据类型 | 同上 |
| `ecat_profile.hpp` | 71 | PDO 布局描述 | 同上 |
| `esf_dump.hpp` | 35 | 异常栈帧转储接口（**含 `<zephyr/kernel.h>`，不纯净**） | `framework/cmd/fatal/` |

**按用户判据（HAL 与芯片耦合 → 归底层），契约属于底层**——它是"底层实现必须满足的形状"，不是"上层要用到的东西"。所以物理上应放 `zephyr/contract/`，底层实现 include 它，中间层也 include 它（**契约是唯一允许跨层双向引用的东西**）。

**为什么契约不能留原位**：契约在 `framework/drivers/.../interface/` 时，底层 `drivers/` include 它 = 底层依赖中间层，这正是当前 9 处反向依赖里"看起来合理"的那 4 处。抽到 `zephyr/contract/` 后，这个方向就变成"底层内部引用"，依赖图彻底单向。

## 6. 分阶段执行方案

> **本规划按阶段写。每阶段开头一张步表，一行 = 一个文件（或一组必须同改的同概念文件）。**
> 用户说"开始第 N 步" = 只改表格里那一行对应的文件，改完停下报告，等"继续"。
