# 四套电控架构详解与评分

> 文档版本：2026-08-01 源码树版
>
> 评测对象：`zephyr_user`、`basic_framework-master`、`COD_H7_Template_CLion-main`、`Dust_SentinelRobot_L_Game`
>
> 文档定位：以 `zephyr_user` 为主线，比较四套电控工程的组织方式、代码设计、构建装配、团队协作和整机闭环能力。
>
> 核心主题：`zephyr_user` 是公共子树，也是维护者或电控组组长的父级工作区；普通使用者在同级目录建立自己的子级工作区，通过 CMake 消费公共能力。

## 阅读说明

这不是一篇只看目录数量的排名。

也不是把四个项目强行放到同一条技术路线上的比较。

四个项目解决的问题并不完全相同。

`basic_framework-master` 更像队伍级基础框架。

`COD_H7_Template_CLion-main` 更像单板电控模板。

`Dust_SentinelRobot_L_Game` 更像具体机器人整机工程。

`zephyr_user` 更像正在形成的平台型公共子树。

因此，本文首先回答：

```text
这四个项目到底在解决什么问题？
```

然后回答：

```text
zephyr_user 为什么要改成子树？
```

再回答：

```text
维护者、组长、普通成员和产品项目之间是什么关系？
```

最后才给出：

```text
横向评分
适用场景
迁移路线
成熟度判断
```

本文不会把“机制已经存在”和“产品已经完全接线”混为一谈。

本文也不会把“已经比赛验证”和“平台设计能力”混为一谈。

## 一、阅读范围与比较方法

### 1.1 比较对象

当前工作区中的四个评测对象是：

```text
zephyr_user
temp/basic_framework-master
temp/COD_H7_Template_CLion-main
temp/Dust_SentinelRobot_L_Game
```

本文中的 `COD_H7` 是：

```text
temp/COD_H7_Template_CLion-main
```

本文中的 `Dust` 是：

```text
temp/Dust_SentinelRobot_L_Game
```

本文中的 `basic` 是：

```text
temp/basic_framework-master
```

本文中的 `zephyr_user` 是当前仓库根目录：

```text
E:\Zephyr\zephyr_user
```

### 1.2 本文的比较重点

本文不把四个项目简单归纳成：

```text
C 工程
C++ 工程
FreeRTOS 工程
Zephyr 工程
```

这样的标签太粗。

本文重点观察以下问题：

```text
谁拥有公共代码？
谁拥有产品变化？
谁决定板卡连接？
谁决定线程组合？
谁决定初始化顺序？
谁决定模块是否进入编译？
谁决定注册对象是否进入镜像？
谁决定线程之间的数据语义？
谁负责公共模块维护？
普通成员如何消费公共能力？
```

### 1.3 五种评价维度

#### 系统组织中心

一个工程到底围绕什么组织。

可能是：

```text
中央初始化函数
固定任务表
Robot 对象
模块实例
消息契约
项目装配
父子工作区
```

#### 职责边界

一个变化应该落在哪个目录。

可能的变化包括：

```text
引脚变化
总线变化
传感器变化
协议变化
算法变化
控制策略变化
线程周期变化
调试功能变化
```

#### 编译和运行装配

观察：

```text
Kconfig 是否决定功能存在
CMake 是否决定源码进入
DeviceTree 是否描述硬件
linker 是否保留注册项
启动器是否拥有统一生命周期
```

#### 团队与权限

观察：

```text
公共代码由谁修改
产品代码由谁修改
版本由谁发布
用户是否需要复制公共模块
修改是否可以集中审查
```

#### 业务闭环

观察：

```text
输入
采集
估计
目标
控制
输出
保护
整机策略
```

### 1.4 评分纪律

本文坚持以下纪律：

```text
目录存在不等于功能接通。
接口存在不等于产品正在使用。
机制先进不等于实战成熟。
实战稳定不等于跨项目复用能力强。
文档描述必须和真实源码入口对应。
```

## 二、先给结论

### 2.1 四个项目的一句话定位

| 项目 | 一句话定位 |
| --- | --- |
| `zephyr_user` | 以 Zephyr 为底座、以 framework 为公共子树、以 project 为产品装配、以维护者和使用者上下级关系为组织边界的平台型架构 |
| `basic_framework-master` | 以 `bsp / modules / application`、实例、pub-sub 和队伍文档为核心的成熟 STM32 基础框架 |
| `COD_H7_Template_CLion-main` | 以 STM32H723、CubeMX、FreeRTOS、固定任务和 CLion/CMake 工具链为核心的单板模板 |
| `Dust_SentinelRobot_L_Game` | 以 Robot 对象、设备拓扑、模块自含线程和整机策略为核心的具体机器人工程 |

### 2.2 如果评价平台架构能力

按照当前代码设计能力和可扩展边界：

```text
zephyr_user
    >
basic_framework-master
    >
Dust_SentinelRobot_L_Game
    >
COD_H7_Template_CLion-main
```

`zephyr_user` 的领先点不是“目录多”。

领先点是：

```text
公共代码和产品代码有意分开。
编译、链接、启动和数据都有独立边界。
板卡和 thread 被留给产品工作区。
公共能力可以由维护者集中维护。
```

### 2.3 如果评价单台机器人的整机闭环

按照当前整机业务完成度：

```text
Dust_SentinelRobot_L_Game
    >
basic_framework-master
    >
zephyr_user
    >
COD_H7_Template_CLion-main
```

这里 Dust 的优势是：

```text
Robot 总控已经存在。
设备拓扑已经形成。
底盘、云台、拨弹和通信已经组合。
```

这里 `zephyr_user` 的排名较低不是因为平台设计差。

而是因为：

```text
平台正在持续装配。
部分产品线程仍然处于项目接线阶段。
尚未经历同等规模的比赛验证。
```

### 2.4 如果评价团队长期演进

最准确的排序是：

```text
zephyr_user
    >
basic_framework-master
    >
Dust_SentinelRobot_L_Game
    >
COD_H7_Template_CLion-main
```

原因是长期演进首先要求：

```text
公共能力能够集中维护。
产品变化不会污染公共层。
新项目不需要复制整个旧工程。
版本能够固定。
新成员能够沿着边界学习。
```

### 2.5 `zephyr_user` 真正想解决的问题

它不是单纯想解决：

```text
如何把 GPIO 写出来。
如何把 CAN 发出去。
如何创建一个线程。
```

这些问题任何一套工程都能解决。

它真正想解决的是：

```text
同一支电控组如何维护多块板卡。
同一套公共模块如何服务多个机器人。
普通成员如何只修改自己的产品代码。
公共修复如何一次修改、多项目受益。
架构升级如何通过版本指针统一下发。
```

### 2.6 最短结论

```text
basic 把队伍经验变成了规则。
COD 把单板能力变成了模板。
Dust 把设备和策略变成了整机。
zephyr_user 把公共能力、产品装配和团队权限变成了上下级子树。
```

## 三、zephyr_user 的真实身份

### 3.1 它不是普通应用工程

普通应用工程通常长这样：

```text
一个工程
一块板
一套任务
一套设备
一个编译入口
```

`zephyr_user` 的设计目标不是只承载这一组关系。

它希望承载：

```text
多个公共驱动
多个算法组件
多个设备协议
多个产品线程
多个板卡接线
多个项目配置
```

因此它必须同时具有：

```text
库的能力
平台的能力
仓库的能力
维护者工作区的能力
```

### 3.2 它是公共子树

`framework/` 下的内容不是某个机器人独占的业务代码。

当前结构包括：

```text
framework/drivers
framework/algorithm
framework/modules
framework/topic
framework/cmd
framework/init
```

这些目录共同组成公共能力树。

公共能力树的核心特点是：

```text
多个项目可能使用。
不能绑定某一个 Robot。
需要统一接口。
需要统一修复。
需要统一版本。
```

### 3.3 它也是维护者工作区

`zephyr_user` 同时是维护者或电控组组长工作区。

维护者在这里负责：

```text
规划公共层。
新增公共模块。
维护公共模块。
维护 board 支持。
维护 DeviceTree binding。
维护启动注册器。
维护链接脚本。
维护构建关系。
维护版本组合。
维护架构文档。
```

这就是为什么 `zephyr_user` 不能只被理解成一个使用者项目。

它在组织关系上属于：

```text
父级能力树
```

### 3.4 当前 `project/` 的位置

当前仓库中的：

```text
project/
```

是维护者仓库里的一个验证和产品装配工作区。

它负责验证：

```text
公共框架能否被实际装配。
板卡是否能被 DeviceTree 描述。
线程是否能通过 Kconfig 和 CMake 进入。
初始化注册是否能被链接器收集。
topic 是否能连接到真实业务线程。
```

未来的普通使用者工作区可以位于：

```text
E:\Zephyr\zephyr_user
E:\Zephyr\robot_a_user
E:\Zephyr\robot_b_user
E:\Zephyr\experiment_user
```

其中 `robot_a_user`、`robot_b_user` 和 `experiment_user` 是同级目录。

它们共同依赖：

```text
E:\Zephyr\zephyr_user
```

### 3.5 为什么必须区分两个身份

如果不区分：

```text
公共子树
维护者工作区
产品工作区
```

就会出现一种危险误解：

```text
所有人都可以把所有代码都放在同一个仓库里修改。
```

短期看起来方便。

长期会造成：

```text
公共驱动被临时需求污染。
一个产品的参数进入所有产品。
公共模块出现多个本地复制版本。
维护者无法判断哪个版本是正式版本。
普通成员不敢升级框架。
新成员不知道应该从哪里开始。
```

### 3.6 子树重构的根本原因

这次子树重构真正要解决的不是目录美观。

而是下面这条关系：

```text
公共能力集中在父级。
产品变化集中在子级。
子级通过构建系统消费父级。
父级通过版本和审查治理公共能力。
```

这条关系可以缩写成：

```text
父级提供复杂度。
子级提供产品语义。
```

### 3.7 这种架构的核心气质

它不是：

```text
把所有代码都藏起来。
把所有成员都限制住。
把产品变化都交给维护者。
```

它是：

```text
把公共复杂度集中治理。
把产品变化留给产品负责人。
把跨项目能力放到可复用层。
把临时实验限制在用户工作区。
```

### 3.8 设计目标的完整表达

`zephyr_user` 希望建立这样的系统：

```text
维护者维护 framework。
维护者维护公共 board 能力。
维护者维护启动和链接边界。
普通成员维护自己的 boards。
普通成员维护自己的 thread。
普通成员选择 Kconfig。
普通成员通过 CMake 引入公共子树。
```

这不是单纯的软件分层。

这是：

```text
代码分层
构建分层
版本分层
责任分层
权限分层
```

## 四、维护者父级工作区与用户子级工作区

### 4.1 目录关系

理想的同级工作区关系如下：

```text
E:\Zephyr\
├── zephyr_user\
│   ├── framework\
│   │   ├── drivers\
│   │   ├── algorithm\
│   │   ├── modules\
│   │   ├── topic\
│   │   ├── cmd\
│   │   └── init\
│   ├── platform\
│   ├── boards\
│   ├── dts\
│   ├── project\
│   └── 子树架构详解.md
│
├── robot_a_user\
│   ├── CMakeLists.txt
│   ├── Kconfig
│   ├── prj.conf
│   ├── boards\
│   └── thread\
│
├── robot_b_user\
│   ├── CMakeLists.txt
│   ├── Kconfig
│   ├── prj.conf
│   ├── boards\
│   └── thread\
│
└── experiment_user\
    ├── CMakeLists.txt
    ├── prj.conf
    ├── boards\
    └── thread\
```

### 4.2 父级依赖方向

正确方向是：

```text
robot_a_user
    -> zephyr_user
```

```text
robot_b_user
    -> zephyr_user
```

```text
experiment_user
    -> zephyr_user
```

不应该形成：

```text
robot_a_user
    <-> robot_b_user
```

也不应该形成：

```text
robot_a_user
    -> framework 内部某个临时分支
```

更不应该形成：

```text
每个用户复制一份 drivers。
每个用户复制一份 modules。
每个用户复制一份 init。
```

### 4.3 用户工作区的最小内容

普通使用者真正必要的内容是：

```text
CMakeLists.txt
Kconfig
prj.conf
boards/
thread/
```

`boards/` 的责任是：

```text
选择板卡。
描述 overlay。
放置产品级 conf。
提供 board.cmake。
绑定产品使用的外设。
```

`thread/` 的责任是：

```text
启动产品线程。
读取公共 topic。
调用公共模块。
实现产品控制策略。
组织控制周期。
```

`Kconfig` 的责任是：

```text
声明产品功能开关。
选择需要的公共模块。
表达产品依赖关系。
```

`prj.conf` 的责任是：

```text
给当前产品提供默认配置。
打开需要的 Zephyr 能力。
打开需要的公共能力。
```

`CMakeLists.txt` 的责任是：

```text
接入 Zephyr。
接入父级子树。
接入产品 boards。
接入产品 thread。
```

### 4.4 用户不需要复制的内容

普通使用者不需要复制：

```text
framework/drivers
framework/algorithm
framework/modules
framework/topic
framework/cmd
framework/init
platform/cmsis
```

原因不是这些目录不能被阅读。

原因是：

```text
阅读和使用不等于复制和分叉。
```

用户可以阅读公共实现。

用户可以提交问题。

用户可以提交修改建议。

用户可以在自己的工作区做临时验证。

但正式公共修改应回到：

```text
维护者工作区
公共子模块仓库
公共版本发布流程
```

### 4.5 用户工作区负责什么

用户工作区负责产品语义：

```text
这辆车使用哪个板。
这辆车打开哪些线程。
这辆车底盘的控制周期是多少。
这辆车云台采用什么模式。
这辆车是否启用遥控器。
这辆车是否启用 PC 通信。
这辆车的产品参数是什么。
```

这些问题没有唯一公共答案。

因此必须留在用户工作区。

### 4.6 父级子树负责什么

父级子树负责公共能力：

```text
如何访问 GPIO。
如何访问 PWM。
如何发送 CAN。
如何接收 UART DMA。
如何封装 IMU。
如何探测 Remote 协议。
如何表达 topic。
如何启动线程。
如何注册初始化项。
如何实现 shell。
如何控制 buzzer。
如何访问 Flash。
```

这些问题应该尽量形成稳定接口。

### 4.7 board 为什么属于用户变化

板卡连接是产品最常见的差异。

不同产品可能使用：

```text
不同 MCU。
不同 CAN 控制器。
不同 UART。
不同 SPI。
不同 PWM。
不同 IMU。
不同 Flash。
不同调试串口。
```

这些变化优先落在：

```text
boards/
overlay
conf
board.cmake
```

而不是复制公共驱动。

### 4.8 thread 为什么属于用户变化

不同产品的控制策略不可能完全相同。

不同产品可能拥有：

```text
不同底盘。
不同云台。
不同射击机构。
不同传感器组合。
不同控制周期。
不同优先级。
不同安全降级。
不同上位机协议。
```

这些变化优先落在：

```text
thread/
```

而不是修改公共设备模块。

### 4.9 project 与同级用户工作区的关系

当前仓库的：

```text
project/
```

可以作为维护者验证用的产品示例。

它展示：

```text
板卡如何接入。
Kconfig 如何选择。
CMake 如何装配。
线程如何注册。
topic 如何连接。
```

同级用户工作区不必原样复制它。

更合理的做法是：

```text
借鉴 project 的装配方式。
保留自己的 boards。
保留自己的 thread。
按产品重新选择 Kconfig。
```

### 4.10 父级和子级的边界矩阵

| 变化类型 | 普通用户是否直接修改 | 推荐位置 | 维护者职责 |
| --- | --- | --- | --- |
| 产品板卡 overlay | 是 | 用户 `boards/` | 提供公共 board 支持 |
| 产品 board conf | 是 | 用户 `boards/` | 维护默认约定 |
| 产品线程 | 是 | 用户 `thread/` | 提供公共模块 API |
| 产品控制参数 | 是 | 用户配置或 thread | 维护接口稳定性 |
| 公共 GPIO 驱动 | 否，提交需求 | `framework/drivers` | 统一修复和发布 |
| 公共算法 | 否，提交需求 | `framework/algorithm` | 维护算法接口 |
| IMU 设备协议 | 否，提交需求 | `framework/modules` | 统一设备模型 |
| Remote 协议 | 否，提交需求 | `framework/modules/remotes` | 统一探测和解码 |
| topic 数据契约 | 评审后修改 | `framework/topic` | 维护兼容性 |
| 初始化注册器 | 否 | `framework/init` | 维护启动顺序 |
| 链接段 | 否 | `framework/cmd/linker` | 维护镜像收集规则 |
| 公共调试工具 | 否，提交需求 | `framework/cmd` | 维护横切能力 |

### 4.11 “普通用户不能随意修改”到底是什么意思

这句话包含三个层次。

#### 架构层次

公共代码不放到每个用户的工作区里。

用户通过外部路径消费：

```text
framework
platform
```

这样用户不会自然地把公共实现当成自己的业务文件。

#### 版本层次

公共模块由独立仓库或 submodule 记录版本。

根仓库记录：

```text
framework/drivers 的提交指针
framework/algorithm 的提交指针
framework/modules 的提交指针
framework/topic 的提交指针
framework/cmd 的提交指针
framework/init 的提交指针
```

用户使用的是一个经过组合的公共版本。

#### 权限层次

CMake 不是权限系统。

真正限制写入需要：

```text
Git 仓库权限。
protected branch。
代码评审。
CI 检查。
发布权限。
文件系统 ACL。
```

三者必须分开理解。

### 4.12 CMake 能做什么

CMake 可以：

```text
让用户引用父级源码。
让用户不需要复制公共源码。
让用户选择需要的模块。
让用户加入自己的 thread。
让用户指定 BOARD_ROOT。
让用户指定 DTS_ROOT。
```

### 4.13 CMake 不能做什么

CMake 不能单独保证：

```text
用户无法打开 framework 文件。
用户无法修改本地 submodule。
用户无法复制公共代码。
用户无法绕过构建系统。
用户无法把临时补丁提交到公共仓库。
```

因此完整治理关系是：

```text
架构负责划分边界。
CMake 负责消费关系。
Git 负责版本关系。
权限系统负责写入关系。
评审流程负责质量关系。
```

### 4.14 父级子树的价值

父级子树不是为了把所有人变成只会调用 API 的人。

它的价值是让公共问题集中发生。

例如：

```text
UART DMA 缓冲区错误。
CAN 过滤器错误。
IMU 温控异常。
Remote 协议误判。
Flash 擦除边界错误。
启动阶段错误。
```

如果每个项目都有一份复制代码。

这些问题就会变成：

```text
robot_a 修一遍。
robot_b 再修一遍。
experiment 再修一遍。
```

如果公共代码集中维护。

它们可以变成：

```text
维护者修一遍。
公共版本发布一次。
多个用户更新指针。
```

### 4.15 子树不是单向压制

父级关系不是：

```text
维护者永远正确。
用户永远不能提出意见。
用户只能等待。
```

合理的关系是：

```text
用户提出需求。
用户提供复现工程。
用户提供测试数据。
维护者判断是否公共化。
维护者在 framework 实现。
维护者更新文档。
维护者发布版本。
用户更新父级指针。
```

### 4.16 父级提供复杂度，子级提供产品语义

这句话不是口号。

它可以逐项展开：

```text
父级提供 CAN 发送能力。
子级决定发送哪一个产品命令。
```

```text
父级提供 IMU 状态。
子级决定姿态如何参与控制。
```

```text
父级提供 Remote 解码。
子级决定遥控器如何映射到底盘。
```

```text
父级提供 topic。
子级决定谁订阅、何时订阅、如何使用。
```

```text
父级提供启动器。
子级决定哪些 thread 被打开。
```

### 4.17 这一部分的结论

`zephyr_user` 的子树设计不是普通的目录拆分。

它同时拆分了：

```text
代码所有权。
构建所有权。
版本所有权。
产品责任。
公共责任。
```

这正是它相对于三个传统单仓工程最有价值的地方。

## 五、上下级关系与团队治理

### 5.1 为什么上下级关系是架构的一部分

嵌入式团队中的很多问题表面是代码问题。

实际是责任问题：

```text
谁可以改驱动？
谁决定协议兼容？
谁发布版本？
谁承担回归？
谁负责板卡？
谁负责整车线程？
```

如果这些问题没有边界。

代码结构再漂亮也会被协作方式破坏。

### 5.2 维护者角色

维护者或电控组组长负责：

```text
制定公共层边界。
维护公共 submodule。
规划新板卡。
接入新的 MCU 平台。
审查公共 API。
维护 Kconfig 依赖。
维护 linker 注册段。
维护公共文档。
维护发布版本。
```

维护者不应该替每个产品实现全部业务策略。

维护者应该提供：

```text
稳定能力。
清楚接口。
可追踪版本。
可复现构建。
```

### 5.3 普通成员角色

普通成员或使用者负责：

```text
选择板卡。
维护板级 overlay。
实现产品 thread。
配置产品参数。
连接公共 topic。
验证实际机器人。
记录产品故障。
```

普通成员不需要维护：

```text
公共 SPI API。
公共 CAN API。
公共 IMU 基类。
公共 Remote 探测器。
公共启动器。
公共链接段。
```

### 5.4 产品负责人角色

产品负责人可以拥有比普通成员更大的业务工作区权限。

但仍然应该遵守：

```text
产品策略放在产品工作区。
公共能力修改回到公共仓库。
临时补丁必须标记来源。
进入公共层的代码必须经过评审。
```

### 5.5 公共化判断

一个功能是否应该进入父级子树，可以问：

```text
是否有两个以上项目需要？
是否与某一台 Robot 无关？
是否可以定义稳定接口？
是否需要统一修复？
是否值得维护版本？
```

如果大多数答案是“是”：

```text
进入 framework。
```

如果答案是：

```text
只服务当前机器人。
只服务某个产品策略。
只用于一次性实验。
```

优先留在：

```text
用户 thread。
用户 boards。
用户 test。
```

### 5.6 公共模块变更流程

推荐流程：

```text
用户提出需求。
用户描述使用场景。
用户提供当前接口。
用户提供复现或测试。
维护者判断层归属。
维护者在对应 submodule 实现。
维护者补充文档。
维护者执行静态检查。
维护者发布子模块提交。
根仓库更新 gitlink。
用户升级组合版本。
```

### 5.7 用户本地临时修改

临时调试可以存在。

但必须区分：

```text
本地实验补丁。
产品工作区修改。
公共模块正式修改。
```

不能把本地实验补丁误认为公共版本。

也不能把公共修复只留在某个用户目录。

### 5.8 版本指针的意义

`.gitmodules` 中的每个 submodule 都是一个版本边界。

根仓库不直接复制所有公共代码历史。

它记录：

```text
当前组合使用哪个 drivers 提交。
当前组合使用哪个 algorithm 提交。
当前组合使用哪个 modules 提交。
当前组合使用哪个 topic 提交。
当前组合使用哪个 cmd 提交。
当前组合使用哪个 init 提交。
```

这样升级可以被描述成：

```text
升级父级组合。
```

而不是：

```text
把六套公共目录逐个复制。
```

### 5.9 保护父级边界的制度

建议至少具备：

```text
framework 仓库写入权限。
主分支保护。
公共模块合并请求。
至少一名维护者审核。
基础构建检查。
接口变更说明。
版本记录。
```

### 5.10 治理不是官僚流程

治理的目的不是增加审批。

治理的目的，是避免：

```text
公共模块被无意破坏。
产品补丁被误发布。
用户之间互相覆盖修改。
同名 API 出现多个版本。
错误修复只存在于某个人电脑。
```

### 5.11 代码边界和人员边界一致

理想状态是：

```text
框架维护者维护 framework。
板卡维护者维护 boards。
产品成员维护 thread。
调试成员维护 scripts 和 test。
```

人员职责与目录职责重合。

问题定位会更快。

### 5.12 上下级关系的最终表达

```text
父级不是产品。
子级不是框架。
父级维护能力。
子级完成装配。
父级发布版本。
子级选择版本。
父级解决共性。
子级解决个性。
```

## 六、zephyr_user 的代码设计艺术

### 6.1 这里说的“艺术”是什么

这里的艺术不是炫技。

不是为了让代码看起来高级。

也不是为了增加抽象层数量。

这里的艺术是：

```text
让每一种变化进入正确的位置。
让每一种复杂度拥有明确的所有者。
让构建系统替团队记住依赖。
让链接器替中央注册表收集对象。
让数据契约替直接调用表达语义。
```

### 6.2 按变化原因分流

`zephyr_user` 最核心的设计可以写成：

```text
硬件引脚变化
    -> DeviceTree / board
```

```text
总线访问变化
    -> drivers
```

```text
设备协议变化
    -> modules
```

```text
数学模型变化
    -> algorithm
```

```text
线程数据语义变化
    -> topic
```

```text
产品策略变化
    -> project/thread
```

```text
运行期调试变化
    -> cmd
```

```text
启动生命周期变化
    -> init
```

### 6.3 五道边界

这套架构最重要的五道边界是：

```text
Kconfig
    决定功能是否存在。
```

```text
CMake
    决定哪些源码进入目标。
```

```text
DeviceTree
    决定硬件实例如何连接。
```

```text
linker
    决定注册对象是否被保留以及边界符号在哪里。
```

```text
startup
    决定对象什么时候运行以及失败如何处理。
```

数据侧还有第六道边界：

```text
topic
    决定线程之间传递什么语义。
```

### 6.4 功能存在和源码进入不是一回事

Kconfig 的作用是：

```text
声明功能。
表达依赖。
选择底层能力。
```

CMake 的作用是：

```text
根据配置加入源文件。
设置头文件路径。
连接架构子目录。
```

两者配合后：

```text
关闭功能。
源文件不进入。
相关注册对象不产生。
镜像不保留无用能力。
```

这比在所有代码里写：

```cpp
if (feature_enabled) {
    ...
}
```

更彻底。

### 6.5 编译期裁剪的意义

编译期裁剪带来的不是只有体积变化。

它还带来：

```text
依赖更明确。
死代码更少。
初始化表更小。
线程数量更清楚。
资源占用更容易估算。
```

### 6.6 设备树的设计艺术

业务代码不应该关心：

```text
某块板的 UART 编号。
某个 MCU 的 SPI 实例号。
某个产品的 PWM 引脚号。
```

业务代码应该关心：

```text
remote-uart
user-can1
imu-spi
imu-pwm
buzzer-pwm
flash-spi
pc-usb
```

这就是语义别名的价值。

### 6.7 板卡身份和产品接线分开

根 `boards/` 的职责是：

```text
给 Zephyr 提供用户板卡。
```

产品 `project/boards/` 的职责是：

```text
描述当前产品如何使用板卡。
```

两者不是一回事。

同一块硬件板可以服务多个产品。

多个产品可以通过不同 overlay 使用同一板卡。

### 6.8 初始化注册的艺术

传统方式是：

```cpp
InitEntry entries[] = {
    {"gpio", gpio_init},
    {"imu", imu_init},
    {"remote", remote_init},
};
```

新增一个模块时要修改中心数组。

多个成员同时新增模块时容易冲突。

`zephyr_user` 使用：

```text
本地声明。
链接聚合。
运行时遍历。
```

组件在自己的文件中注册：

```cpp
REGISTER_INIT(fn, stage, level, name);
```

链接脚本收集：

```ld
KEEP(*(.user_init))
```

启动器遍历：

```cpp
for (const InitEntry* e = start; e < end; ++e) {
    e->func();
}
```

### 6.9 这不是魔法

注册式设计仍然有清晰链路：

```text
宏展开
    -> 静态对象
        -> section
            -> linker KEEP
                -> start/end 符号
                    -> 运行时遍历
```

每一步都可以在源码和链接脚本中验证。

### 6.10 注册机制的扩展

当前同一类思想可以用于：

```text
初始化项。
线程项。
Remote 协议。
IMU 设备。
CAN 接收处理器。
Shell 变量。
```

这说明它不是一次性的技巧。

它是一种可复用的架构公式：

```text
声明。
收集。
保留。
遍历。
```

### 6.11 阶段和等级分离

`InitStage` 解决：

```text
什么时候初始化。
```

`ThreadStage` 解决：

```text
什么时候启动线程。
```

`InitLevel` 解决：

```text
失败后停机还是继续。
```

这三个问题如果混在一个枚举里，会导致：

```text
初始化时机不清楚。
失败策略不清楚。
线程启动关系不清楚。
```

分开之后可以表达：

```text
IMU 在 EarlyInit 初始化。
IMU 线程在 EarlyThread 启动。
IMU 失败属于 High。
```

### 6.12 失败等级的工程含义

High 失败：

```text
记录错误。
蜂鸣器提示。
系统停机。
```

Mid 失败：

```text
记录警告。
保留其他能力。
```

Low 失败：

```text
记录警告。
允许系统继续运行。
```

这比每个模块自行写：

```cpp
while (1) {}
```

更统一。

### 6.13 数据契约的艺术

直接调用的问题是：

```text
底盘直接抓取遥控器内部变量。
云台直接依赖 UART 接收缓冲区。
CAN 发送线程直接知道所有电机对象。
```

topic 的设计把问题变成：

```text
谁发布。
谁订阅。
数据是什么。
更新频率是多少。
数据是状态还是事件。
队列还是最新值。
```

### 6.14 三类数据

#### 最新状态

适合：

```text
遥控器状态。
IMU 状态。
电机反馈快照。
```

#### 有序消息

适合：

```text
CAN 发送命令。
一次性事件。
控制请求。
```

#### 一致快照

适合：

```text
多电机反馈。
高频控制状态。
中断更新、线程读取。
```

### 6.15 代码设计的最终抽象

`zephyr_user` 的艺术可以总结成：

```text
把“谁改什么”变成目录边界。
把“什么时候编译”变成 Kconfig。
把“编译哪些源文件”变成 CMake。
把“硬件接在哪里”变成 DeviceTree。
把“谁被发现”变成 linker section。
把“什么时候运行”变成 startup stage。
把“怎么通信”变成 topic contract。
把“谁负责维护”变成父子工作区。
```

这不是为了复杂而复杂。

这是为了让变化被定位。

### 6.16 和传统工程的差别

传统工程常见模式：

```text
main 变长。
freertos.c 变长。
CAN switch 变长。
全局变量变多。
宏开关散落。
每个项目复制一份框架。
```

`zephyr_user` 想把它变成：

```text
本地组件声明。
公共能力集中。
产品线程本地。
板卡描述声明式。
配置链可追踪。
版本组合可复现。
```

### 6.17 设计艺术的代价

这套设计不是没有代价。

代价包括：

```text
需要理解 CMake。
需要理解 Kconfig。
需要理解 DeviceTree。
需要理解 linker section。
需要理解 submodule。
需要理解公共接口和产品接口。
```

但长期收益是：

```text
新项目不必复制公共模块。
新成员不会直接修改所有层。
新增功能修改面更小。
公共问题可以统一修复。
```

### 6.18 这一部分结论

`zephyr_user` 的代码设计艺术，不在于使用了多少新名词。

而在于：

```text
每一个机制都对应一个真实变化。
每一个边界都对应一个真实责任。
每一个公共模块都对应一个版本所有者。
每一个产品线程都对应一个产品语义。
```

## 七、zephyr_user framework 六层结构

### 7.1 六层总图

```text
framework/drivers
    硬件访问和传输
        ↓
framework/modules
    设备能力和协议
        ↓
framework/algorithm
    纯计算和状态更新
        ↓
framework/topic
    跨线程数据契约
        ↓
framework/init
    生命周期和启动
        ↓
framework/cmd
    运行期控制和横切工具
```

实际项目装配由：

```text
project/
```

完成。

### 7.2 drivers

drivers 负责：

```text
GPIO。
PWM。
SPI。
CAN。
UART DMA。
RS485。
Stream。
USB 适配。
```

drivers 不负责：

```text
底盘策略。
云台策略。
机器人模式。
产品控制逻辑。
```

### 7.3 modules

modules 负责：

```text
IMU。
Remote。
Motor。
PowerMeter。
设备协议。
设备状态。
设备生命周期。
```

modules 可以调用 drivers。

modules 可以调用 algorithm。

modules 可以发布 topic。

modules 不应该知道某台车的全部策略。

### 7.4 algorithm

algorithm 负责：

```text
PID。
滤波。
四元数。
EKF。
RLS。
功率分配。
推理或模型计算。
```

algorithm 不应该直接持有：

```text
UART。
SPI。
CAN。
GPIO。
Zephyr 线程对象。
某个具体 Robot。
```

### 7.5 topic

topic 负责：

```text
消息结构。
发布方式。
订阅方式。
队列。
快照。
数据所有权说明。
```

topic 不负责：

```text
创建具体设备。
决定产品策略。
实现电机控制。
实现 IMU 寄存器协议。
```

### 7.6 init

init 负责：

```text
main。
System_Startup。
InitStage。
ThreadStage。
InitLevel。
注册表遍历。
失败处理。
```

### 7.7 cmd

cmd 负责：

```text
shell。
buzzer。
Flash。
链接段支持。
构建辅助。
```

cmd 是横切层。

它不应变成底盘业务层。

### 7.8 project

project 负责：

```text
产品 board。
产品 overlay。
产品 conf。
产品 Kconfig。
产品 thread。
产品参数。
产品策略。
```

### 7.9 层之间的正确依赖

```text
project
    -> drivers
    -> modules
    -> algorithm
    -> topic
    -> cmd
```

```text
modules
    -> drivers
    -> algorithm
    -> topic
```

```text
algorithm
    -> 基础类型和数学库
```

```text
topic
    -> Zephyr IPC 或轻量数据结构
```

不希望出现：

```text
algorithm -> project/thread
drivers -> chassis
topic -> 某个具体 Robot
```

### 7.10 层与变化的对应

| 变化 | 首选层 |
| --- | --- |
| UART 实例变化 | board / DeviceTree |
| UART DMA 机制变化 | drivers |
| SBUS 帧格式变化 | modules/remotes |
| 姿态滤波参数变化 | algorithm 或产品配置 |
| IMU 对外状态变化 | topic |
| 底盘逆解变化 | project/thread 或 algorithm |
| shell 命令变化 | cmd |
| 启动错误策略变化 | init |

## 八、编译期装配链

### 8.1 当前真实构建入口

当前仓库的真实业务 CMake 入口是：

```text
project/CMakeLists.txt
```

不是一个虚构的 `src/CMakeLists.txt`。

也不是把所有业务都塞进 `main.c`。

### 8.2 `project/CMakeLists.txt` 的装配责任

它负责：

```text
设置 FW_ROOT。
设置 ZEPHYR_USER_DIR。
设置 BOARD_ROOT。
设置 DTS_ROOT。
设置 SOC_ROOT。
设置 SDK glue。
设置 ZEPHYR_EXTRA_MODULES。
查找 board overlay。
查找 board conf。
接入 Zephyr。
加入 framework 子目录。
加入 thread 子目录。
```

### 8.3 `framework/zephyr/module.yml`

当前 framework 的 module 描述是：

```yaml
name: user_framework
build:
  settings:
    dts_root: drivers/communication/stream/usb
```

它的价值是让 Zephyr 能发现 framework 相关的设备树根路径。

### 8.4 Kconfig 链

产品 Kconfig 可以写：

```text
PRJ_MAIN
    -> TRD_GPIO
    -> TRD_REMOTE
    -> TRD_IMU
    -> TRD_CHASSIS
    -> TRD_GIMBAL
```

线程配置再选择公共能力：

```text
TRD_REMOTE
    -> DUST_MOD_DEV_REMOTE
    -> DUST_MOD_DEV_REMOTE_AUTO
```

```text
TRD_IMU
    -> DUST_MOD_DEV_IMU
    -> DUST_TPC_IMU_TO
```

```text
TRD_CHASSIS
    -> DUST_MOD_DEV_MOTOR_DJI
    -> DUST_MOD_CTL_POWER
    -> DUST_TPC_TO_CAN_TX
```

### 8.5 CMake 链

配置打开后：

```text
CONFIG_TRD_GPIO
    -> 加入 trd_gpio.cpp
```

```text
CONFIG_TRD_REMOTE
    -> 加入 trd_remote.cpp
```

```text
CONFIG_TRD_IMU
    -> 加入 trd_imu.cpp
```

这意味着关闭配置后：

```text
源码不进入。
线程不注册。
依赖可以被裁剪。
```

### 8.6 DeviceTree 链

产品 overlay 负责：

```text
哪个 UART 是遥控器。
哪个 CAN 是电机总线。
哪个 SPI 是 IMU。
哪个 PWM 是蜂鸣器。
哪个 SPI 是 Flash。
哪个 USB 是 PC。
```

业务代码读取语义 alias：

```text
remote-uart
user-can1
imu-spi
buzzer-pwm
flash-spi
pc-usb
```

### 8.7 linker 链

注册宏生成 section。

链接脚本使用：

```ld
KEEP(*(.user_init))
KEEP(*(.user_thread))
KEEP(*(.can_rx1))
KEEP(*(.can_rx2))
KEEP(*(.can_rx3))
KEEP(*(.remote))
KEEP(*(.imu))
KEEP(*(.shell_var))
```

然后产生：

```text
__user_init_start
__user_init_end
__user_thread_start
__user_thread_end
__remote_start
__remote_end
__imu_start
__imu_end
```

### 8.8 startup 链

启动过程是：

```text
framework/init/main.c
    -> System_Startup()
        -> RunStage(PreInit)
        -> RunStage(PreThread)
        -> RunStage(EarlyInit)
        -> RunStage(EarlyThread)
        -> RunStage(MidInit)
        -> RunStage(MidThread)
        -> RunStage(LateInit)
        -> RunStage(LateThread)
        -> RunStage(AppInit)
        -> RunStage(AppThread)
```

### 8.9 完整五层装配图

```text
Kconfig
    决定功能存在
        ↓
CMake
    决定源文件进入
        ↓
DeviceTree
    决定硬件连接
        ↓
linker
    决定注册对象收集
        ↓
startup
    决定运行阶段
```

### 8.10 这条链为什么厉害

传统工程常把这些信息散落：

```text
宏在头文件。
源文件在 IDE 工程。
引脚在 CubeMX。
初始化在 main。
回调在 switch。
线程在 freertos.c。
```

`zephyr_user` 尝试把它们串起来。

每一步都有自己的裁决者。

## 九、启动器与注册式生命周期

### 9.1 `REGISTER_INIT`

`REGISTER_INIT` 表达：

```text
这个组件有一个初始化函数。
这个函数属于哪个阶段。
这个函数失败属于哪个等级。
这个组件应该显示什么名字。
```

### 9.2 `REGISTER_THREAD`

`REGISTER_THREAD` 表达：

```text
这个组件有一个线程启动函数。
这个线程属于哪个阶段。
启动失败采用什么等级。
```

### 9.3 本地注册的价值

线程文件可以自己写：

```cpp
bool thread_init();
bool thread_start();

REGISTER_INIT(thread_init, PreInit, Low, "thread_init");
REGISTER_THREAD(thread_start, PreThread, Low, "thread_start");
```

它不需要修改中央初始化数组。

### 9.4 代码局部性

代码局部性意味着：

```text
实现在哪里。
初始化在哪里。
线程启动在哪里。
注册声明在哪里。
```

可以在同一文件或同一模块附近找到。

### 9.5 中央入口的职责

中央入口只负责：

```text
启动框架。
运行阶段。
处理统一失败。
```

中央入口不负责：

```text
知道每一个业务线程名称。
知道每一种 Remote 协议。
知道每一个 IMU 型号。
知道每一个 CAN ID。
```

### 9.6 运行顺序和开发顺序

启动顺序是运行期事实。

开发时可以先写：

```text
drivers。
modules。
algorithm。
topic。
project/thread。
```

但运行时仍然必须遵守：

```text
基础初始化先于依赖它的模块。
设备初始化先于使用设备的线程。
topic 创建先于发布和订阅。
```

### 9.7 注册不是无序

注册式架构不等于任意顺序。

顺序约束通过：

```text
阶段。
依赖。
配置。
命名。
文档。
```

表达。

### 9.8 失败策略统一

如果每个模块自己决定失败：

```text
一个模块死循环。
一个模块继续。
一个模块复位。
一个模块蜂鸣。
```

系统行为会混乱。

统一 `InitLevel` 后：

```text
High 由启动器停机。
Mid 由启动器告警。
Low 由启动器记录。
```

### 9.9 `trd_gpio.cpp` 的意义

当前 `project/thread/gpio/trd_gpio.cpp` 展示了典型产品线程结构：

```text
本地 Thread 对象。
本地 Task。
本地 init。
本地 start。
REGISTER_INIT。
REGISTER_THREAD。
```

这说明产品 thread 不是把所有公共功能重新实现一遍。

它只负责：

```text
组织当前产品行为。
```

### 9.10 这一部分结论

注册式生命周期的价值是：

```text
让组件拥有自己的启动声明。
让启动器拥有统一执行方式。
让链接器拥有统一收集方式。
让维护者不用维护巨大中央列表。
```

## 十、板卡、设备树与产品 thread

### 10.1 板卡不是产品策略

板卡描述：

```text
硬件是什么。
引脚怎么连。
设备挂在哪条总线。
```

产品线程描述：

```text
如何使用硬件。
如何控制机器人。
如何协调模块。
```

二者必须分开。

### 10.2 board 的变化

board 变化包括：

```text
UART 实例。
CAN 实例。
SPI 实例。
PWM 通道。
GPIO 方向。
传感器地址。
Flash 片选。
USB 控制器。
```

### 10.3 thread 的变化

thread 变化包括：

```text
控制周期。
线程优先级。
模式机。
目标生成。
PID 调用。
CAN 命令。
安全降级。
```

### 10.4 这两个目录为什么留给用户

因为它们正好是：

```text
产品差异最大。
公共复用最少。
需要成员快速迭代。
```

### 10.5 公共模块不应该知道产品 board

公共 IMU 模块应该知道：

```text
如何读取配置的 SPI 设备。
如何初始化传感器。
如何发布状态。
```

它不应该知道：

```text
这是 Robot A。
这是哨兵。
这是某个底盘。
```

### 10.6 公共模块不应该知道产品 thread

电机模块应该知道：

```text
如何接收反馈。
如何生成命令。
如何提供快照。
```

它不应该知道：

```text
底盘采用麦轮。
云台采用串级 PID。
机器人处于小陀螺模式。
```

### 10.7 项目 thread 的自由度

产品 thread 可以：

```text
组合多个设备。
组合多个算法。
订阅多个 topic。
发布多个命令。
定义状态机。
定义控制周期。
定义安全策略。
```

### 10.8 项目 thread 的边界

产品 thread 不应该：

```text
复制公共驱动。
复制公共 Remote。
复制公共 IMU。
自己修改公共链接段。
在多个地方重新定义同一个 topic。
```

### 10.9 这一部分结论

`board` 和 `thread` 是用户工作区的核心，不是因为其他层不重要。

而是因为：

```text
board 表达产品硬件。
thread 表达产品行为。
```

## 十一、设备模块与数据契约

### 11.1 Remote

Remote 模块可以把协议差异收敛在：

```text
DR16。
SBUS。
VT12。
VT13。
```

协议插件负责：

```text
Validate。
Decode。
line_cfg。
注册。
```

Remote 核心负责：

```text
接收。
探测。
切换。
超时。
发布。
```

### 11.2 IMU

IMU 模块可以把：

```text
设备寄存器。
采样。
标定。
温控。
数据处理。
```

组织成稳定能力。

产品线程不必直接操作每个寄存器。

### 11.3 Motor

Motor 更接近被动设备。

典型路径：

```text
CAN IRQ
    -> 更新反馈
        -> 快照
            -> 产品 thread 读取
```

它不一定需要独立业务线程。

### 11.4 PowerMeter

PowerMeter 可以被底盘策略使用。

但功率控制属于：

```text
公共算法能力。
产品底盘策略。
```

具体归属要按复用程度判断。

### 11.5 topic 的状态语义

`remote_to` 可以表达：

```text
当前遥控器状态。
```

`imu_to` 可以表达：

```text
当前 IMU 状态。
```

`to_can_tx` 可以表达：

```text
待发送的 CAN 命令。
```

### 11.6 状态和事件分开

状态：

```text
可以被后来者读取。
只需要最新值。
```

事件：

```text
需要按顺序处理。
不能随意覆盖。
```

如果把事件当状态：

```text
可能丢失动作。
```

如果把状态当事件：

```text
队列可能堆积。
```

### 11.7 topic 的价值

topic 让产品线程不必直接依赖：

```text
设备内部对象布局。
UART 缓冲区。
CAN 回调细节。
IMU 寄存器状态。
```

### 11.8 数据所有权

每个 topic 都应该回答：

```text
谁写。
谁读。
谁负责时间戳。
谁负责失联。
谁负责默认值。
谁负责线程安全。
```

### 11.9 四套项目的数据差别

```text
zephyr_user
    topic / msgq / snapshot
```

```text
basic
    message_center / 实例 / 约定
```

```text
Dust
    对象成员 / 共享状态 / 临界区
```

```text
COD
    全局结构体 / extern / 中断直接更新
```

### 11.10 这一部分结论

`zephyr_user` 的数据设计艺术是：

```text
把设备内部状态变成公共契约。
把产品策略变成 topic 的消费者。
把 CAN 输出变成有边界的命令。
```

## 十二、cmd、USB 与运行期控制面

### 12.1 cmd 不是普通业务目录

cmd 负责：

```text
shell。
buzzer。
Flash。
构建辅助。
链接段。
```

它服务多个层。

它不属于某一个机器人。

### 12.2 shell

shell 的价值是：

```text
运行时读取变量。
运行时修改变量。
打印状态。
验证模块。
```

注册式 shell 变量可以减少：

```text
中央变量表。
大量 if。
重复命令解析。
```

### 12.3 buzzer

buzzer 可以统一表达：

```text
启动成功。
阶段完成。
初始化错误。
系统停机。
```

产品线程不必自己实现蜂鸣器节奏。

### 12.4 Flash

Flash 可以承载：

```text
校准参数。
产品参数。
持久化配置。
```

产品只需要调用能力接口。

### 12.5 USB 为什么特殊

USB 不只是：

```text
读几个字节。
写几个字节。
```

它还包括：

```text
枚举。
描述符。
EP0。
CDC ACM。
端点。
reset。
DMA。
缓存。
IRQ。
```

因此 USB 需要：

```text
外部协议栈。
硬件 HAL。
项目 Stream 适配。
```

### 12.6 USB 的正确边界

协议栈负责：

```text
USB 状态机。
标准请求。
CDC 请求。
端点生命周期。
```

HAL 负责：

```text
控制器。
PHY。
IRQ。
DMA。
```

项目 Stream 适配负责：

```text
把 USB 变成上层可读写的数据流。
```

### 12.7 cmd 与 USB 的共同点

它们都不是普通的单一业务模块。

它们都是：

```text
对多个层提供稳定入口的基础设施。
```

### 12.8 这一部分结论

特殊边界不是架构混乱。

只要它满足：

```text
有明确所有者。
有稳定接口。
有配置门禁。
不反向依赖产品策略。
```

## 十三、basic_framework

### 13.1 定位

`basic_framework-master` 是成熟的队伍级 STM32 框架。

它的组织中心是：

```text
bsp。
modules。
application。
message_center。
```

### 13.2 它的优势

```text
分层规则成熟。
文档完整。
pub-sub 有经验。
实例化模式成熟。
DWT 调试能力强。
任务超时检查意识强。
团队协作规范完整。
```

### 13.3 它的初始化

它更倾向于：

```text
RobotInit。
集中初始化。
集中创建任务。
```

这种方式的优点是：

```text
新人容易找到入口。
固定工程容易调试。
任务清单集中。
```

### 13.4 它的数据契约

message center 让：

```text
cmd。
chassis。
gimbal。
shoot。
```

之间减少直接包含。

### 13.5 它的不足

```text
公共边界更多依赖规则。
配置裁剪依赖宏和工程维护。
pub-sub 同步保护不够强。
部分解析在 ISR 内完成。
跨 MCU 和 RTOS 迁移成本较高。
```

### 13.6 与 zephyr_user 的关系

basic 可以给 `zephyr_user` 的启发是：

```text
文档传承。
故障复盘。
实时性自检。
提交纪律。
```

`zephyr_user` 比 basic 多出的机制是：

```text
Kconfig。
DeviceTree。
linker 注册。
submodule。
父子用户工作区。
```

## 十四、COD_H7

### 14.1 定位

COD 是：

```text
STM32H723。
HAL。
FreeRTOS。
CubeMX。
CLion。
CMake。
Ninja。
```

组成的单板模板。

### 14.2 它的优势

```text
H7 外设覆盖完整。
FDCAN 联调方便。
UART DMA 经验丰富。
CLion 工具链现代。
compile_commands 可用。
DWT 测时方便。
算法组件数量较多。
```

### 14.3 它的运行模型

典型路径：

```text
main。
HAL 初始化。
MCU_Init。
MX_FREERTOS_Init。
固定任务。
osKernelStart。
```

### 14.4 它的数据风险

典型路径：

```text
ISR 写全局结构体。
任务直接读取全局结构体。
```

如果没有：

```text
临界区。
原子协议。
队列。
快照。
```

就存在数据撕裂和竞态。

### 14.5 它的长期问题

```text
任务新增要改中央文件。
设备新增要改中央回调。
配置开关不一定真实生效。
项目差异常通过复制工程解决。
```

### 14.6 与 zephyr_user 的关系

COD 可以贡献：

```text
H7 现场调试经验。
DMA 双缓冲。
缓存处理。
CLion 工具链。
```

但其公共平台治理能力还需要补：

```text
topic。
Kconfig。
注册器。
父子工作区。
```

## 十五、Dust

### 15.1 定位

Dust 是具体哨兵下板工程。

它的组织中心是：

```text
Robot。
Chassis。
Gimbal。
Reload。
Imu。
Communication。
```

### 15.2 它的优势

```text
C++ 类封装直观。
整机策略集中。
设备拓扑明确。
模块对象拥有状态。
比赛业务闭环较完整。
```

### 15.3 它的任务模型

模块常见方式：

```text
对象 Init。
对象创建线程。
对象 Task。
对象维护状态。
```

优点是对象完整。

代价是任务创建点分散。

### 15.4 它的通信模型

典型路径：

```text
CAN 回调。
按照 ID 分发。
调用具体电机对象。
Robot 或模块读取状态。
```

### 15.5 它的长期问题

```text
设备对象和全局 CAN 管理器耦合。
任务普遍使用软轮询。
跨模块数据契约没有独立层。
部分工程文件较大。
部分功能仍是半成品。
```

### 15.6 与 zephyr_user 的关系

Dust 可以给 `zephyr_user` 的启发是：

```text
整机策略必须有明确落点。
控制热路径必须可读。
设备拓扑必须能被新人看懂。
```

`zephyr_user` 不应该把所有策略都抽成碎片。

产品层仍然需要：

```text
清楚的协调线程。
清楚的状态机。
清楚的控制链。
```

## 十八、复用、迁移与维护成本

### 18.1 新增一个板卡

在 `zephyr_user` 中优先修改：

```text
boards/
overlay。
conf。
board.cmake。
DeviceTree binding。
```

不应该复制：

```text
drivers。
modules。
algorithm。
init。
```

### 18.2 新增一个设备

推荐路径：

```text
底层访问 -> drivers。
设备协议 -> modules。
公共状态 -> topic。
产品使用 -> thread。
```

### 18.3 新增一个 Remote 协议

推荐路径：

```text
新增协议文件。
实现 Validate。
实现 Decode。
填写 line 配置。
REGISTER_REMOTE。
打开 Kconfig。
```

Remote 核心不应该因为新增协议而不断扩大。

### 18.4 新增一个 IMU

推荐路径：

```text
新增 IMU 设备实现。
绑定设备树。
REGISTER_IMU。
保持统一校准入口。
保持统一状态输出。
```

### 18.5 新增一个产品线程

推荐路径：

```text
用户工作区新增 thread 文件。
用户 Kconfig 增加开关。
用户 CMake 加入源文件。
线程注册 init。
线程注册 start。
连接 topic。
```

### 18.6 从 COD 迁移

COD 的：

```text
算法。
DMA。
H7 板级经验。
```

可以迁移到：

```text
algorithm。
drivers。
boards。
```

固定任务要重新划分成：

```text
公共模块线程。
产品 thread。
topic。
```

### 18.7 从 Dust 迁移

Dust 的：

```text
Robot 策略。
底盘控制。
云台控制。
拨弹逻辑。
```

主要进入：

```text
用户 project/thread。
```

Dust 的公共设备能力再判断是否提升到：

```text
modules。
drivers。
algorithm。
```

### 18.8 从 basic 迁移

basic 的：

```text
message center。
实例模型。
任务诊断。
文档流程。
```

可以分别映射为：

```text
topic。
modules。
cmd 或诊断工具。
架构文档和团队流程。
```

### 18.9 迁移不是复制

错误迁移方式：

```text
复制整个工程。
复制全部 BSP。
复制全部设备。
复制全部任务。
改名。
```

正确迁移方式：

```text
识别公共能力。
识别产品策略。
公共能力进入父级。
产品策略留在子级。
使用 Kconfig 选择。
使用 board 描述差异。
使用 thread 装配行为。
```

### 18.10 维护成本的变化

传统工程初期成本低：

```text
打开工程。
复制文件。
改全局变量。
加一个任务。
```

长期成本高：

```text
复制分叉。
版本漂移。
中央文件冲突。
隐藏依赖。
全局状态。
```

`zephyr_user` 初期成本高：

```text
理解 CMake。
理解 Kconfig。
理解 DTS。
理解 linker。
理解 submodule。
```

长期成本更可控：

```text
公共代码集中。
产品工作区轻量。
版本可固定。
依赖可追踪。
```

## 十九、业务闭环能力对比

### 19.1 统一闭环

所有电控系统都可以抽象成：

```text
输入
    -> 状态
        -> 目标
            -> 控制
                -> 输出
                    -> 反馈
```

### 19.2 COD

```text
遥控器。
    -> remote_ctrl。
        -> Control_Task。
            -> PID。
                -> Control_Info。
                    -> CAN_Task。
```

### 19.3 Dust

```text
遥控器。
视觉。
裁判系统。
    -> Robot。
        -> Chassis。
        -> Gimbal。
        -> Reload。
            -> CAN。
                -> 电机。
```

### 19.4 basic

```text
robot_cmd。
    -> message_center。
        -> chassis。
        -> gimbal。
        -> shoot。
            -> motor。
                -> feedback。
```

### 19.5 zephyr_user

```text
Remote。
    -> remote_to。
        -> chassis / gimbal。
            -> algorithm。
                -> to_can_tx。
                    -> CAN TX thread。
                        -> drivers。
```

IMU 链路：

```text
IMU device。
    -> ImuManager。
        -> Processor。
            -> imu_to。
                -> product thread。
```

### 19.6 平台能力和业务能力分开

`zephyr_user` 当前最强的是：

```text
平台边界。
公共模块。
配置装配。
生命周期。
数据契约。
```

Dust 当前最强的是：

```text
整机策略。
设备拓扑。
比赛业务。
```

两者评价必须分开。

### 19.7 产品层仍然重要

平台不能替代产品线程。

产品线程仍然必须决定：

```text
怎么开环。
怎么闭环。
怎么切模式。
怎么保护。
怎么降级。
怎么协调多个模块。
```

### 19.8 这一部分结论

最好的目标不是：

```text
所有东西都抽象到 framework。
```

而是：

```text
公共能力进入 framework。
产品策略留在 project/thread。
```

```text
在用户 thread 里复制驱动。
在产品代码里重定义公共 topic。
为了一个参数修改公共接口。
```

### 22.6 推荐的做法

```text
尽量使用公共接口。
把产品差异留在产品层。
把公共 bug 提交到父级。
把实验补丁标记清楚。
把真实运行结果写回文档。
```

## 二十三、维护者发布公共能力的工作流

### 23.1 需求进入

```text
收集多个用户需求。
确认是否存在共性。
确认是否值得进入 framework。
确认 API 是否稳定。
```

### 23.2 选择层

```text
硬件访问 -> drivers。
设备协议 -> modules。
纯计算 -> algorithm。
数据契约 -> topic。
生命周期 -> init。
运行期工具 -> cmd。
产品策略 -> project。
```

### 23.3 实现

```text
在对应 submodule 实现。
保持依赖方向。
保持公共接口。
增加配置门禁。
增加注册项。
更新架构文档。
```

### 23.4 验证

```text
检查配置关闭路径。
检查配置打开路径。
检查链接 section。
检查初始化日志。
检查线程启动。
检查数据契约。
检查至少一块板卡。
```

### 23.5 发布

```text
公共 submodule 提交。
根仓库更新 gitlink。
记录版本说明。
说明兼容性。
说明迁移方式。
通知用户更新。
```

### 23.6 版本升级

用户升级的是：

```text
父级组合版本。
```

用户不应该自行拼装：

```text
drivers 任意分支。
modules 任意分支。
topic 任意分支。
init 任意分支。
```

除非这是明确的开发任务。

### 23.7 公共 API 评审问题

```text
是否绑定了某一台 Robot？
是否需要被多个项目使用？
是否可以在没有产品策略的情况下测试？
是否引入了反向依赖？
是否有配置关闭路径？
是否有错误处理？
是否有线程安全说明？
是否有版本兼容说明？
```

### 23.8 维护者最重要的判断

维护者不只是写代码的人。

维护者要判断：

```text
什么值得公共化。
什么必须留在产品层。
什么应该成为稳定契约。
什么只是一次性实验。
```

## 二十四、最终结论

### 24.1 四套架构各自最强

`basic_framework-master` 最强的是：

```text
团队规则。
文档传承。
消息组织。
调试纪律。
```

`COD_H7` 最强的是：

```text
H7 单板。
DMA。
CLion。
CMake。
快速联调。
```

`Dust` 最强的是：

```text
Robot 对象。
设备拓扑。
整机策略。
比赛闭环。
```

`zephyr_user` 最强的是：

```text
公共子树。
维护者父级工作区。
用户同级子级工作区。
Kconfig。
CMake。
DeviceTree。
linker 注册。
阶段化启动。
topic 契约。
submodule 版本边界。
```

### 24.2 `zephyr_user` 的核心创新

它不是只把代码分成更多目录。

它把：

```text
公共能力。
产品差异。
构建装配。
启动生命周期。
硬件连接。
数据契约。
版本治理。
人员责任。
```

放进了同一套结构中。

### 24.3 为什么要付出这么大代价重构

因为旧式单工程的典型问题是：

```text
所有人都能改所有东西。
所有产品都复制所有代码。
公共修复无法统一下发。
板卡和业务混在一起。
初始化和线程依赖藏在中央文件。
```

子树架构希望改成：

```text
维护者维护公共父级。
成员维护自己的产品子级。
用户通过 CMake 消费父级。
公共模块通过 submodule 固定版本。
产品通过 board 和 thread 表达差异。
```

### 24.4 最准确的评价

```text
basic 是工程纪律的胜利。
COD 是单板工具链的胜利。
Dust 是整机对象组织的胜利。
zephyr_user 是平台边界和团队上下级关系的胜利。
```

### 24.5 最终排名

#### 平台化能力

```text
zephyr_user
    >
basic_framework-master
    >
Dust_SentinelRobot_L_Game
    >
COD_H7_Template_CLion-main
```

#### 单车整机能力

```text
Dust_SentinelRobot_L_Game
    >
basic_framework-master
    >
zephyr_user
    >
COD_H7_Template_CLion-main
```

#### 团队长期维护能力

```text
zephyr_user
    >
basic_framework-master
    >
Dust_SentinelRobot_L_Game
    >
COD_H7_Template_CLion-main
```

### 24.6 最后一段

如果只看“现在能不能跑”，Dust 和 basic 会非常有竞争力。

如果只看“从一块 H7 板快速开始”，COD 很直接。

如果看“下一块板、下一辆车、下一个成员加入后系统会不会失控”，就必须看：

```text
公共代码在哪里。
产品代码在哪里。
谁负责维护公共层。
用户如何引入公共层。
公共版本如何固定。
板卡和线程是否被留在产品工作区。
```

这正是 `zephyr_user` 子树设计的核心。

它真正建立的不是一棵目录树。

它建立的是：

```text
维护者父级。
用户子级。
公共能力。
产品语义。
编译装配。
运行生命周期。
数据契约。
版本治理。
```

最终目标可以压缩成一句话：

```text
让普通用户自由做产品，让维护者集中维护平台，让公共能力不再被每个项目重复复制。
```
