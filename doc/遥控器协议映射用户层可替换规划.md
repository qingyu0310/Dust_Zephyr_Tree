# 遥控器协议映射用户层可替换规划

> 2026-10-31 第五版。前四版越写越复杂，本版回到最简形态：**默认函数照常跑，弱函数只做后处理，框架最后统一校验输出**。

---

## 0. 形态

```text
Decode（协议解析）
    ↓  OutputData（协议原生，无损）
DefaultFillOutputData（框架默认映射，默认灵敏度，.cpp 内部函数）
    ↓  Message 已填好
FillOutputData（__weak 后处理，默认空实现，用户区按需覆盖）
    ↓
ValidateOutput（框架兜底校验，不暴露给用户区）
    ↓
zbus 发布
```

**默认函数永远执行，弱函数只追加。** 用户不写弱函数 = 空实现 = 行为与现在完全一致。

前几版的错误：

| 版本 | 错在哪 |
|---|---|
| 一 | 造 `RawInput` 中性层，有损，SBUS `sw3` 无处安放 |
| 二 | 弱函数要求整份替换默认映射，用户改一个键要复制全部 |
| 三 | 造 `variant` + `RemoteStrategy`，等于第二三份协议清单（`REGISTER_REMOTE` 已经有一份） |
| 四 | 弱函数仍是"替换"语义，用户还得自己调 `DefaultFillOutputData` |
| **五** | **弱函数是后处理，默认函数自动跑完再调它** |

### 1.5 用户区：带状态（长按、单击切换）

状态直接放弱函数里的 `static`，不建类、不建对象：

```cpp
namespace vt13 {

/**
 * @brief sentinel 的 VT13 后处理：右键单击切换瞄准
 * @param in   协议输出
 * @param out  已填好的业务消息
 */
void FillOutputData(const OutputData& in, topic::remote_to::Message& out)
{
    static bool aiming     = false;      // 瞄准开关
    static bool last_right = false;      // 右键边沿检测

    if (in.mouse.right && !last_right) {
        aiming = !aiming;
    }
    last_right = in.mouse.right;

    out.autoaim_ctrl = aiming ? topic::remote_to::StartMode::On : topic::remote_to::StartMode::Off;
}

} // namespace vt13
```

`static` 在协议实例同一生命周期内有效（`REGISTER_REMOTE` 生成的是全局唯一实例），单实例架构下这就是正确的状态容器。

### 1.6 输出校验：防用户区把数据写坏

用户区弱函数能任意改 `Message`，可能写出非法值（`NaN`、超范围、枚举越界）。框架在弱函数之后统一兜底，**校验函数不暴露**——用户区看不到、也调不到。

**放在 `protocol_base.hpp`，与 `normMouse` 等工具函数同处（全局作用域，框架内部使用）：**

```cpp
/**
 * @brief 输出消息兜底校验 — 弱函数跑完后由框架调用
 *
 * 连续量钳到边界，非法值（NaN）归零，枚举越界归到安全默认值。
 * 用户区不可见：不提供声明给用户覆盖，也不在协议头文件里出现。
 *
 * @param pub  待校验的业务消息
 */
inline void ValidateOutput(topic::remote_to::Message& pub)
{
    pub.chassisx = ClampAxis(pub.chassisx);
    pub.chassisy = ClampAxis(pub.chassisy);
    pub.yaw      = ClampAxis(pub.yaw);
    pub.pitch    = ClampAxis(pub.pitch);

    if (pub.chassis_mode > topic::remote_to::ChassisMode::Spin)   pub.chassis_mode = topic::remote_to::ChassisMode::Normal;
    if (pub.shoot_ctrl   > topic::remote_to::StartMode::On)       pub.shoot_ctrl   = topic::remote_to::StartMode::Off;
    if (pub.reload_ctrl  > topic::remote_to::StartMode::On)       pub.reload_ctrl  = topic::remote_to::StartMode::Off;
    if (pub.autoaim_ctrl > topic::remote_to::StartMode::On)       pub.autoaim_ctrl = topic::remote_to::StartMode::Off;
    if (pub.supercap_ctrl > topic::remote_to::StartMode::On)      pub.supercap_ctrl = topic::remote_to::StartMode::Off;
}
```

配套的钳位函数（同样放 `protocol_base.hpp`，不暴露）：

```cpp
/**
 * @brief 连续量钳位 — 越界钳到 ±1，NaN 归零
 * @param v  输入值
 * @return float  钳位结果
 */
inline float ClampAxis(float v)
{
    if (!(v == v)) return 0.0f;      // NaN
    if (v >  1.0f) return  1.0f;
    if (v < -1.0f) return -1.0f;
    return v;
}
```

**四个设计点：**

1. **钳位而不是清零** —— 用户区乘系数放大后超出 `[-1,1]` 是**正常用法**（灵敏度加倍），框架钳到 `±1` 即可。清零会让"打满方向"变成"不动"。
2. **NaN 单独处理** —— `!(v == v)` 是判 `NaN` 的标准写法（`NaN` 与任何数比较都为假）。`NaN` 没法钳，只能归零。
3. **枚举比较用 `>` 而不是 `==` 白名单** —— `ChassisMode` 只有 `Normal=0/Spin=1`，`StartMode` 只有 `Off=0/On=1`，`> 最大值` 即可拦住强转出来的非法值。枚举一旦扩展，这行跟着改。
4. **不丢弃整帧** —— 用户区写坏一个字段，其余字段仍有效；丢弃整帧会让订阅方误判失联。

**校验位置**：`Decode` 内、`FillOutputData` 之后、返回 `true` 之前。`DefaultFillOutputData` 的输出本身就合法，校验主要针对用户覆盖。

> **不暴露的实现方式**：`ValidateOutput` 定义在 `protocol_base.hpp` 但**四个协议头文件（`dr16.hpp` / `sbus.hpp` / `vt12.hpp` / `vt13.hpp`）不 include 它**——用户区只 include 协议头文件，看不到这个函数。

## 3. 状态所有权

| 状态 | 归属 |
|---|---|
| `version` | **框架**，`HandleLocked` 统一自增 |
| `last_valid_ms` / 失联判定 / 失联清零 / 切协议复位 | **框架** |
| 本帧消息起点 | **框架**，局部 `Message frame_msg {}`，解码成功才赋值给 `pub_` |
| 键盘 toggle | 协议（现有 `keyboard_state_`，不动） |
| 长按计时、瞄准开关、灵敏度、键位 | **弱函数内的 `static`**（用户区自己写） |

`HandleLocked` 改法（`remote.cpp:192-220`）：

```cpp
    while (frame_.frame_pos_ >= entry->frame_size)
    {
        topic::remote_to::Message frame_msg {};        // 本帧从空消息完整构造

        if (entry->protocol->Decode(frame_.frame_buf_, entry->frame_size, frame_msg))
        {
            frame_msg.version = pub_.version + 1;      // 框架统一自增
            pub_ = frame_msg;

            if (detect_.lost_) {
                DUST_LOG_INF("reconnect %s", entry->name);
                detect_.lost_ = false;
            }
            detect_.last_valid_ms = k_uptime_get_32();
            detect_.fail_count = 0;
            Consume(entry->frame_size);
        }
        else
        {
            detect_.fail_count++;
            Consume(entry->frame_size);
        }

        if (detect_.fail_count >= kUnlockFailLimit) {
            ResetDetect();
            break;
        }
    }
```

**为什么用局部 `frame_msg` 而不是 `pub_ = {}` 再解**：`Task()` 在 `ProcessChunk` 后无条件发布 `pub_`（`remote.cpp:40`）。先清 `pub_` 再解码失败，订阅方会收到一帧全零。

`Decode` 签名不变（仍是 `(buf, len, pub)`），四个协议无需配合改动。

## 4. 独立缺陷：`last_valid_ms` 截断

`remote.hpp:110` `uint16_t last_valid_ms`，`remote.cpp:207` 写 `k_uptime_get_32()`。

设帧到达时刻 `T`，存 `T mod 65536`。之后 `now = T + δ`：

```text
now - stored = floor(T / 65536) * 65536 + δ
```

- `T < 65536`（上电 65.5 s 内）→ 差值 = δ，正确
- `T ≥ 65536` → 差值恒 ≥ 65536，**恒 > kRemoteTimeoutMs(100)**

即**上电 65.5 s 之后，每一次无数据轮询都必然判失联**，与上一帧多近无关。100 ms 超时退化成"一个 poll 周期（50 ms）"。

连带两处：

- `last_valid_ms == 0` 当哨兵（`remote.cpp:68`），但 `0` 也是 `65536` 的倍数 → 正常帧落在这些时刻被误判成哨兵，下一帧打假 `reconnect`（`remote.cpp:204-206`）
- `OnRetry` 的 `pub_ = {}` 与 `zbus_chan_pub` 无条件执行（`remote.cpp:73-74`），哨兵只挡日志没挡清零

**修法**：字段改 `uint32_t`，新增 `bool lost_` 替掉 `== 0` 哨兵。

## 10. 与既有规则的一致性
