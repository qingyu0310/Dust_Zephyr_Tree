# EtherCAT 协议栈解耦与类型化 PDO 重构规划

日期：2026-10-31。

状态：规划稿。本文只定义下一轮重构的职责、数据契约、迁移步骤和回归要求；本次不修改源码、不编译、不烧录。

## 1. 本轮目标与依据

本轮处理的是当前 C++ 栈内部的责任和状态耦合，重点是 `EcatDevice::Init()` 的相互绑定，以及业务 PDO 类型仍定义在协议核心的问题。已经完成的 SSC 移植、HAL 分离和 PHY 设备模块化是现状，不重新执行一遍。

完成标准不是少几个 Bind 或少几个文件，而是：

- 应用在 trd 声明自己的 RxPDO/TxPDO 类型、对象映射和板卡装配，不修改 core 才能换 PDO。
- AL 状态机只做转换决策，不同时持有邮箱、PDO、同步、字典和 SII 五个具体对象。
- 字典不再拥有其他域的可写运行状态，其他域也不通过 `dictionary.Data()` 跨域修改。
- 邮箱拥有收发帧，SDO/Info 处理载荷；应答不通过 Device 反向绕回邮箱。
- 初始化有明确提交点，回调、PHY、对象模型未准备好时不启用事件。
- 改一个事件入口时，不需要靠记忆猜另一个类中的掩码和确认副作用。
- 保留已经实际跑通的双向 PDO、状态机保护和主站恢复协作行为。

### 1.2 USB 参考：借鉴真实边界，不照搬协议形态

已阅读 `stream/usb/usb.hpp/.cpp`、`core/usb_dev_port.hpp/.cpp`、`core/usb_cdc_acm.hpp`。

USB 当前链路是顶层处理业务收发、DevPort 管理设备生命周期与事件、CDC 处理类协议、HAL 管硬件。上层接收有限的完成/配置事件，下层不反向查询整个上层对象。

EtherCAT 应学习这种责任边界，而非为每层增加一个转发类。USB 当前也存在默认 HAL 入口和回调，不能把它所有细节都认定为 EtherCAT 必须照抄的规则。EtherCAT 的 PDO 是周期过程镜像，不应强行继承 Stream，也不应按 USB 字节流队列处理。

## 2. 当前代码的具体耦合

### 2.1 Init 中的关系图

当前 `core/ecat_device.cpp::Init()` 包含：

```cpp
sync_.BindParameters(dictionary_.Data().sync_manager_out, dictionary_.Data().sync_manager_in);
state_machine_.Bind(mailbox_, process_data_, sync_, sii_service_);
state_machine_.BindDictionary(dictionary_);
dictionary_.BindStateQuery(QueryState, this);
dictionary_.BindTimestamp(QueryTimestamp, this);
sdo_.Bind(dictionary_, SubmitReply, this);
sdo_info_.Bind(dictionary_, SubmitReply, this);
coe_.Bind(sdo_, sdo_info_);
mailbox_.SetDispatcher(DispatchMailbox, this);
sii_service_.Bind(esc);
```

这不是单纯“传了几个引用”：

| 现状 | 隐含牵连 | 直接后果 |
|---|---|---|
| Sync 持有字典成员的可写引用 | 同步状态属于 Sync，但存储实际属于 Dictionary | 字典布局变化可能破坏同步数据；SDO 写入又需要回头通知 Sync |
| 状态机持有五个具体域 | 状态决策、布局生成、寄存器执行、资源清理混在一起 | 改降态或 Init 容易把协议校验和硬件清理顺序一起改坏 |
| 字典通过 Device 回查 AL/时间戳 | 读对象绕回组合根，再进入兄弟类 | 查询上下文不透明；此前时间戳前门漏接就读错对象 |
| SDO/Info 回调 Device::SubmitReply | 应答借 Device 回到 Mailbox | 传输失败和帧所有权跨越多层，易出现释放/重发遗漏 |
| Mailbox 回调 Device，再到 CoE/SDO | Mailbox 不只是收发，还决定何时执行业务协议 | 收包、协议执行、发包上下文与缓冲生命周期相互依赖 |
| 业务回调在 slave.Init 后设置 | Init 内部已经 StartEvents | 有事件可达而业务接口尚未安装的窗口 |

**不能用“把这些 Bind 移到构造函数”作为本轮完成结果。** 构造绑定可以保证生命周期，但上述跨域状态访问和反向应答链必须实际减少。

### 2.2 PDO 当前仍是应用专用的核心配置

`core/spec/ecat_pdo_layout.hpp` 定义 `counter[8]` 的 PdoOutputs/PdoInputs，随后影响：

- 应用类型及业务回调的长度判断；
- ObjectData 中 `0x6000/0x7010` 的数组；
- `0x1600/0x1A00` 映射、`0x1C12/0x1C13` 分配；
- 字典真实成员偏移表；
- 过程数据布局和缓冲；
- SDO/SDO Info 对外描述。

当前字典部分对象项仍能看到映射 Record 的子项数写为字面量 `8`。即使部分循环已经按每方向字数推导，也不能据此说更改布局只改一个 sizeof 就全部正确。

**结论：业务类型应离开 core；类型、线上映射和对象访问必须由一套明确描述关联起来。** 只给 EthercatSlave 加两个模板参数，而底下仍读全局 PdoOutputs，不算完成。

## 3. 目标边界与状态所有权

### 3.1 依赖方向

```text
trd：业务 PDO 类型、字段映射、ESC/PHY 实例与端口配置
  └─ EthercatSlave<RxPdo, TxPdo>：类型适配、业务回调、启动/停止入口
       └─ EcatDevice：非模板，设备生命周期与有限的协议编排
            ├─ EcatStateMachine：AL 决策、pending、超时、错误锁存
            ├─ EcatSync：同步配置、时基、DC/SM 监测
            ├─ EcatProcessData：经过校验的线上过程镜像及搬运
            ├─ EcatMailbox：帧池、队列、in-flight/repeat/store 所有权
            ├─ CoE/SDO/Info：请求解析、会话、响应构造
            └─ Dictionary：描述与访问引擎，不拥有兄弟域运行状态

core ── EcatEsc 契约 ── ESC HAL ── 厂商 API
trd  ── PHY 设备模块，经 ESC 的 MDIO 能力访问芯片
```

不增加 `EcatContext` 把所有对象再装一遍给各类随意索引；不增加一层全是转发的 Runtime/Manager/Controller；不通过 friend、全局默认实例或注册表绕过边界。

### 3.2 所有权表

| 内容 | 唯一持有者 | 其他域怎样使用 |
|---|---|---|
| AL 状态、错误码、pending、转换超时、输出/输入许可 | StateMachine | 读取不可变快照；输入事实、取得转换结果，不直接改字段 |
| 同步参数、看门狗监测状态、DC 时间 | Sync | 对象访问经窄的读写操作；写入时校验并更新对应标志 |
| 固定对象及 PDO 字段描述 | Profile/schema 配置 | 编译期或静态只读视图；Device/Dictionary/PDO 共用同一来源 |
| 业务类型、业务存储、业务处理函数 | trd/类型化门面 | 显式编码或经过验证的复制；不把自然内存指针冒充线上布局 |
| 过程镜像交换缓冲 | ProcessData | 只在定义的生产/消费上下文访问，快照复制边界明确 |
| 邮箱帧池及所有权 | Mailbox | 请求借用、响应完成提交；协议层不自行释放池槽 |
| SDO 分段和 Info 分片游标 | 对应服务 | 一次请求推进，停止/复位明确取消 |
| EEPROM 介质与物理读写 | ESC HAL | SII 服务只解释命令，不新增另一个 SII 硬件接口 |
| PHY 型号、端口号、MDIO 地址、通告能力 | trd 装配 | 门面接收显式端口配置，不自行根据数组下标猜板卡配置 |

这里允许必要、单向、生命周期明确的依赖；目标不是“所有类不准有任何引用”。

## 4. PDO 类型化方案：模板只放在边界

### 4.1 选定方向

采用 **`EthercatSlave<RxPdo, TxPdo>` 类型化门面 + 非模板协议内核 + 显式字段描述**。

- 两个结构由 trd 或项目自己的 PDO 头声明。
- 模板负责业务类型检查、存储及到内核字节视图的适配。
- AL、邮箱、SDO、Info、SII、通用字典解析不随业务类型一起模板化。
- descriptor/schema 明确记录映射内容；通用 C++ 不能仅凭 sizeof 反射出成员类型、对象索引、子索引和填充。
- 当前八个 UDINT 可以使用明确命名的计数器描述生成器，但它只是这种布局的辅助工具，不能变成所有业务只能放 UDINT 的要求。

下文 `PdoSchema`、描述生成辅助函数、转换结果等新增名称都是**拟议接口**，尚不存在，实施时先落声明与契约。不能拿这些示意名字当已有 API 直接调用。

### 4.2 trd 期望形态

下面是拟议用法，不是当前可直接编译代码。`test_pdo_schema` 表示项目内静态定义的完整字段描述。

```cpp
struct PdoOutputs
{
	uint32_t counter[8];
};

struct PdoInputs
{
	uint32_t counter[8];
};

static ecat::EthercatSlave<PdoOutputs, PdoInputs> slave_ { test_pdo_schema };
```

ESC、PHY 和端口配置仍在 trd 明确创建；业务收发接口改为 `const PdoOutputs&` / `PdoInputs&` 类型化回调。当前即时回调模式在迁移中保留，回调仅在调用期间借用数据，不允许把临时引用保存到别处。

回调的安装作为初始化前的不可变业务配置提交，或作为 Init 的参数整体传入；禁止启动事件后再分两次补上接收/发送回调。

### 4.3 一个字段必须描述哪些信息

| 信息 | 示例 | 用途 |
|---|---|---|
| 对象索引与子索引 | `0x7010:01` | 对象字典及 PDO 映射 |
| 数据类型及位宽 | UNSIGNED32、32 bit | SDO/Info 的声明和编码 |
| 在线上镜像中的位置 | RxPDO bit offset 0 | 过程数据编码，独立于 C++ padding |
| 在业务类型中的位置/访问器 | `offsetof(PdoOutputs, counter)` | 访问真正的业务成员 |
| 读写及映射权限 | 标准 CoE access 位 | 状态权限、Info、枚举 |
| 名称/名称规则 | 条目名称 | SDO Info，不依赖不受限的 C 字符串扫描 |

同一份字段描述生成映射表、分配引用、对象描述、线上长度及访问绑定，不能手写五套互不校验的数字。

### 4.4 RxPDO 和 TxPDO 完全独立

**禁止加入 `sizeof(RxPdo) == sizeof(TxPdo)`、字数必须相同、必须成对存在之类限制。** EtherCAT 两个方向独立分配，当前 32/32 只是业务实例。

通用内核按位宽和协议映射工作；不强加所有 PDO 必须 32 位对齐或长度为 4 的倍数。当前 Counter schema 可以声明它处理 UDINT，不能据此约束其他 schema。

无某方向数据时，使用明确的“无映射”配置表达，线上长度为 0；不能用 C++ 空结构的 sizeof=1 表示零字节 PDO。支持范围按阶段验证，不悄悄把零长度转换成一个字节。

### 4.5 不把内存布局当协议布局

`sizeof(T)` 只代表本机对象大小，不能单独决定线上长度。若字段描述证明当前类型布局与线上布局完全一致，可以使用 memcpy 快路径；其他布局采用显式编码，保存大小端及位字段规则。

独立校验每方向映射位长、字段可访问范围、目标缓冲容量及 SM 长度。支持不等长类型不等于支持任意运行期动态改映射；本轮保留当前固定只读映射能力，不顺手承诺动态重映射。

### 4.6 PDO 与 SDO 是否共用业务数据，必须显式定约

当前 ProcessData 的交换缓冲、业务回调局部值和 Dictionary 的计数器成员是不同存储。不能在本轮重构时悄悄把 SDO 读值改成“上一帧 PDO”。

迁移初期：描述和映射共用 schema，但保留当前数据可见性；在规划接口中明确哪类对象使用独立对象存储，哪类绑定过程镜像。若用户后续选择共用，需另列行为变更和读写快照规则。否则“消除重复字段”可能变成协议行为回归。

### 4.7 SII/ESI 与类型化配置的关系

模板不会自动改写 EEPROM，也不会自动生成正确的 ESI/SII。当前默认 SII 曾报告每方向 4 字节，而 CoE 实际映射为 32 字节；本轮必须同时保留并核对主站 CoE 识别路径。

项目 profile 应关联其身份、PDO schema 与匹配的 SII/ESI 版本。若 SII 镜像仍由单独工具生成，要明确生成输入及一致性检查，不能声称模板保证了 EEPROM 一致。不得用强写 32 字节或刷 EEPROM 掩盖 SDO 应答错误。

### 4.8 模板实例不能共享一套可变全局布局

当前 cpp 中的应用 `kSlots`、映射表和成员偏移依赖核心全局 ObjectData。类型化之后必须把这部分变成每个 profile 的只读描述视图，并为每个实例保留独立运行存储；不能在非模板 cpp 里继续引用“唯一一套业务类型”。

同一程序声明两种不同 PDO 类型时，不能互相覆盖映射、状态或回调。只读标准描述可以共享，业务存储、同步状态、邮箱会话和过程镜像不能共享。

本轮保留静态/值成员内存模型，不为 schema、回调或桥接引入动态分配、std::function 和运行期全局注册。trd 提交的描述和硬件引用必须覆盖从站运行生命周期，不能将 thread_init 局部数组或临时对象的指针保存到内核。

## 5. Init 解耦：逐条替换，不藏到构造函数

### 5.1 目标数据流

```text
AL 请求/监测事实 → StateMachine 决策 → Device 执行有限生命周期动作 → 完成/失败回报
邮箱请求 → Mailbox 借出帧 → CoE/SDO/Info 处理 → 返回结果 → Device 提交 Mailbox
对象读写 → Dictionary 描述与权限校验 → 对应对象所有者的窄访问接口
过程事件 → ProcessData 编解码 → 类型化业务回调
```

Device 保留必要的组合与执行顺序；减少的是子域反向取得兄弟对象和父对象的能力，不是将协议编排消灭。

### 5.2 当前每条绑定的去向

| 当前代码 | 目标处理 | 必须实际消除的耦合 |
|---|---|---|
| `sync.BindParameters(dictionary.Data()...)` | 同步参数由 Sync 持有；字典标准对象经受控读写接口访问 | Dictionary 不再拥有 Sync 的可写状态；无可写 Data 大入口 |
| `state_machine.Bind(mailbox,pdo,sync,sii)` | 状态机接收校验事实，返回明确转换步骤；Device 调对应域完成执行 | 状态机不持有这些具体类，不执行邮箱/SM 寄存器操作 |
| `state_machine.BindDictionary(dictionary)` | 布局生成与校验由 Device 在转换要求的时机执行，把结果/尺寸交给状态机 | 状态机不依赖字典解析实现 |
| `dictionary.BindStateQuery(QueryState,this)` | 每次访问传入本次请求的 AL 状态快照 | Dictionary 不反向查询 Device |
| `dictionary.BindTimestamp(QueryTimestamp,this)` | 标准时间对象访问器直达 Sync 的时间读写能力 | 不借 Device 回查；读写方向明确，不能只接读 |
| `sdo.Bind(dictionary,SubmitReply,this)` | 服务处理入口显式接收字典访问视图及响应缓冲，返回处理结果 | 删除经过 Device 的 ReplySink 环路；服务不释放 mailbox 帧 |
| `sdo_info.Bind(...)` | 同上，分片游标保留在 Info | 分片续发由发送完成/线程调度明确推进 |
| `coe.Bind(sdo,sdo_info)` | CoE 只做有限服务路由；可作为 Device 内部路由函数，若类无状态且仅转发则取消该类 | 不为减少代码行数另造 Registry |
| `mailbox.SetDispatcher(...)` | Mailbox 提供取请求/提交响应操作，Device 主动调用协议处理器 | 传输层不调用上层协议，控制流单向 |
| `sii.Bind(esc)` | 确认 SII 服务只有 ESC 能力依赖，生命周期固定；可构造期固定引用 | 这条是必要依赖，不以“Bind 必须清零”为目标瞎拆硬件 |

标准对象访问器可以使用明确的函数指针或窄接口，但仅暴露该对象需要的读写能力；不能传 `EcatDevice*` 后任意取全部域，也不能复制整个运行上下文给字典。

### 5.3 状态机如何保留协议顺序

状态机保留当前 AL 状态、错误锁存、pending 目标和超时。它根据请求和事实给出具体转换步骤，步骤是有限的 AL 生命周期语义，不做通用事件总线或动态命令队列。

例如 PREOP→SAFEOP：

1. 要求准备输入通道。
2. Device 由同一 schema 生成本次布局，校验 SM 与区域、同步配置。
3. 全部前置校验成功后，提交 SM 使能、初始输入和事件掩码。
4. 将结果回报状态机；状态机决定提交 SAFEOP 或保留原态并锁存错误。
5. Device 根据最终快照发布 AL Status/Code。

若中间步骤失败，由执行者回滚自己已提交的资源，并报告错误；不允许“软件状态 SAFEOP、输入已停、SM 又被禁用”的半状态。主站新请求取消旧 pending 的规则必须保留。

降 INIT 不经过与该转换无关的过程数据校验。同步健康、首帧、配置校验、资源执行是不同事实，不能合并成一个笼统的 ready 布尔值。

### 5.4 邮箱服务返回值和缓冲所有权

Mailbox 借出的请求帧在协议处理期间只允许一个修改者。可以继续原地构造响应，但必须由传输层所有权状态明确表达。

服务返回值区分：已构造响应、无需响应、SDO 中止、邮箱协议错误、需要后续片段。发送失败属于传输结果，不强转成 SDO abort code。

| 时刻 | 帧持有者 | 谁能释放 |
|---|---|---|
| 空闲池 | Mailbox | 无业务持有 |
| 请求借出 | Device 本次处理借用 | 借用结束由 Mailbox 收回或转响应 |
| 响应入队 | Mailbox 发送队列 | Mailbox |
| 已写 SM1 等主站读走 | in-flight | Mailbox，不能被 IsQueued=false 释放 |
| 主站读走后保留重发 | repeat | Mailbox |
| 重发顶出的待发帧 | store | Mailbox，处理别名后释放 |

重发请求按 toggle 变化处理，ACK 按实际硬件 PDI 字节写回；退出 PREOP、复位和 Init 失败清除会话及缓冲别名。

### 5.5 启动生命周期拆成 Prepare 和 Start

参考 USB 的 Init/Start 责任分离，拟议生命周期为：

1. trd 构造静态业务类型、schema、硬件实例和端口配置。
2. 门面准备类型适配与业务接口；内核建立模型和各域初始状态。
3. ESC Open，允许寄存器/MDIO 访问，但保持事件关闭。
4. 按当前硬件已验证顺序完成 SII、ESC 基础初始化和 PHY 配置；不能自行重排硬件内部已验证步骤。
5. 初始化实际 SM 数、容量、AL 状态和本次事件掩码；验证所有回调目标与数据生命周期。
6. 置好可接受事件的运行标志，再开启事件，提交启动成功。

当前代码 `StartEvents()` 在 `ready_=true` 之前；业务回调和门面 PHY 配置又在 core Init 返回后才完成。这里应通过明确的启动提交点消除窗口，而不是机械换两行顺序。

Init 失败谁回收、Start 失败谁关闭事件、PHY 失败是否终止、Reset 后何时可再次 Start，要形成状态表；反复 Init 不能残留旧上下文和旧 pending。

## 6. 事件上下文：已出过故障，单独迁移

### 6.1 当前可运行基线必须标红

**已验证回归：** 将 `OnPdi()` 从 `HandleAlEvents()` 改为只调 `HandlePdiEvents()`，但仍让 AL Control 事件触发 PDI，中断源未被对应 ISR 消费；主站大量 ALCTL 写入失败。恢复原入口后用户确认重新跑通。

因此本轮前几个阶段保留当前事件处理语义，不顺手“清理 ISR”。诊断计数以及当前 `OnPdi/Poll` 的处理路径必须进入迁移差异清单。

### 6.2 最终必须建立事件责任表

| 事件 | 拟议执行者 | 确认方式 | 掩码要求 |
|---|---|---|---|
| AL Control | 线程 | 读 `0x0120`，处理完整请求 | 如果 ISR 不处理，就不让它持续触发 PDI；仍由 Poll 读取事件 |
| SM Change | 线程 | 按状态校验并读相关 Activation | 保留无 pending、无错误、非 INIT 等门控；AL Control 已处理时去掉旧快照对应位 |
| EEPROM 命令 | 线程 | 完成命令并发布状态 | 与实际 emulated 模式和事件源相匹配 |
| SM2 输出 | 即时 PDO 路径 | 读取有效数据或按状态确认区域 | 在允许模式下启用；不能重复消费旧快照 |
| SM3 输入 | 按当前同步类型 | 实际发布/确认规则 | 与输入同步配置共同决定 |
| SYNC0/SYNC1 | 对应即时同步路径 | 正确状态寄存器确认 | 独立 IRQ 与 PDI 复用只能选明确的一套，避免双处理 |
| 1 ms 节拍 | 定时器轻量推进 | 不适用 | 不因为其他域也 Tick 再累加一次 |

完整迁移同时包含掩码、入口、硬件确认、线程唤醒、pending 及并发规则；不能只改一个调用函数。

PDO 事件必须有明确的消费所有者。线程轮询回退与 PDI 中断不能无保护地拿同一事件快照各调用一次业务；若支持纯轮询模式，应由配置明确选择执行者。

### 6.3 并发不是“Poll 外面包一个大锁”

不能关 ESC 全部中断后在锁内执行邮箱解析、格式化日志、Flash 落盘或长等待。业务回调可重入性、状态快照、SM 配置提交、队列操作分别定义短临界区。

共享双缓冲/版本号/原子量要匹配目标 CPU 和实际上下文，不能只加 volatile。事件通知也不能随意存一个过期 bitmask 重放，必须区分可合并通知和必须保序的请求值。

## 10. 分阶段迁移与每阶段落点

### P0：保存当前可运行基线和红线清单

记录当前从站/主站版本或工作区快照、业务 profile、镜像版本和日志。未提交修改也要保留；不得用 reset/restore/stash 清掉用户工作。

输出：当前 Init 依赖图、事件责任表、R01～R18 迁移台账。旧静态审查逐条标注“当前仍有/已修/未验证”，不继续沿用旧行号当事实。

### P1：先引入项目 PDO schema，保持当前调度

将业务类型移到项目，建立两方向独立描述；验证所有映射/分配、对象计数、真实成员访问由同一 profile 得出。先保持当前事件入口及状态机执行路径。

输出：trd 明确声明类型；core 不再引用项目 `counter[8]`；32/32 基线和不等长 profile 的表示方式完整。不能只把头文件搬到 project，再让 core 反向 include project。

### P2：落地类型化门面与启动提交点

添加薄模板门面，提前准备 typed 回调，保留非模板 Device；实现 Prepare/Start/失败清理，将 PHY 及端口配置从门面常量迁回 trd 参数。

输出：Init 不再开事件后补业务接口；对象生命周期明确；同一个门面类型可接不同 ESC/PHY 实例，不存在默认固定板卡。

### P3：拆字典存储所有权与标准对象访问

Sync 自持参数，Dictionary 接 AL 快照；时间戳接专用读写能力。替换真实字段访问时逐项核对 B/R 红线，防止再次出现 `0x1C00` 四项同偏移和权限漏移位。

输出：不再有 Sync→Dictionary.Data 可写引用；读写标准对象不借 Device 回查全局状态；CA 和单项读同源。

### P4：拆邮箱传输和协议响应控制流

Mailbox 借请求，服务返回响应结果，由同一调用层提交。先建立帧状态及失败行为，再删除 dispatcher/ReplySink 桥，不在移除旧桥之后补空返回值凑编译。

输出：一条明确的请求到响应路径；direct send、queued、repeat 都有持有者；无 Device::SubmitReply 反向环路。

### P5：拆 AL 决策和资源执行

逐转换对照 SSC 列出：前置事实、动作顺序、提交点、pending、回滚、最终状态和 Code。状态机从依赖具体对象转为根据事实返回有限步骤，Device 执行并回报。

输出：状态机不再 include 五个兄弟域头文件；INIT/SAFEOP/OP 恢复语义、首帧门控不变。不得同时改主站恢复行为。

### P6：最后单独迁移事件上下文

在 P1～P5 已分别验证的基础上，联合更改掩码、入口和确认。逐项验证 R07；为每种模式指定唯一 PDO 消费者。

输出：线程慢路径与即时路径责任明确；不存在“启用了中断但 ISR 不确认”的源，也没有长时间关 IRQ 执行邮箱或存储。

### P7：回归与清理

用户执行编译和上板，按下一节验证。全部通过后再清理迁移兼容代码和临时诊断。规划时没有发生的验证不填写为通过。

| 字典 | 身份、同步参数、时间戳、计数器单读/CA 起始 0/1、短写和权限 | 偏移、访问位、保留项及真实数据所有者错误 |
| SDO 报文 | expedited 16 B 总长、Normal/分段、Abort、Info 全部列表 | 漏四字节、总长/载荷混淆、Info 尾部截断 |
| 状态转换 | INIT→PREOP→SAFEOP→OP、错误确认、任意合法退 INIT、取消旧 pending | 拒绝恢复、旧首帧强开 OP、资源与 AL 状态不一致 |
| 中断/轮询 | AL Control 在相应上下文及时确认，SM_ACT 无遗漏，PDO 无双回调 | 中断风暴、线程饥饿、同快照重复处理 |
| watchdog | 故意暂停主站，确认 SAFEOP+0x001b；恢复后主站 ACK 并重新 OP | 从站偷偷忽略 watchdog 或收到一帧强制恢复 |
| 邮箱重发 | request toggle 两个方向、满队列、direct send 后 repeat | 释放正在发送帧、漏 ACK、丢响应 |
| 同步模式 | 先验证 SM；DC/SYNC0/SYNC1 及无输出模式按声明逐项验 | SM 测通冒充 DC 全通过 |
| 长时间运行 | 至少覆盖此前故障时间尺度，并主动触发一次断流恢复 | 只跑几秒进 OP 就宣布稳定 |
| 观测 | 故障发生时计数、完整 AL Status/Code、主站恢复日志可关联 | 只看 INF 是否显示来判断协议状态 |

编译、语法、静态审查、上板和长时间运行是不同证据，分别记录。本次没有执行这些验收。

## 12. 实施纪律与交付要求

1. 每阶段先读当前相关文件及完整 SSC 对应函数，列差异再修改；已有源码和用户确认的运行结果优先于旧文档状态。
2. 标准符号先查定义和 namespace；拟议接口明确新增，声明、实现、调用与构建链一次对应完整。
3. 源码编辑使用能报告匹配失败的编辑/补丁工具，不用字符串替换脚本批量写回。
4. 延续子树当前 C++、Tab、中文 Doxygen/行尾注释风格。命名空间之间不累计缩进，类/函数内部保留正常缩进；不因重构顺手改全树格式。
5. 不恢复 SSC 全局变量，不增加 god object、friend 树、通用注册中心；不把 Bind 藏进另一层就声称解耦。
6. 不擅自加入 Rx/Tx 等长、必须四字节对齐、只能同种数据类型等业务限制。
7. 每阶段提交具体变化、红线映射和验证状态；用户没有执行编译或上板时，只能写“待验证”。不一次混改类型、调度、协议和底层后再逐个猜故障。
8. 不提前删除当前可运行路径、错误观测和历史故障记录；替换完成后再清旧，保留变更可追溯性。

本轮最终交付应是一个可在 trd 声明具体 PDO 类型、配置板卡并安装业务处理器的从站实例；内部协议状态各有所有者，调用方向清楚，已排过的故障有明确的防回归契约。
