# 跑飞亡语诊断系统规划

> 日期：2026-08-04 · 平台：hpm5361icb (Zephyr v4.3.0) · 主题：CAN 错误风暴 → 日志停 → 系统失能（"跑飞"）→ 如何诊断定位
> 目标：建立一套「跑飞时能留证据、死后能定位死点」的诊断机制，同时治本消除风暴。规划只写有依据的，技术点未验证的一律标注【实施时验证】。

---

## 0. 背景

### 0.1 现象

实际运行：打印一段 CAN 错误日志后，日志停止、遥控/底盘无响应、系统失能。挂上调试器运行则长期正常。

```
[00:00:04.568,000] <err> can: can can@f0280000 state=1 tx_err=128 rx_err=0
[00:00:04.569,000] <err> can: can can@f0280000 state=1 tx_err=128 rx_err=0
...反复...
（此后日志停止，系统失能）
```

### 0.2 已确认的根因链（有证据）

```
CAN 总线无对端 ACK（电调未接/未上电/无 120Ω 终端/波特率不匹配）
  → 每发一帧 TX 错误 +8，tx_err 累积到 128 → ERROR_PASSIVE
  → M_CAN 错误中断反复触发
  → can.cpp:110 state_callback 在【中断里】LOG_ERR
  → LOG_MODE_IMMEDIATE 同步输出 + console 走 poll_out 逐字节忙等
  → CPU 大量时间泡在中断里忙等 → 调度饿死 → "控制不了"
```

证据位置：
- 错误打印：[can.cpp:107-111](framework/drivers/communication/can/can.cpp#L107-L111)（`state_callback` 注册于 [can.cpp:46](framework/drivers/communication/can/can.cpp#L46)）
- 立即日志：[prj.conf:19](project/prj.conf#L19) `CONFIG_LOG_MODE_IMMEDIATE=y`
- console UART：[hpm5361icb.overlay:107-114](project/boards/hpm/hpm5361icb/hpm5361icb.overlay#L107-L114)（uart3，921600，DMA），LOG 后端走 `uart_hpm_poll_out` → `uart_send_byte` 逐字节忙等
- CAN 1Mbps：[hpm5361icb.overlay:73-78](project/boards/hpm/hpm5361icb/hpm5361icb.overlay#L73-L78)

### 0.3 为什么进调试正常（诚实结论）

调试器的 halt/单步**打断了错误中断的持续累积**，风暴起不来；运行节奏也变了（调试时底盘往往没在持续发 CAN）。**CAN 无应答这个根因在调试时照样存在**——调试正常只是掩盖，不是修复。

### 0.4 本规划范围

聚焦「跑飞亡语」诊断体系。**不含**「启动即崩的 .shell_var 链接段问题」（那是另一个问题，根因已定位为 inline 变量动态初始化写入只读 flash 段，另行处理）。

## 1. 待解的核心问题

### 1.1 "日志停了"到底是哪种

| 机制 | 描述 | 判据 |
|------|------|------|
| A. 日志通道死 | 风暴中 UART 发送/DMA 状态卡死，CPU 可能还活着，但打不出字 | 独立心跳仍在、主日志停 |
| B. CPU 死 | 跳到非法处 / ISR 锁死 / 死循环，不再执行日志路径 | 心跳也停 |

当前无法区分 A/B——因为没有独立的观察通道。**亡语体系的第一块砖就是造一个不依赖日志系统的独立心跳通道。**

### 1.2 诊断手段的层级

```
系统失能
 ├─ ① 心跳通道        → 区分「CPU 死」vs「日志通道死」
 ├─ ② 环形日志缓冲    → 死后从 RAM dump 死前最后 N 条
 ├─ ③ 异常钩子        → 异常型跑飞时 dump 现场（线程/栈/寄存器）
 ├─ ④ WDOG + 复位原因 → 自动复位 + 重启自报死因
 └─ ⑤ 调试器抓现场    → 最终定位 PC 落点
治本
 └─ ⑥ CAN 错误日志移出 ISR + 修总线无 ACK
```

## 2. 阶段一：独立心跳通道（诊断地基）

### 2.1 目的

在不依赖日志系统、不依赖底盘线程的前提下，给外部一个"系统还活着"的可靠信号。有了它，跑飞后第一件事就是看心跳——三秒定位 A/B。

### 2.2 硬件/资源

- 用 **uart1**：overlay 已配好（[hpm5361icb.overlay:87-94](project/boards/hpm/hpm5361icb/hpm5361icb.overlay#L87-L94)，100000 bps，DMA），**当前代码未使用**（已确认无 `DT_ALIAS`/`DEVICE_DT_GET` 引用）→ 专用诊断通道。
- 加 alias：`heartbeat-uart = &uart1;`（[hpm5361icb.overlay:6-16](project/boards/hpm/hpm5361icb/hpm5361icb.overlay#L6-L16)）

### 2.3 实现

新增 `project/thread/diag/trd_diag.cpp`，用现有 `Thread<>` 模板 + `REGISTER_THREAD`（参照 [trd_can_tx.cpp](project/thread/can/trd_can_tx.cpp) 结构）：

```cpp
namespace thread::diag {

static Thread<1024> heartbeat_thread_ {};

// 心跳：200ms 一次，uart1 逐字节忙等发 "H" + 序号
static void Task(void*, void*, void*)
{
    // 用 uart_hpm poll_out（直接寄存器忙等，不依赖日志/DMA 后端）
    for (uint8_t seq = 0;; ++seq) {
        // uart_poll_out(heartbeat_dev, 'H');
        // uart_poll_out(heartbeat_dev, '0' + (seq % 10));
        k_msleep(200);
    }
}

bool thread_init()
{
    // DEVICE_DT_GET(DT_ALIAS(heartbeat_uart)) + device_is_ready 检查
    return true;
}

bool thread_start() { heartbeat_thread_.Start(Task, ThreadPrio::Lowest); return true; }

REGISTER_INIT  (thread_init,  PreInit,  High, "diag_init");
REGISTER_THREAD(thread_start, LateThread, Lowest, "diag_start");

} // namespace thread::diag
```

要点：
- 优先级 **Lowest**：正常时占不到 CPU；一旦它都不跑 = 系统真失能。
- 独立于日志系统：即使 uart3/日志全卡死，心跳照常。
- 需要把 trd_diag.cpp 加进 project 的 CMakeLists（跟随 chassis/can 线程的添加方式）。

### 2.4 验证

1. 正常跑：串口工具接 uart1（USB-TTL @100000），应看到稳定的 `H0 H1 H2...` 周期性输出。
2. **拔掉电调/去掉终端电阻复现风暴**：
   - 心跳停 → 机制 B（CPU 死/ISR 风暴占死）
   - 心跳在、主日志停 → 机制 A（日志通道死）→ 直接指向"中断里立即日志 + DMA UART"这条链
3. 再挂调试器对比：两种心跳状态对应调试器看到的现场。

### 2.5 验收

- 正常/风暴两种工况下，心跳行为稳定可复现，能明确区分 A/B。
- 心跳线程本身栈无压力（栈使用 < 50%，用 Thread Analyzer 或阶段三钩子确认）。

## 3. 阶段二：环形日志缓冲 + 死后 dump

### 3.1 目的

让日志**先落 RAM 环形缓冲再后台刷**。这样即使主日志通道卡死，死前最后一段日志还在内存里，断电前用调试器能救回来——这是最接近"遗言"的手段。

### 3.2 改动

```kconfig
# prj.conf：把立即模式换成 deferred（log_msg 入内部缓冲 + 后台线程刷）
CONFIG_LOG_MODE_IMMEDIATE=n
CONFIG_LOG_MODE_DEFERRED=y
CONFIG_LOG_BUFFER_SIZE=8192   # 日志内部缓冲（MPSC），存未处理的 log_msg；默认 1024，按 RAM 余量调
CONFIG_LOG_PROCESS_THREAD=y   # 后台刷日志的线程（默认开）
CONFIG_LOG_PROCESS_THREAD_CUSTOM_PRIORITY=y   # 允许自定义优先级
CONFIG_LOG_PROCESS_THREAD_PRIORITY=3
```

注意（v4.3 源码确认，见 `subsys/logging/log_core.c` / `Kconfig.processing`）：
- deferred 机制：`LOG_ERR()` 在调用处**只做**——从 `CONFIG_LOG_BUFFER_SIZE` 的 MPSC 内部缓冲分配 log_msg 块、拷参数、入队，**立即返回**。`LOG_PROCESS_THREAD` 后台线程（可配优先级/栈，唤醒周期 `LOG_PROCESS_THREAD_SLEEP_MS`）再取出消息、格式化、送 UART backend。
- **ISR 里打日志不再忙等**（只做入队，几十条指令）——这一步本身就能缓解风暴对 CPU 的占用（与阶段五配合）。
- **缓冲满**：新日志丢弃并计数 `z_log_dropped`（死后 dump 能看到丢弃数）。
- **后端仍是逐字节 poll_out、无 DMA**：deferred 只是把"忙等"从 ISR 挪到后台线程，不是消除忙等（详见下方「3.5 无 DMA 说明」）。
- 代价：日志有后台处理延迟；RAM 多占 `LOG_BUFFER_SIZE`。

### 3.3 死后 dump 流程

1. 跑飞后**不要断电**。
2. 调试器（J-Link/OpenOCD）halt CPU。
3. 找到日志内部缓冲：就是 `CONFIG_LOG_BUFFER_SIZE` 那块 MPSC 缓冲（log_core 的 `curr_log_buffer` / `buf32[]`，符号表里可查 `log_core.c` 相关全局），或直接 `memory window` 搜日志特征串（如 `state=` 前文）。
4. 导出 RAM → 恢复死前最后 N 条。

> 精确缓冲结构体名/地址【实施时验证】：可在阶段三异常钩子里顺手 dump，或读 `subsys/logging/log_core.c` / `log_msg.c` 确认。

### 3.4 验收

- 正常跑：日志照常输出（延迟可接受），RAM 占用在预算内。
- 人为制造一个可复现死机（如临时在循环里 `LOG_ERR` 刷爆），死后能从 RAM dump 出最后几十条，且**能看到死亡点前一条日志**。

### 3.5 无 DMA 说明（机制事实）

Zephyr 的 UART log 后端（`subsys/logging/backends/log_backend_uart.c`）输出方式是 **`uart_poll_out` 逐字节**，没有 DMA、没有 fifo_fill（源码 `log_backend_uart.c:73,78,104` 全是 `uart_poll_out`）。本平台 HPM 驱动的 `uart_poll_out` = `uart_send_byte` = **忙等 TX 空再发一字节**（921600 下每字节约 10μs，一条几十字节日志 ≈ 几百 μs 阻塞）。

设备树 uart3 虽配了 `dmas`（[hpm5361icb.overlay:107-114](project/boards/hpm/hpm5361icb/hpm5361icb.overlay#L107-L114)），但 log 后端**不走 DMA 路径**——DMA 只服务 `CONFIG_UART_ASYNC_API` 的异步收发。日志输出永远是 poll 忙等。这正是「ISR 里打一条 LOG_ERR = ISR 里阻塞几百 μs」的直接证据，也是风暴拖死系统的机制。

## 4. 阶段三：异常钩子增强

### 4.1 目的

覆盖"异常型跑飞"（CPU 触发 fault）：在 Zephyr 默认 FATAL 打印之外，追加 dump 当前线程、栈水位、补打环形缓冲，尽量多留现场。

### 4.2 实现

重写 `k_sys_fatal_error_handler`（`<zephyr/kernel.h>` 默认弱实现）：

```cpp
void k_sys_fatal_error_handler(unsigned int reason, const struct arch_esf *esf)
{
    // 1. 打印 reason + 当前线程名（z_current->name）
    // 2. 打印关键栈水位：z_current->stack_info.size / used（high watermark）
    // 3. 若开了阶段二，把 RAM 环形日志缓冲完整补刷一遍（尽量吐干净）
    // 4. 若心跳通道在，补发一条 "FATAL reason=0x%x" 标记
    // 然后进入默认行为（z_riscv_fatal_error / 挂起）
}
```

放哪个文件：【实施时定】`project/` 下新建 `fatal_handler.cpp`，或并入 trd_diag.cpp。默认的寄存器打印（mcause/mtval/call trace）由 Zephyr 保留，我们只**追加**。

> 注意：异常钩子只覆盖"触发异常"的跑飞。**跳飞/死循环/ISR 卡死不触发**，这正是阶段一/二存在的意义。

### 4.3 验收

- 人为触发一个非法访问（如 `*(volatile uint32_t*)0x80000000 = 1;`），确认 FATAL 打印 + 追加信息都出现，且能看到当前线程名与栈水位。

## 5. 阶段四：WDOG 自动复位 + 复位原因自报

### 5.1 目的

跑飞（尤其死循环型，异常钩子抓不到）不能永远失联——用硬件看门狗超时强制复位，复位后在诊断通道自报"上次死因"，实现系统自愈 + 自诊断。

### 5.2 实现

1. 使能 HPM 硬件看门狗：
   ```kconfig
   # prj.conf
   CONFIG_WATCHDOG=y
   CONFIG_WATCHDOG_INIT_PIN=...       # 【实施时查】HPM WDT 驱动 Kconfig 选项
   ```
   设备树启用 wdt 节点（HPM5361 dtsi 的 `wdt`/`wdg` 节点【实施时验证】是否存在/可配）。
2. 喂狗线程：主循环每 200ms 喂一次（喂狗周期 < 超时周期）。
3. 复位原因：读 RCM 复位原因寄存器（HPM SDK 有 `rom_get_reset_status` 或 RCM 寄存器），在 **PreInit 诊断线程**里打印/心跳上报。
4. 心跳通道在复位后会重新起，重启后第一条心跳带"上次复位原因"标记。

> HPM 的 WDT 驱动与复位原因 API 在 zephyr 树/HPM 树的适配情况【实施时验证】：先查 `zephyr/drivers/watchdog/` 有无 hpm 实现，若无则需自写一个极简 `wdt` 驱动或用现有外设驱动替代。

### 5.3 验收

- 人为死循环（如 `for(;;);`）→ 超时后自动复位，重启后诊断通道报告"看门狗复位"。
- 正常跑不误复位。

## 6. 阶段五：CAN 错误处理治本

### 6.1 目的

亡语是补救，**风暴才是根**。这一阶段把"中断里打日志"这条死亡链拆掉，并修总线。

### 6.2 改动

**A. 日志移出中断**（[can.cpp:107-111](framework/drivers/communication/can/can.cpp#L107-L111)）：

```cpp
void Can::state_callback(const device *dev, enum can_state state, can_bus_err_cnt err_cnt, void *user_data)
{
    // 不再 LOG_ERR；只发信号，让诊断/日志线程去打
    k_sem_give(&g_can_diag_sem);          // ISR 安全
    // 或 zbus_pub(&can_diag_topic, ...)   // ISR 安全，项目已有 zbus 基础设施
}
```

诊断线程（阶段一的 diag 线程）`k_sem_take` 后，在**线程上下文**打印，可带节流（如 1s 最多 1 条）。

**B. 错误处理策略**：
- error passive 阶段：降频发送（[trd_can_tx.cpp:41-48](project/thread/can/trd_can_tx.cpp#L41-L48) 可在 `Send` 返回失败时计数退避）。
- bus-off：配置 `CAN_MODE_AUTO_BUS_OFF_RECOVERY` 或应用层 `can_recover`【实施时确认 HPM 支持】。

**C. 修总线无 ACK（物理层，现场必做）**：
- 电调上电接入 CAN_H/CAN_L；
- 总线两端 120Ω 终端电阻；
- 波特率 1M 对齐；示波器看 `mcan0` TX 波形。

### 6.3 验收

- 总线无对端时：日志**不再在中断里打**，系统不再被拖死；心跳正常；`state` 变化有节流地记录。
- 总线恢复 ACK 后：无 `state=1` 错误，系统长时间运行稳定。

## 7. 阶段六：调试器抓现场（最终定位）

### 7.1 目的

前五阶段是"留证据"，调试器抓现场是"定死点"——复现跑飞后，直接看最后一刻 CPU 在哪。

### 7.2 流程

1. J-Link/OpenOCD 连接，全速运行，复现风暴。
2. 心跳停下的瞬间 halt。
3. 看：
   - **PC** 落在哪个函数（`addr2line` 映射）→ 是否在 `uart_send_byte`/log 后端（机制 A）？是否在异常向量（机制 B）？
   - **调用栈** 与各线程 `stack_info`（哪个线程栈爆/ISR 栈水位）
   - `mstatus/mcause/mtval`（若停在异常）
4. 对照阶段一的心跳判据，把"心跳停/不停"映射到具体死点，沉淀为经验。

### 7.3 验收

- 能在 30 分钟内复现并抓到一个跑飞现场，确认机制 A 或 B，并落到具体函数/线程。

## 8. 执行顺序与优先级

| 顺序 | 阶段 | 原因 |
|------|------|------|
| 1 | 阶段一 心跳通道 | 诊断地基，几行代码，立刻能区分 A/B |
| 2 | 阶段五A 日志移出 ISR | 治本第一步，可能直接消除"日志停+失能" |
| 3 | 阶段三 异常钩子 | 异常型跑飞立即可用 |
| 4 | 阶段二 环形日志 | 依赖阶段三/调试器辅助验证，RAM 预算需量 |
| 5 | 阶段六 调试器抓现场 | 有 1-4 后抓现场更有效 |
| 6 | 阶段四 WDOG 复位 | 收尾，需要 WDT 驱动支持【待验证】 |

> 建议先做 **1 + 2A**：改动最小、立刻能确认"跑飞是中断风暴拖死"这条主线是否成立；若成立，系统失能直接缓解，亡语体系再慢慢补全。

## 11. 一句话结论

CAN 总线无对端 ACK → 错误中断风暴 → 中断里立即日志把系统拖死；调试正常只是时序掩盖。**先造独立心跳通道 + 把 CAN 日志移出中断**（阶段一 + 五A，改动最小），即可确认主链；环形日志、异常钩子、WDOG 复位按序补齐，让每次跑飞都能留遗言、能定位。
