# AI 时代架构设计者的学习取舍

> 适用对象：正在从“主要写代码的人”转向“设计架构、定义边界、驱动 AI/成员实现的人”
> 适用场景：`zephyr_user` 子树、嵌入式框架、Zephyr/HPM/STM32 等需要同时理解系统结构和底层接口的工程

---

## 1. 结论先说

你不需要把所有 API 细节都背熟，也不应该把主要精力放在“记住每个函数参数”上。

但你必须掌握一类更高价值的 API 细节：那些会影响架构边界、生命周期、资源模型、错误传播、并发时序、可移植性和可验证性的细节。

换句话说：

```text
普通 API 用法可以交给 AI 查。
API 背后的约束不能交给 AI 猜。
```

AI 时代，架构设计者的能力重心不是“我能不能手写每一行代码”，而是：

1. 我知道系统应该被切成哪些层。
2. 我知道每一层承担什么责任。
3. 我知道哪些底层约束会反过来塑造上层架构。
4. 我能判断 AI 写出来的实现有没有违反这些约束。
5. 我能把模糊需求变成可执行、可验证、可维护的工程方案。

所以，对不熟的东西，学习顺序不应该是：

```text
概念 -> API 全背 -> 写代码
```

而应该是：

```text
概念 -> 工作流 -> 关键约束 -> 最小 API 面 -> 架构影响 -> 再按任务下钻
```

---

## 2. 你现在的角色已经变了

以前你主要是在解决：

```text
这个功能怎么写出来？
```

现在你更多是在解决：

```text
这个功能应该放在哪一层？
这一层应该暴露什么接口？
谁依赖谁？
失败怎么传播？
资源谁拥有？
生命周期谁管理？
以后换板子、换驱动、换业务时哪里不该动？
AI 或队员照着写时会不会写歪？
```

这件事从 `zephyr_user` 子树已经能看出来。

你的子树不是简单堆代码，而是在刻意拆边界：

```text
boards / dts        -> 板卡与设备树
drivers/            -> 子树级底层驱动
framework/drivers   -> 通用外设访问封装
framework/algorithm -> 纯计算能力
framework/modules   -> 设备能力组合
framework/topic     -> 数据契约
framework/cmd       -> 横切调试与辅助能力
framework/init      -> 生命周期与注册启动
project/            -> 当前验证工程或业务装配
```

这说明你的核心工作已经不是“我会不会调用某个函数”，而是“我能不能设计出一个让函数调用不乱飞的系统”。

API 细节仍然重要，但它的重要性变成了服务架构判断，而不是替代架构判断。

## 3. API 细节分三类

学习一个新东西时，不要把所有 API 当成同等重要。可以分成三类。

### 3.1 第一类：可查询 API

这类 API 只要知道“有这个能力”，细节可以现查。

典型例子：

```text
函数名字
参数顺序
枚举值名字
配置项拼写
某个结构体字段名
某个 helper 的返回值类型
```

这些东西不值得长期背。AI、IDE、源码、官方文档都可以帮你查。

你的要求应该是：

```text
我知道它属于哪个模块。
我知道它大概解决什么问题。
我知道要去哪里查权威定义。
```

例如 Zephyr 里某个 GPIO API 的具体参数顺序，不需要靠记忆硬背；需要时看 `include/zephyr/drivers/gpio.h` 或现有调用点即可。

### 3.2 第二类：契约 API

这类 API 必须理解，因为它决定“怎么用才不出事”。

典型内容：

```text
返回值语义
阻塞还是非阻塞
是否可在 ISR 调用
回调在哪个上下文执行
buffer 所有权归谁
调用后数据是否还能改
初始化前后顺序
失败后是否可以重试
线程安全边界
超时语义
资源释放时机
```

这些不是普通细节，而是契约。契约一旦理解错，AI 写的代码再漂亮也会坏。

例如：

```text
UartDma::Send 是异步单段 DMA。
Send 返回 true 只表示提交成功，不等于数据已经发完。
tx_busy_ 没清之前再次 Send 会失败。
```

这个细节不是“参数怎么填”的问题，而是直接决定上层日志、协议回复、AI 输出桥接是否必须拼成一整段再发。

这类 API 你必须会判断。

### 3.3 第三类：架构 API

这类 API 会决定层次边界和系统形态，必须重点掌握。

典型内容：

```text
注册宏
生命周期入口
Kconfig select 链路
CMake 装配方式
DeviceTree chosen / alias / binding
链接段收集机制
HAL 抽象边界
topic 数据契约
模块初始化阶段
失败策略
```

在你的子树里，这类 API 比普通业务函数重要得多。

例如：

```text
REGISTER_INIT()
REGISTER_THREAD()
InitStage
ThreadStage
InitFailPolicy
target_sources(app)
ZEPHYR_EXTRA_MODULES
select DUST_*
DT_ALIAS(...)
DT_CHOSEN(...)
```

这些东西不是“一个 API”，而是系统骨架。你必须理解它们怎样共同组成：

```text
Kconfig -> CMake -> DTS -> 编译 -> 链接段 -> 启动遍历 -> 线程运行
```

AI 可以帮你写某个 `REGISTER_THREAD()` 调用，但你必须知道它注册到哪里、什么时候跑、失败后谁处理、为什么它不应该绕过 `framework/init`。

## 4. 什么时候只看宏观

当你处在下面这些阶段时，应该优先看宏观，不要陷进 API 细节：

```text
判断一个技术能不能放进架构
决定模块边界
决定依赖方向
决定是放 framework 还是 project
决定是通用能力还是板卡能力
决定是否要抽象接口
决定生命周期阶段
决定配置门禁
决定文档和使用者心智模型
```

这时你要问的问题是：

```text
这个东西解决什么问题？
它依赖哪些资源？
它向上暴露什么能力？
它向下依赖什么硬件/系统服务？
它失败时影响范围多大？
它是否会绑定某块板子？
它未来是否会换实现？
它应该由维护者控制，还是由业务使用者控制？
```

比如你评估一个新算法库，第一步不是背 API，而是判断：

```text
它是不是纯计算？
是否依赖 malloc？
是否依赖浮点？
是否可在中断中使用？
是否需要动态内存？
是否适合放 framework/algorithm？
是否会污染 drivers/modules 的边界？
```

这些判断比 `foo_init(x, y, z)` 的参数顺序重要。

---

## 5. 什么时候必须下钻 API

下面这些情况不能只看宏观，必须下钻到 API 细节甚至源码。

### 5.1 API 影响资源所有权

只要涉及 buffer、DMA、指针、队列、内存池，就必须弄清楚所有权。

你要知道：

```text
buffer 是调用者持有还是驱动持有？
函数返回后 buffer 能不能释放？
回调拿到的指针是否仍有效？
DMA 是否还在读写这块内存？
队列里存的是值、指针还是引用？
```

嵌入式里这不是细节，是生死线。

### 5.2 API 影响时序

只要涉及中断、DMA、线程、回调、异步发送、定时器，就必须看契约。

你要知道：

```text
调用立即完成，还是提交异步操作？
完成事件在哪里通知？
回调运行在 ISR 还是线程？
能不能阻塞？
能不能调用日志？
是否需要锁？
是否可能重入？
```

如果这个细节不清楚，上层架构会被设计错。

### 5.3 API 影响配置链路

Kconfig、CMake、DTS、linker section 这类东西必须下钻。

因为它们决定“代码是否真的进镜像”，不是“代码写没写”。

你需要知道：

```text
谁 select 谁？
默认值是什么？
哪个 CMakeLists 把源文件加进 app？
设备树节点从哪里来？
binding 是否匹配？
chosen 和 alias 谁消费？
链接段是否被 KEEP？
```

这些东西 AI 很容易写得“看起来对”，但实际编译或运行时完全没接上。

### 5.4 API 影响跨平台边界

如果一个 API 只在 HPM 有、STM32 没有，或者 Zephyr 主线有但 SDK glue 没有，你必须理解它。

因为这决定：

```text
放 framework/drivers 还是 drivers/usb/hal/hpm？
要不要抽 interface？
Kconfig 是否按 SoC 拆？
DTS binding 是否要分厂商？
CI 是否需要 HPM tree patch？
```

跨平台问题不能靠“AI 写一个能编译的版本”解决。你要设计的是可替换边界。

### 5.5 API 影响错误语义

返回 `0`、负 errno、bool、nullptr、超时，这些都要看。

你要知道：

```text
失败是否可恢复？
失败是否说明设备不存在？
失败是否说明暂时 busy？
失败是否应该 HaltOnFail？
失败是否只需要降级？
```

这会影响 `InitFailPolicy`、日志级别、重试策略和业务线程是否继续跑。

## 6. 对 API 的掌握深度标准

你不需要把 API 背到“能默写”，但要达到下面这个标准。

### 6.1 最低标准：能定位

你应该知道：

```text
这个 API 在哪个头文件
属于哪个层
谁是典型调用方
有没有现成例子
官方文档或源码在哪里
```

这是能让 AI 和 IDE 帮你工作的基础。

### 6.2 合格标准：懂契约

你应该能回答：

```text
它什么时候调用？
调用前需要什么初始化？
调用后资源归谁？
失败怎么表达？
是否阻塞？
是否线程安全？
是否 ISR 安全？
是否依赖 Kconfig/DTS/CMake？
```

达到这个程度，你就能审 AI 的代码。

### 6.3 架构师标准：能抽象

你应该能判断：

```text
这个 API 应不应该被上层直接看到？
它是否应该被 framework 包起来？
它的哪些参数应该暴露，哪些应该固化在板卡层？
它的错误是否应该转换成统一错误模型？
它的生命周期是否应该交给 REGISTER_INIT？
它是否应该成为 topic、module、driver、cmd 的一部分？
```

这才是你现在最需要练的能力。

## 7. AI 时代的正确分工

你和 AI 不应该抢同一件事。

AI 适合做：

```text
查 API 名字
补参数
生成样板代码
按已有模式扩展文件
对照源码整理调用链
写初稿文档
批量改机械结构
列验证清单
```

你应该抓：

```text
系统边界
抽象层级
生命周期
资源预算
错误策略
接口稳定性
跨平台策略
验证闭环
哪些事实必须实测
哪些地方不能让 AI 猜
```

一个很实用的分工是：

```text
AI 负责把“局部正确”做快。
你负责定义什么叫“整体正确”。
```

如果你把时间花在背所有 API 上，你会变成更强的程序员，但不一定会变成更强的架构设计者。

如果你完全不理解 API 契约，只看宏观，你会变成会画图但落不了地的人。

正确位置在中间：

```text
宏观决定方向。
契约决定边界。
普通细节交给工具。
关键细节亲自确认。
```

## 8. 用你的子树举例

### 8.1 `framework/algorithm`

这里你不需要背每个滤波器的全部成员函数。

但你需要知道：

```text
algorithm 是纯计算层。
不应该依赖 Zephyr device。
不应该直接管线程。
不应该直接碰 DTS。
不应该持有具体外设。
```

你还需要知道关键契约：

```text
是否动态分配内存？
状态量大小是多少？
输入输出单位是什么？
更新频率是否影响稳定性？
是否需要初始化协方差、限幅、采样周期？
```

这些会影响模块层和业务层怎么用它。

### 8.2 `framework/drivers`

这里 API 细节比 algorithm 更重要。

因为它面对硬件、DMA、回调、设备树。

你需要掌握：

```text
Init 何时调用
Send/Read 是否阻塞
buffer 生命周期
回调上下文
错误码
DTS alias/chosen 消费方式
Kconfig 门禁
```

但你仍然不需要背所有 Zephyr 原生 API。你要掌握的是封装层想屏蔽什么、必须暴露什么。

### 8.3 `framework/init`

这里属于架构 API，必须重点掌握。

因为它决定整个系统怎么启动。

你需要理解：

```text
REGISTER_INIT 注册到哪里
REGISTER_THREAD 注册到哪里
InitStage / ThreadStage 怎么分
InitLevel 怎么排序
InitFailPolicy 怎么影响失败处理
链接段如何被收集
System_Startup 如何遍历
```

这比背某个业务线程里的函数调用重要得多。

### 8.4 `project`

这里你要关注的是装配，而不是沉迷局部实现。

核心问题是：

```text
这个业务线程启用了哪些架构能力？
它 select 了哪些 DUST_*？
它依赖哪些设备树 alias/chosen？
它是否把业务逻辑泄漏到 framework？
它是否把板卡细节写死到通用层？
```

## 9. 学新东西时的五层阅读法

以后遇到不熟的技术，可以按这个顺序学。

### 第一层：概念层

先回答：

```text
它是什么？
解决什么问题？
它在系统里通常处在哪一层？
它和我已有架构的哪个模块相似？
```

不要急着看 API。

### 第二层：流程层

弄清楚典型生命周期：

```text
配置 -> 初始化 -> 运行 -> 回调/事件 -> 错误 -> 关闭
```

比如 USB 就是：

```text
DTS/Kconfig -> HAL init -> device stack init -> enumeration -> setup request -> endpoint transfer -> callback
```

流程不清楚，API 看得越多越乱。

### 第三层：约束层

专门找限制：

```text
能不能在 ISR 用？
是否异步？
是否需要对齐？
buffer 谁持有？
是否需要 ZLP？
是否需要 cache flush？
是否依赖时钟？
是否有固定初始化顺序？
```

这一层是最值得你亲自看的。

### 第四层：最小 API 面

只挑完成一个最小闭环必须用的 API。

例如：

```text
init
start
send/read
callback
stop
error query
```

先不要看完整 API 大全。

### 第五层：架构落点

最后决定：

```text
放哪一层？
是否封装？
封装暴露什么？
配置从哪里来？
谁拥有资源？
谁处理错误？
谁负责验证？
```

这一步才对应你现在真正的工作。

## 10. 一个判断表

| 问题 | 只看宏观 | 必须看 API 契约 | 必须看源码/实现 |
| --- | --- | --- | --- |
| 判断技术是否值得引入 | 是 | 否 | 否 |
| 决定放在哪一层 | 是 | 是 | 视情况 |
| 写 README/架构说明 | 是 | 关键 API 要看 | 视情况 |
| 设计 HAL 抽象 | 否 | 是 | 是 |
| 写驱动封装 | 否 | 是 | 是 |
| 调 DMA/USB/CAN/UART 问题 | 否 | 是 | 是 |
| 只是补一个普通调用 | 否 | 轻量确认 | 否 |
| 评审 AI 生成代码 | 是 | 是 | 关键路径要看 |
| 处理 Kconfig/CMake/DTS | 否 | 是 | 经常要看 |
| 处理跨板卡差异 | 是 | 是 | 经常要看 |

## 11. 你应该训练的不是“背 API”，而是“API 风险嗅觉”

一个架构设计者看到 API 时，应该自然地问：

```text
这个调用有没有隐藏状态？
有没有异步完成？
有没有资源所有权转移？
有没有线程上下文要求？
有没有配置前提？
有没有平台差异？
错误会不会被吞掉？
失败后系统处于什么状态？
上层是否应该知道这个细节？
```

这比“我记得函数参数顺序”重要得多。

AI 可以帮你补参数，但 AI 很可能不知道你的架构边界。它会倾向于把功能写通，而不是把系统写稳。

你的价值就在于识别：

```text
这段代码局部能跑，但放进我的系统会破坏边界。
这段代码看起来麻烦，但它保住了生命周期。
这个参数不是普通参数，它代表资源所有权。
这个宏不是普通宏，它决定代码会不会进镜像。
这个回调不是普通函数，它运行在不能阻塞的上下文。
```

## 12. 最适合你的学习投入比例

对你现在的阶段，推荐比例是：

```text
40% 架构与边界
25% 流程与生命周期
20% 关键 API 契约
10% 典型源码实现
5% 普通 API 记忆
```

普通 API 记忆只占很小一部分。

但“关键 API 契约 + 典型源码实现”加起来有 30%，不能完全省掉。因为嵌入式架构不是纯软件抽象，硬件时序、内存、DMA、中断、DTS、Kconfig 都会把抽象拉回现实。

## 13. 实战规则

以后你学一个新模块，可以按这个模板落地。

### 13.1 先写一页架构卡

```text
模块名称：
解决的问题：
所在层：
上游依赖：
下游消费者：
生命周期：
配置来源：
资源所有权：
错误策略：
跨平台点：
必须掌握的 API 契约：
可以现查的 API：
验证方式：
```

这张卡比 API 摘抄更有价值。

### 13.2 API 只摘“会改变设计”的部分

不要写：

```text
函数 A 参数 1 是 xxx，参数 2 是 xxx
函数 B 参数 1 是 xxx，参数 2 是 xxx
```

除非这些参数影响设计。

应该写：

```text
Send 是异步提交，完成靠 TX_DONE 回调，因此上层不能连续分段发送。
Read 读取内部 BipBuffer，数据到达由 sem_ 唤醒，因此线程应阻塞等待而不是轮询。
shell UART 后端消费 zephyr,shell-uart chosen，因此 overlay 必须提供 chosen。
```

这种记录才是架构知识。

### 13.3 每次让 AI 写代码前，先给它边界

不要只说：

```text
帮我写一个 USB 类。
```

要说：

```text
这个类属于 framework/drivers，只封装通用 USB device stack。
HAL 差异留在 drivers/usb/hal/<platform>。
不允许依赖 project/thread。
发送接口必须体现异步 busy 语义。
配置从 DTS 和板卡 Kconfig 来。
失败通过 bool/errno 返回，由 init 层决定 HaltOnFail。
```

AI 不是不能写架构代码，而是你必须先把架构边界喂给它。

---

## 14. 最终答案

你应该关注宏观，但不能停在宏观。

更准确地说，你应该把学习重心从“API 使用细节”转到“API 契约对架构的影响”。

普通 API 细节可以现查，可以让 AI 补，可以靠 IDE 跳转。

但下面这些东西你必须亲自理解：

```text
生命周期
资源所有权
并发时序
错误语义
配置链路
跨平台边界
抽象是否泄漏
验证方式
```

这就是 AI 时代架构设计者和普通代码执行者的分界线。

代码执行者关心：

```text
这个 API 怎么调？
```

架构设计者关心：

```text
这个 API 的约束会不会改变我的系统设计？
这个 API 应不应该被别人直接看到？
这个 API 的错误和生命周期应该由谁承担？
```

你的子树已经在往这个方向走了。继续往前走时，不要让自己被 API 大全拖回“背函数”的旧模式；也不要因为 AI 能写代码，就放弃对关键契约的掌控。

最好的状态是：

```text
宏观看得清，边界定得住，关键 API 契约心里有数，普通细节随用随查。
```
