# 线程故障钩子编译期注册规划

> 2026-10-24。动机：当前故障配置靠 `Start()` 前连续三次 `Set*()` 调用完成，分散在每个线程的启动函数里，漏写不报错、写错顺序也能跑，**配置与线程本体是分离的**。本规划把配置收进注册期。
>
> **拍板结论（用户 2026-10-24）**：采用**方案 A（链接段注册宏）**；`keep_alive` **不进注册**（只有 shell 需要保留，继续走独立接口）。

---

## 1 现状

### 1.1 当前写法

每个线程在 `Start()` 之前手工调 setter：

```cpp
// framework/modules/remotes/remote.hpp:73-81
bool Start(ThreadPrio prio = ThreadPrio::Normal)
{
    if (!ready_) return false;
    thread_.SetFaultPolicy(ThreadFaultPolicy::Recover);
    thread_.SetRetryHook(OnRetry);
    thread_.SetExitHook(OnExit);
    thread_.Start(TaskEntry, K_NO_WAIT, prio, this, "remote");
    return true;
}
```

| 线程 | 位置 | policy | retry | exit | keep_alive |
|------|------|--------|-------|------|------------|
| `shell` | `framework/shell/shell.cpp:179` + `shell.hpp:38` | 默认 `Recover` | 无 | 无 | **true**（`SetKeepAlive`，**本次不动**） |
| `imu` | `framework/modules/imu/drivers/imu.hpp:46-48` | `Recover` | `OnRetry` | `OnExit` | false |
| `remote` | `framework/modules/remotes/remote.hpp:76-78` | `Recover` | `OnRetry` | `OnExit` | false |
| `output` | `project/thread/gpio/trd_gpio.cpp:60` | **未设（默认 Recover）** | 无 | 无 | false |
| `test` | `project/thread/test/trd_test.cpp:82-84` | `Recover` | `OnRetry` | `OnExit` | false |

### 1.2 问题

| # | 问题 | 证据 | 后果 |
|---|------|------|------|
| 1 | **配置分散**：policy / retry / exit 三行散在启动函数里，与线程本体分离 | 上表五处 | 读代码要先翻 `Start()` 才知道线程属于哪一档影响面 |
| 2 | **漏写无提示**：`output` 完全没设，静默拿到默认 `Recover` | `trd_gpio.cpp:60` | 心跳线程出事会把整机全杀，与「影响小就自杀」相反 |
| 3 | **顺序无约束**：先 `Start()` 后 `SetFaultPolicy()` 也编得过，只是不生效 | `thread.hpp:134` 起 | 配置静默丢失 |
| 4 | **重复样板**：每个线程三行，内容只有参数不同 | 上表 | 新增线程容易照抄漏项 |

## 2 设计

### 2.1 机制

新增 `.thread_fault` 链接段，宏在编译期生成一张只读配置表；`Thread::Start()` 内部按线程名查表，命中则写入 `fault_`。

本质是**链接期收集 + 启动期查表**，不是纯编译期求值。本方案与框架既有的 `REGISTER_INIT` / `REGISTER_THREAD` / `REGISTER_SHELL_CMD` / `REGISTER_IMU` 完全同构。

`keep_alive` **不进配置表**：只有 shell 需要保留，它继续用现成的 `SetKeepAlive()`。

### 2.2 配置项结构

`framework/init/thread/thread_fault.hpp` 追加：

```cpp
/**
 * @brief 线程故障配置项：编译期放入 .thread_fault 段，Start 时按线程名查找
 */
struct ThreadFaultEntry
{
    const char*        name;        // 线程名，必须与 Start() 的 name 参数完全一致
    ThreadFaultPolicy  policy;      // 故障策略
    RetryHook          retry;       // Retry 钩子；nullptr=未装
    ExitHook           exit;        // 亡语；nullptr=未装
};

/**
 * @brief 按线程名查找故障配置
 * @param name 线程名
 * @return 命中的配置项；未注册返回 nullptr
 */
const ThreadFaultEntry* FindThreadFault(const char* name);
```

### 2.3 注册宏

```cpp
/**
 * @brief 注册线程故障配置
 *
 * 与 REGISTER_INIT / REGISTER_THREAD 同构：编译期放入 .thread_fault 段，
 * Thread::Start() 按线程名查表后生效。新增线程只在自己的源文件里加一行。
 *
 * @param ident_   唯一标识符（通常与线程名一致）
 * @param name_    线程名（字符串字面量，必须与 Start 的 name 参数一致）
 * @param policy_  ThreadFaultPolicy 枚举值
 * @param retry_   Retry 钩子；nullptr 表示未装
 * @param exit_    亡语；nullptr 表示未装
 */
#define REGISTER_THREAD_FAULT(ident_, name_, policy_, retry_, exit_)                \
    static const ThreadFaultEntry kThreadFault_##ident_                             \
        __attribute__((used, __section__(".thread_fault"))) = {                     \
        name_, ThreadFaultPolicy::policy_, retry_, exit_                            \
    }
```

### 2.4 查找实现

`framework/init/thread/thread_fault.cpp` 追加：

```cpp
extern const ThreadFaultEntry __thread_fault_start[];
extern const ThreadFaultEntry __thread_fault_end[];

const ThreadFaultEntry* FindThreadFault(const char* name)
{
    if (name == nullptr) return nullptr;

    for (const ThreadFaultEntry* e = __thread_fault_start; e < __thread_fault_end; ++e)
    {
        if (e->name != nullptr && std::strcmp(e->name, name) == 0) {
            return e;
        }
    }
    return nullptr;
}
```

需要 `#include <cstring>`（该文件目前没有）。

### 2.5 链接段

`framework/cmd/linker/dust_init.ld` 追加：

```ld
SECTION_PROLOGUE(.thread_fault,,)
{
    __thread_fault_start = .;
    KEEP(*(.thread_fault))
    __thread_fault_end = .;
} GROUP_LINK_IN(ROMABLE_REGION)
```

### 2.6 Start 内部应用

`framework/init/thread/thread.hpp` 的 `Start()` 开头追加：

```cpp
// 按线程名取故障配置；未注册时保留默认值并告警（写错名字能看见）
const ThreadFaultEntry* cfg = FindThreadFault(name);
if (cfg != nullptr)
{
    fault_.policy     = cfg->policy;
    fault_.retry_hook = cfg->retry;
    fault_.exit_hook  = cfg->exit;
}
else
{
    DUST_LOG_WRN("thread %s has no fault config, using default", name);
}
```

### 2.7 各线程改成

| 文件 | 改成 |
|------|------|
| `project/thread/gpio/trd_gpio.cpp` | 文件内加 `REGISTER_THREAD_FAULT(output, "output", Isolate, nullptr, nullptr);` |
| `project/thread/test/trd_test.cpp` | 删三行 `Set*`，加 `REGISTER_THREAD_FAULT(test, "test", Recover, OnRetry, OnExit);` |
| `framework/modules/remotes/remote.hpp` | 删三行 `Set*`；`OnRetry` / `OnExit` 从 `private` 移到 `public`；类定义之后加 `REGISTER_THREAD_FAULT(remote, "remote", Recover, OnRetry, OnExit);` |
| `framework/modules/imu/drivers/imu.hpp` | 同上 |
| `framework/shell/shell.cpp` / `shell.hpp` | **不动**（`KeepAlive` 不进注册，`shell_.SetKeepAlive(true)` 原样保留） |

> ⚠️ imu / remote 的 `OnRetry` / `OnExit` 是**私有静态成员**，宏在类外引用会编不过。本规划选「钩子移到 `public`」——它们本身就是被框架回调的，没有隐藏的必要。

## 3 与方案 B（模板参数）的对比记录

方案 B 已评估但不采用，记录在此备查：把 policy/retry/exit 做成 `Thread` 的非类型模板参数（`Thread<2048, Recover, OnRetry, OnExit>`），值编进类型、零运行期开销、写错编译报错。不采用的原因：

1. **类型签名全变**：`Thread<2048>` 出现在 `imu.hpp` / `remote.hpp` / `shell.hpp` 三个头文件和两个 project 线程，全部要改；A 一行不动。
2. **与框架风格不一致**：框架里全部是「宏 + 链接段 + 遍历」，B 会引入唯一的「模板参数配置」风格。
3. **丧失运行期可配**：调试时无法用 shell 改策略；A 保留 setter 即可。

| # | 场景 | 预期 |
