# 线程编写指南：从 REGISTER_INIT 到 Task

> 日期：2026-10-19
> 适用：`framework/init`（启动器 + 线程模板）、`project/thread/`（业务线程）、用户区 `project/thread/`
> 目标：把「一个线程从源码到跑起来」的每一层、每一处细节讲清楚，包括编译期如何确定、链接期如何成表、启动期如何遍历、运行期如何调度，以及任务体与错误处理如何分离。

---

## 1. 文档定位

本文只讲**线程的生命周期**，不讲业务逻辑。读完应当能回答：

- 我写的这个 `.cpp` 到底进没进镜像？
- `REGISTER_INIT` / `REGISTER_THREAD` 展开成了什么？
- 启动器凭什么能按顺序找到它们？
- `Task` 里为什么不用写 `for (;;)`、不用写错误处理？
- 出错时到底发生了什么？
- `thread list` 里的数字从哪来的？

---

## 2. 全链路总览

```text
┌──────────────────────────────────────────────────────────────────┐
│ 编译期：线程"存不存在"                                            │
│   Kconfig 符号 → CMake 条件 → .cpp 是否参与编译 → 宏是否展开       │
└───────────────────────────────┬──────────────────────────────────┘
                                ↓
┌──────────────────────────────────────────────────────────────────┐
│ 链接期：线程"在哪张表里"                                          │
│   .user_init / .user_thread 段 → KEEP → __user_*_start/end 符号    │
└───────────────────────────────┬──────────────────────────────────┘
                                ↓
┌──────────────────────────────────────────────────────────────────┐
│ 启动期：线程"什么时候被创建"                                      │
│   System_Startup → PreInit → PreThread → EarlyInit → … → AppThread │
└───────────────────────────────┬──────────────────────────────────┘
                                ↓
┌──────────────────────────────────────────────────────────────────┐
│ 运行期：线程"怎么跑、出错怎么办"                                  │
│   Thread::Run 外壳 → Task 一拍 → TaskResult → 钩子 / 统计          │
└──────────────────────────────────────────────────────────────────┘
```

四层各自独立，任何一层出问题，现象完全不一样：

| 层 | 出问题的现象 |
|---|---|
| 编译期 | 日志里根本没有这个线程的 `[boot] xxx init/start` |
| 链接期 | 源码写了注册宏，但段里没有（`map` 文件可查） |
| 启动期 | 有 `[boot]` 日志但顺序不对，或启动卡在某阶段 |
| 运行期 | 线程起来了但 `run` 不涨、`retry` 异常、程序卡死 |

## 3. 第一层：编译期 —— 线程是否存在

### 3.1 Kconfig 门禁

业务线程的开关定义在 `project/Kconfig`（用户区同理）：

```kconfig
config TRD_XXX
    bool "XXX thread"
    default n
    select DUST_MOD_DEV_XXX      # 该线程依赖的架构层模块
    help
      说明这个线程做什么。
```

`TRD_*` 是**业务门禁**，不带 `DUST_` 前缀（架构层的符号才带，见下）。

架构层被它 `select` 的符号在各自子模块里定义：

| 前缀 | 位置 | 例子 |
|---|---|---|
| `DUST_DEV_*` / `DUST_COM_*` | `framework/drivers/Kconfig` | `DUST_DEV_GPIO_OUTPUT`、`DUST_COM_UART_DMA` |
| `DUST_MOD_DEV_*` | `framework/modules/Kconfig` | `DUST_MOD_DEV_IMU`、`DUST_MOD_DEV_REMOTE` |
| `DUST_TPC_*` | `framework/topic/Kconfig` | `DUST_TPC_IMU_TO` |
| `DUST_CMD_*` | `framework/cmd/Kconfig` | `DUST_CMD_SHELL` |
| `DUST_CTL_*` / `DUST_FLT_*` / `DUST_ID_*` | `framework/algorithm/Kconfig` | `DUST_CTL_PID` |

开关打开的位置是**板卡配置文件**（`project/boards/<vendor>/<cfg>/<board>.conf`）或 `project/prj.conf`：

```conf
CONFIG_TRD_XXX=y
```

### 3.2 CMake 装配

`project/thread/CMakeLists.txt` 里每个线程一个 `if`：

```cmake
if(CONFIG_TRD_XXX)
    target_sources(app PRIVATE ${CMAKE_CURRENT_SOURCE_DIR}/xxx/trd_xxx.cpp)
    target_include_directories(app PRIVATE
        ${CMAKE_CURRENT_SOURCE_DIR}
        ${CMAKE_CURRENT_SOURCE_DIR}/xxx
    )
endif()
```

**这一步决定 `.cpp` 进不进编译。** `CONFIG_TRD_XXX=n` 时这个文件**根本不参与编译**——不是编了再丢，是压根没编。

### 3.3 宏展开成什么

```cpp
REGISTER_INIT(thread_init, EarlyInit, High, HaltOnFail, nullptr, "imu_init");
```

展开为**两份对象**（`Init_entry.hpp`）：

```cpp
// ① 结构体本身：放在普通 const 区，按正常 C++ 布局
static const InitEntry kInitEntry_thread_init = {
    thread_init,                    // function
    nullptr,                        // rollback
    InitStage::EarlyInit,           // stage
    InitLevel::High,                // level
    StartFailPolicy::HaltOnFail,     // fail
    "imu_init"                      // name
};

// ② 指向结构体的指针：放进 .user_init 段
static const InitEntry* const kInitEntryPtr_thread_init
    __attribute__((used, __section__(".user_init"), aligned(sizeof(void*)))) =
        &kInitEntry_thread_init;
```

```cpp
REGISTER_THREAD(thread_start, EarlyThread, HaltOnFail, "imu_start");
```

展开为：

```cpp
static const ThreadEntry kThreadEntry_thread_start = {
    thread_start,                   // start
    ThreadStage::EarlyThread,       // stage
    "imu_start"                     // name
};

static const ThreadEntry* const kThreadEntryPtr_thread_start
    __attribute__((used, __section__(".user_thread"), aligned(sizeof(void*)))) =
        &kThreadEntry_thread_start;
```

**为什么段里存指针而不是结构体**：

| 项 | 段内存结构体 | 段内存指针 |
|---|---|---|
| 每项占段空间 | `sizeof(InitEntry)` = 16 B | 4 B（32 位目标） |
| 结构体布局变化 | 段内字节布局跟着变 | 段内始终是 4 B 指针 |
| 遍历步长 | 依赖 `sizeof(InitEntry)` | 恒定 `sizeof(void*)` |
| 对齐要求 | 结构体自然对齐 | `aligned(sizeof(void*))` 显式声明 |

当前全源码编译，收益主要是**防御性**的：结构体字段增删不再影响段内布局，遍历代码也不必依赖结构体大小。

### 3.4 逐字拆解五个属性

| 部分 | 作用 | 少了会怎样 |
|---|---|---|
| `static` | 内部链接，不导出符号 | 多个 `.cpp` 用同名函数注册时会符号冲突 |
| `const` | 放进只读段（ROM） | 占 RAM |
| `used` | 告诉编译器「别因为没被引用就删掉」 | `-O2` + LTO 下整个注册项被优化掉，段为空 |
| `__section__(".user_init")` | 强制放进指定段 | 留在 `.rodata`，启动器找不到 |
| `aligned(sizeof(void*))` | 保证段内每项按指针宽度对齐 | 遍历时可能取到错位地址 |

注意：`used` / `__section__` / `aligned` **只加在指针对象上**，结构体本体不需要——它被指针引用，编译器不会删。

**`used` 是最容易漏的一环**：这些对象在源码里没有任何引用，编译器完全有理由删除。`used` 是强制保留的唯一手段。

### 3.5 为什么 `.cpp` 里不需要 `#ifdef`

因为**编译单元本身就是条件编译**：

```cpp
// trd_imu.cpp —— 不需要整个文件包 #ifdef CONFIG_TRD_IMU
#include "imu.hpp"
#include "Init_entry.hpp"
...
REGISTER_INIT(thread_init, EarlyInit, High, HaltOnFail, nullptr, "imu_init");
```

`CONFIG_TRD_IMU=n` 时 CMake 不编译这个文件，`REGISTER_INIT` 从来没被展开过。

**例外**：写在头文件里、会被多个编译单元展开的宏，才需要 `#ifdef` 保护。

## 4. 第二层：链接期 —— 段如何闭合成表

### 4.1 链接脚本

`framework/cmd/linker/dust_init.ld`：

```ld
SECTION_PROLOGUE(.user_init,,)
{
    __user_init_start = .;
    KEEP(*(.user_init))
    __user_init_end = .;
} GROUP_LINK_IN(ROMABLE_REGION)
```

- `KEEP(...)`：即使没有外部引用也不丢弃这些段
- `__user_init_start` / `__user_init_end`：链接器自动生成的边界符号

`init/CMakeLists.txt` 把它接进 Zephyr 链接流程：

```cmake
zephyr_linker_sources(ROM_SECTIONS ../cmd/linker/dust_init.ld)
```

### 4.2 启动器怎么拿到表

`startup/Init_entry.cpp`：

```cpp
extern const InitEntry*   const __user_init_start[];
extern const InitEntry*   const __user_init_end[];
extern const ThreadEntry* const __user_thread_start[];
extern const ThreadEntry* const __user_thread_end[];

for (const InitEntry* const* item = __user_init_start; item < __user_init_end; ++item)
{
    const InitEntry* e = *item;
    ...
}
```

声明成**指针数组**：`item++` 的步长恒为 `sizeof(void*)`，与结构体大小无关。取表时再 `*item` 解出结构体指针。

> 类型必须精确写成 `const InitEntry* const*`（指向「常量指针」的指针）。少一层会触发 `Comparison of distinct pointer types` 编译错误。

### 4.3 段的物理布局

```text
.user_init 段（指针表）
┌─────────────────────────────┐ ← __user_init_start
│ &InitEntry(buzzer)          │ 4 B
├─────────────────────────────┤
│ &InitEntry(w25q128)         │ 4 B
├─────────────────────────────┤
│ &InitEntry(dbg)             │ 4 B
├─────────────────────────────┤
│ ...                         │
└─────────────────────────────┘ ← __user_init_end

.rodata（结构体本体，布局与段无关）
┌─────────────────────────────┐
│ InitEntry(buzzer)   16 B    │
├─────────────────────────────┤
│ InitEntry(w25q128)  16 B    │
├─────────────────────────────┤
│ InitEntry(dbg)      16 B    │
└─────────────────────────────┘
```

**顺序由链接器决定**，不是源码顺序。所以：

- 同阶段同等级的条目不保证按书写顺序执行
- 需要严格顺序 → 用不同阶段或不同等级表达

### 4.4 段里的顺序为什么"看起来是对的"

实际上 GCC 通常按目标文件顺序拼接，而目标文件顺序跟随 CMake 的 `target_sources` 顺序，所以现象上往往是源码顺序。**这是实现细节，不是契约**，不要依赖。

## 5. 第三层：启动期 —— 什么时候创建线程

### 5.1 阶段与等级

十个阶段，两两成对：

```text
PreInit   → PreThread
EarlyInit → EarlyThread
MidInit   → MidThread
LateInit  → LateThread
AppInit   → AppThread
```

**为什么成对**：先让资源初始化完毕，再启动使用这些资源的线程。例如 IMU 必须在 `EarlyInit` 里把器件和 SPI 打开，`EarlyThread` 才能开始采样。

**等级只作用于 Init**：

```cpp
static constexpr InitLevel kLevelOrder[] = {
    InitLevel::High,
    InitLevel::Mid,
    InitLevel::Low,
};
```

`RunStage(InitStage)` 对每个阶段跑三轮：High → Mid → Low。同一轮里按链接段顺序遍历。

`RunStage(ThreadStage)` **没有等级**，直接一遍遍历。

### 5.2 初始化项执行

```cpp
static void RunStage(InitStage stage)
{
    if (startup_aborted) return;

    for (const InitLevel level : kLevelOrder)
    {
        for (const InitEntry* e = __user_init_start; e < __user_init_end; ++e)
        {
            if (e->stage != stage) continue;
            if (e->level != level) continue;

            if (!e->function()) {
                if (e->rollback != nullptr) e->rollback();
                HandleInitFail(*e);
                continue;
            }
            DUST_LOG_OK("[boot] %s init", e->name);
        }
    }
    DUST_LOG_OK("=====     [boot] %s ok     =====\n", StageName(stage));
}
```

关键点：

1. **失败先回滚**：`rollback` 在 `HandleInitFail` 之前调用，保证哪怕要停机，本项申请的资源也已经释放
2. **失败不打印成功横幅**：`continue` 跳过 `DUST_LOG_OK`
3. **每阶段结束打一条横幅**：看到 `[boot] EarlyInit ok` 就知道这个阶段整个过了

### 5.3 失败策略

```cpp
if (e->fail == StartFailPolicy::HaltOnFail) {
    DUST_LOG_ERR("[boot] %s fail", entry.name);
    EXEC_BUZZER_ERR(nullptr);
    while (1) {}                    // 死循环，等待复位
} else {
    DUST_LOG_WRN("[boot] %s fail", entry.name);
}
```

| 策略 | 行为 | 适用 |
|---|---|---|
| `HaltOnFail` | 红字报错 + 蜂鸣 + 死循环 | 系统跑不起来的基础资源（调试台、IMU、遥控器） |
| `ContinueOnFail` | 橙字告警，继续下一项 | 可选功能、能降级运行的功能 |

**注意**：`HaltOnFail` 的 `while(1){}` 不返回，所以同一阶段的后续条目**不会执行**，后面的阶段也不会。这是有意的——基础资源没了，继续跑没有意义。

### 5.4 线程项执行

```cpp
static void RunStage(ThreadStage stage)
{
    if (startup_aborted) return;

    for (const ThreadEntry* e = __user_thread_start; e < __user_thread_end; ++e)
    {
        if (e->stage != stage) continue;

        if (!e->start()) {
            DUST_LOG_ERR("[boot] %s start fail", e->name);
            startup_aborted = true;
            continue;
        }
        DUST_LOG_OK("[boot] %s start", e->name);
    }
    DUST_LOG_OK("=====     [boot] %s ok     =====\n", StageName(stage));
}
```

线程项的语义：

- **启动函数返回 `bool`**：`k_thread_create` 本身不返回错误（除非参数非法），但业务可以检查前置条件后返回 `false`
- **没有等级**：线程启动天然比初始化轻，不需要再分优先级
- **失败即中止**：任一 `start()` 返回 `false`，`startup_aborted` 置位，后续阶段全部跳过
- **查询接口**：`System_StartupAborted()` 返回 0/1

### 5.5 启动时间线

```text
main()
  → System_Startup()
      PreInit     [High → Mid → Low]   ← 调试台 / buzzer / flash / GPIO
      sleep 500
      PreThread                        ← shell 线程
      sleep 500 + 蜂鸣
      EarlyInit   [High → Mid → Low]   ← IMU / 遥控器
      sleep 500
      EarlyThread                      ← IMU / 遥控器线程
      sleep 500 + 蜂鸣
      MidInit / MidThread / LateInit / LateThread / AppInit / AppThread
  → while(1) k_msleep(1000)
```

总共约 4.5 秒（9 次 500ms + 4 次蜂鸣）。**阶段性 sleep 是留给硬件上电稳定的**，不要删。

## 6. 第四层：运行期 —— 线程怎么跑

### 6.1 两条路径

`Thread<StackSize>` 有两个 `Start` 重载族：

```cpp
// 路径 A：裸任务
void Start(k_thread_entry_t entry, ThreadPrio prio = ThreadPrio::Normal,
           void* p1 = nullptr, const char* name = nullptr);

// 路径 B：受管任务（无周期）
void Start(TaskFunc entry, ThreadPrio prio, void* context, const char* name);

// 路径 C：受管任务（带周期）
void Start(TaskFunc entry, k_timeout_t period, ThreadPrio prio,
           void* context, const char* name);
```

三条最终都走同一个 `Start(k_thread_entry_t, ...)`：

```cpp
void Start(k_thread_entry_t entry, ThreadPrio prio, void* p1, const char* name)
{
    atomic_clear(&paused_);
    name_ = name;

    k_thread_create(&thread_, stack_, K_THREAD_STACK_SIZEOF(stack_),
                    entry, p1, nullptr, nullptr,
                    static_cast<uint8_t>(prio), 0, K_NO_WAIT);
    atomic_set(&started_, 1);

    if (name != nullptr) k_thread_name_set(&thread_, name);

    RegisterThreadInstance(this);
}
```

`K_NO_WAIT` = 立即进入就绪队列，不等线程函数返回。

### 6.2 路径 A：裸任务

```cpp
static void Task(void*, void*, void*)
{
    for (;;)
    {
        k_msleep(10);
        // 业务
    }
}
thread_.Start(Task, ThreadPrio::High, nullptr, "foo");
```

- 入口是 `k_thread_entry_t`（`void(*)(void*,void*,void*)`），Zephyr 原生签名
- 循环、等待、错误处理**全部自己写**
- **不参与统计**：`run_count` 永远是 0
- 仍然会登记到 `thread_registry`，`thread pause/resume` 有效

适用：事件驱动线程（等信号量 / 队列）、需要自维护状态机的线程。

### 6.3 路径 B/C：受管任务

```cpp
static TaskResult Task(void* context)
{
    // 一拍的动作
    return TaskResult::Continue;
}
thread_.Start(Task, K_MSEC(10), ThreadPrio::High, nullptr, "foo");
```

内部先保存参数，再转成路径 A：

```cpp
void Start(TaskFunc entry, k_timeout_t period, ThreadPrio prio,
           void* context, const char* name)
{
    task_    = entry;
    period_  = period;
    context_ = context;

    Start(RunEntry, prio, this, name);   // this 作为 p1 传给外壳
}
```

`RunEntry` 是静态桥接：

```cpp
static void RunEntry(void* p1, void* p2, void* p3)
{
    static_cast<Thread*>(p1)->Run();
}
```

### 6.4 外壳 `Run()`

```cpp
void Run()
{
    for (;;)
    {
        atomic_inc(&run_count_);                     // ① 计数
        const uint64_t begin_cycle = k_cycle_get_64(); // ② 开始时刻

        const TaskResult result = task_(context_);    // ③ 调 Task 一拍

        const uint64_t elapsed = k_cycle_get_64() - begin_cycle; // ④ 耗时
        run_cycles_ += elapsed;
        last_run_cycles_ = elapsed;
        if (elapsed > max_run_cycles_) max_run_cycles_ = elapsed;

        switch (result)                              // ⑤ 结果分派
        {
            case TaskResult::Continue: break;
            case TaskResult::Retry:  atomic_inc(&retry_count_);
                                     if (retry_hook_ == nullptr || !retry_hook_(context_)) {
                                         DefaultHandle(this);
                                     }
                                     break;
            case TaskResult::Exit:   DefaultHandle(this); break;
        }

        if (!K_TIMEOUT_EQ(period_, K_NO_WAIT)) {
            k_sleep(period_);                        // ⑥ 周期等待
        }
    }
}
```

**Task 里不该出现的东西，全部被搬到这里**：

| 原本写在 Task 里 | 现在 |
|---|---|
| `for (;;)` | 外壳的 `for (;;)` |
| `k_msleep(N)` | 外壳的 `k_sleep(period_)` |
| `if (error) { log; return; }` | `return TaskResult::Retry / Exit` |
| 重连逻辑 | Retry 钩子 |
| 运行次数 / 耗时统计 | 外壳自动采集 |

### 6.5 `TaskResult` 三态

```cpp
enum class TaskResult : uint8_t
{
    Continue = 0,   // 本拍成功：等下一拍再调一次
    Retry    = 1,   // 需要重试：先交给 Retry 钩子，处理不了再交给 DefaultHandle
    Exit     = 2,   // 需要退出：跳过 Retry 钩子，直接交给 DefaultHandle 按策略处置
};
```

| 返回值 | 统计 | 是否调钩子 | 后续 |
|---|---|---|---|
| `Continue` | — | 否 | 等周期后重进 |
| `Retry` | `retry_count++` | **是** | 钩子返回 `true` 则重进；`false` 走 `DefaultHandle` |
| `Exit` | — | 否 | 直接走 `DefaultHandle`（`Isolate` 自杀 / `Recover` 全杀） |

`Retry` 与 `Exit` 的最终处置都由 `DefaultHandle` 按 `ThreadFaultPolicy` 决定，差别只在于要不要先给 Retry 钩子一次自救机会。

### 6.6 Retry 钩子

```cpp
using RetryHook = bool (*)(void* context);
```

作为 `Start()` 第 6 个参数传入：

```cpp
thread_.Start(Task, period, prio, context, "foo",
              ThreadFaultConfig{ OnRetry, OnExit, ThreadFaultPolicy::Recover });
```

典型实现（设备掉线重连）：

```cpp
static bool OnRetry(void* ctx)
{
    auto* self = static_cast<MyDriver*>(ctx);

    self->Close();
    for (;;)
    {
        if (self->Open()) return true;   // 重进 Task
        k_msleep(1000);
    }
    return false;                        // 放弃，交给 DefaultHandle 按策略处置
}
```

**契约**：

1. 钩子在**被管理线程自己的上下文**里执行，不要在里面等别的线程
2. 钩子返回 `true` → 重新进入 Task 函数体（**从函数头开始**，不是从出错处继续）
3. 钩子抛不出异常（MCU 关闭了异常），用返回值表达成功/放弃
4. 钩子拿不到错误码，需要错误分类时用 `context` 里的字段传递（见 §8.3）

### 6.7 周期语义

```cpp
if (!K_TIMEOUT_EQ(period_, K_NO_WAIT)) {
    k_sleep(period_);
}
```

- `period_` 有值时：一拍结束到下一拍开始之间睡这么久
- `period_ is K_NO_WAIT`：**完全不睡**，连续调用 Task（`remote` 用这个，节拍由 Task 内部的 `k_sem_take` 决定）
- 周期是**两拍之间的间隔**，不是「固定频率节拍器」——Task 自身耗时会计入总周期

想固定频率（例如严格 1kHz）需要自己算补偿：

```cpp
const int64_t start = k_uptime_get();
Task(...);
const int64_t remain = period_ms - (k_uptime_get() - start);
if (remain > 0) k_msleep(remain);
```

当前外壳不做补偿，`imu` / `remote` 都是「间隔」语义。

### 6.8 运行统计

```cpp
struct ThreadStats
{
    const char* name;            // 线程名
    uint32_t    run_count;       // Task 进入次数
    uint32_t    retry_count;     // Retry 次数
    uint32_t    drop_count;      // 业务自己调的 CountDrop()
    uint64_t    run_ns;          // Task 累计执行时间
    uint64_t    max_run_ns;      // 单次最长
    uint64_t    last_run_ns;     // 最近一次
    uint32_t    stack_unused;    // 栈剩余字节
    bool        running;         // 是否活着
    bool        paused;          // 是否暂停
};
```

**口径**：

- `run_ns` / `max_run_ns` / `last_run_ns` 只测量 **Task 函数体**，不含外壳的 `k_sleep`、不含统计本身
- 时间源 `k_cycle_get_64()`，需要 `CONFIG_TIMER_HAS_64BIT_CYCLE_COUNTER=y`（当前板卡已开）
- 栈剩余量需要 `CONFIG_INIT_STACKS=y` + `CONFIG_THREAD_STACK_INFO=y`（已开），否则返回 0

业务额外指标：

```cpp
thread_.CountDrop();     // drop_count++
```

### 6.9 暂停 / 恢复

```cpp
void Pause()  { k_thread_suspend(&thread_); atomic_set(&paused_, 1); }
void Resume() { k_thread_resume(&thread_); atomic_clear(&paused_); }
```

- 内核级挂起，**栈、局部变量、程序计数器全部保留**
- 恢复后从挂起的那条指令继续
- **风险**：如果被暂停的线程持有互斥量，等它的线程会永久阻塞
- 当前工程只用 `irq_lock` 短临界区（关中断，不会跨调度点），所以安全
- 后续引入 `k_mutex` 时需要重新评估

### 6.10 线程登记表

```cpp
class thread_registry
{
    static constexpr uint8_t kMaxThreads = 16;
    static bool Add(ThreadBase* thread);
    static ThreadBase* At(uint8_t index);
    static uint8_t Count();
    static ThreadBase* Find(const char* name);
};
```

- `ThreadBase` 是非模板基类，让不同 `StackSize` 的 `Thread<>` 能放进同一张表
- `Add` 在 `Thread::Start` 里调用
- `RegisterThreadInstance()` 是个自由函数，定义在 `Init_entry.cpp`——这样 `thread.hpp` 不用 include `thread_registry.hpp`，避免头文件循环依赖
- `static inline` 成员（C++17）：头文件里只有一个实例，不会每个编译单元一份

## 8. 跨拍状态契约

### 8.1 为什么必须放外面

受管任务的 Task **每拍重新进入函数体**。函数内的局部变量每拍都会重新初始化：

```cpp
// 错误：t 永远不会累积
static TaskResult Task(void*)
{
    float t = 0.0f;      // 每拍都归零
    t += 0.01f;          // 永远是 0.01
    ...
}
```

```cpp
// 正确：放函数外
static float t_ = 0.0f;

static TaskResult Task(void*)
{
    t_ += 0.01f;         // 累积
    ...
}
```

### 8.2 放哪里

| 位置 | 写法 | 适用 |
|---|---|---|
| `namespace` 级 `static` | `static float t_ = 0.0f;` | 简单状态 |
| 类成员 | `class Foo { float t_ = 0.0f; }` | 状态多、需要封装 |
| `context` 指针传入 | `Start(Task, period, prio, &obj_, "foo")` | 需要多实例或统一管理 |

### 8.3 用 context 传递错误分类

钩子签名只有 `bool(void*)`，拿不到错误原因。需要区分错误时，用 context 里的字段传：

```cpp
struct Ctx {
    uint8_t last_error;    // 0=none, 1=bus, 2=timeout
};

static Ctx ctx_ {};

static TaskResult Task(void* p)
{
    auto* c = static_cast<Ctx*>(p);
    if (!dev_.Read()) { c->last_error = 2; return TaskResult::Retry; }
    return TaskResult::Continue;
}

static bool OnRetry(void* p)
{
    auto* c = static_cast<Ctx*>(p);
    if (c->last_error == 2) { /* 超时重连路径 */ }
    return dev_.Reopen();
}

thread_.Start(Task, K_MSEC(10), ThreadPrio::High, &ctx_, "foo");
```

### 8.4 重进时的现场

返回 `Retry` 且钩子返回 `true` 之后，Task 从**函数头**重新进入：

```text
Task 第一次调用
  → 读到错误 → return Retry
  → 外壳：retry_count++ → 调钩子
  → 钩子重连成功 → 返回 true
  → 外壳：等一个周期 → 重新调 Task（从函数第一行开始）
```

所以：

- 函数内局部变量**丢失**
- 函数外 static / 类成员 / context 指向的对象**保留**
- 设备句柄如果放在函数外，钩子里可以直接重建

## 9. 常见错误

### 9.1 线程根本没起来

**现象**：日志里没有 `[boot] xxx start`

| 排查点 | 方法 |
|---|---|
| Kconfig 没开 | 看 `build/zephyr/.config` 里 `CONFIG_TRD_XXX` |
| CMake 没写 `if` 块 | 看 `project/thread/CMakeLists.txt` |
| `.cpp` 编了但段里没有 | 看 `build/zephyr/zephyr.map` 搜 `kThreadEntryPtr_` |
| 启动在前面就中止了 | 搜日志 `start fail` |

### 9.2 编译报错 `macro requires 6 arguments`

**现象**：`REGISTER_INIT` 传了 5 个参数

**原因**：宏签名是 `(fn, stage, level, fail, rollback, name)`

**修**：补 `rollback`，没有清理函数就传 `nullptr`

```cpp
// 错
REGISTER_INIT(thread_init, EarlyInit, High, HaltOnFail, "xxx_init");
// 对
REGISTER_INIT(thread_init, EarlyInit, High, HaltOnFail, nullptr, "xxx_init");
```

### 9.3 编译报错 `macro passed 4 arguments, but takes just 3`

**现象**：`REGISTER_THREAD` 参数个数不对

**原因**：线程项**没有 `level`（High/Mid/Low）**，但有 `fail`（HaltOnFail/ContinueOnFail）。这两个枚举名字容易混。

```cpp
// 错：把 level 当第三个参数
REGISTER_THREAD(thread_start, EarlyThread, High, "xxx_start");
// 对：第三个参数是失败策略
REGISTER_THREAD(thread_start, EarlyThread, HaltOnFail, "xxx_start");
```

### 9.4 Task 不启动 / `run` 不涨

**现象**：`thread list` 里 `STATE=running` 但 `RUN=0`

**原因**：用了路径 A（裸任务），没有外壳统计

**修**：改成 `Start(TaskFunc, ...)` 重载

### 9.5 `thread show` 显示 `?`

**原因**：`Start()` 的 `name` 参数传了 `nullptr`

**修**：所有 `Start` 都传名字

### 9.6 线程优先级与业务冲突

`ThreadPrio` 数值越小优先级越高：

| 枚举 | 数值 | 典型用途 |
|---|---|---|
| `Highest` | 1 | 硬实时（极少用） |
| `VeryHigh` | 2 | 紧急响应 |
| `High` | 3 | 控制环、传感器采样 |
| `Normal` | 4 | 一般业务 |
| `Low` | 5 | 心跳、慢速任务 |
| `VeryLow` | 6 | 后台 |
| `Lowest` | 7 | 调试台 |

**注意**：优先级只影响调度竞争，**不能代替初始化顺序**。资源没 ready 就是没 ready，提高优先级救不了。

### 9.7 暂停后无法恢复

**现象**：`thread pause` 后 `thread resume` 没反应

**排查**：

- 确认 `Pause()` 之前线程已经 `Start()`（`started_ == 1`）
- `STATE` 应该是 `paused`；如果显示 `dead`，线程已经退出了，`resume` 无效

static Thread<2048> thread_ {};

/**

static TaskResult Task(void* context)
{

    t_ += 0.01f;

    float ch1 = std::cosh(t_) * 2.0f;

}

| `return TaskResult::Continue` | 正常，等下一拍 |
| `Start(Task, K_MSEC(10), ...)` | 10ms 周期 |
| `REGISTER_INIT(..., nullptr, ...)` | 无清理资源 |
| `REGISTER_THREAD(fn, stage, name)` | 3 参数 |

## 11. 参数速查

### 11.1 `REGISTER_INIT(fn, stage, level, fail, rollback, name)`

| 参数 | 类型 | 说明 |
|---|---|---|
| `fn` | `bool(*)()` | 初始化函数 |
| `stage` | `InitStage` | `PreInit / EarlyInit / MidInit / LateInit / AppInit` |
| `level` | `InitLevel` | `High / Mid / Low`，同阶段执行顺序 |
| `fail` | `StartFailPolicy` | `HaltOnFail / ContinueOnFail` |
| `rollback` | `void(*)()` 或 `nullptr` | 失败回滚 |
| `name` | 字符串字面量 | 日志标识 |

### 11.2 `REGISTER_THREAD(fn, stage, fail, name)`

| 参数 | 类型 | 说明 |
|---|---|---|
| `fn` | `bool(*)()` | 启动函数，创建线程后立即返回 |
| `stage` | `ThreadStage` | `PreThread / EarlyThread / MidThread / LateThread / AppThread` |
| `fail` | `StartFailPolicy` | `HaltOnFail` 中止后续启动 / `ContinueOnFail` 继续 |
| `name` | 字符串字面量 | 日志标识 |

**注意**：第三个参数是**失败策略**，不是等级。线程项没有 `InitLevel`。

### 11.2b `Start(...)` 的 `ThreadFaultConfig` 参数

故障配置不是注册宏，而是 `Start()` 的第 6 个参数（带默认值）：

```cpp
thread_.Start(Task, K_MSEC(10), ThreadPrio::High, ctx, "foo",
              ThreadFaultConfig{ OnRetry, OnExit, ThreadFaultPolicy::Recover, false });
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `retry` | `bool(*)(void*)` 或 `nullptr` | Retry 钩子 |
| `exit` | `void(*)(void*)` 或 `nullptr` | 亡语 |
| `policy` | `ThreadFaultPolicy` | `Isolate` 自杀 / `Recover` 全杀 |
| `keep_alive` | `bool` | `Recover` 全杀时是否保留（只有 shell 为 `true`） |

不传即全默认（`{}` = 无钩子 + `Recover` + 不保留）。

### 11.3 `Thread<StackSize>`

| 项 | 说明 |
|---|---|
| `StackSize` | 栈字节数，编译期常量 |
| 实例 | 静态对象，**不可拷贝**（有虚函数） |
| RAM | 栈 + ≈72 B 管理字段 |

### 11.4 `Start` 重载对照

| 写法 | 入口类型 | 循环 | 统计 |
|---|---|---|---|
| `Start(void(*)(void*,void*,void*), prio, p1, name)` | 裸任务 | 自己写 | 无 |
| `Start(TaskFunc, period, prio, ctx, name)` | 受管，周期 | 外壳 | 有 |

### 11.5 shell 命令

| 命令 | 作用 |
|---|---|
| `thread list` | 全部线程：状态 / run / retry / fatal / drop / 栈剩余 |
| `thread show <name>` | 单线程详情：含 last / max / total 耗时 |
| `thread pause <name>` | 暂停（保留现场） |

## 12. 设计要点回顾

### 12.1 为什么错误处理从 Task 里剥离

传统写法：

```cpp
void Task(void*, void*, void*)
{
    for (;;)
    {
        if (!dev.Read()) {
            DUST_LOG_ERR("read fail");
            dev.Close();
            for (int i = 0; i < 3; i++) {
                k_msleep(1000);
                if (dev.Open()) break;
            }
            continue;
        }
        process();
        k_msleep(10);
    }
}
```

问题：

1. **每个线程都要重复写同一套重连逻辑**
2. **错误处理与业务交织**，代码读起来是「业务—错误—业务—错误」
3. **统计无处安放**：想加一个「这个线程跑了多少次」，得改每个 Task

受管任务的结构：

```cpp
static TaskResult Task(void* ctx)      // 只有业务
{
    if (!dev.Read()) return TaskResult::Retry;
    process();
    return TaskResult::Continue;
}

static bool OnRetry(void* ctx)         // 只有重连
{
    dev.Close();
    while (!dev.Open()) k_msleep(1000);
    return true;
}
```

**职责分离**：Task 只管「这一拍做什么」，错误分类靠返回值，恢复策略在钩子里，统计和周期在外壳。

### 12.2 为什么用返回值而不是异常

| | 异常 | 返回值 |
|---|---|---|
| Zephyr 默认 | `-fno-exceptions`，编译不过 | 支持 |
| 开销 | unwinder 表进 flash + 栈展开 | 一次函数返回 |
| ISR 中 | 不能抛 | 无限制 |
| 可读性 | `catch` 可以离 `throw` 很远 | 必现于调用点 |

要开异常需要 `CONFIG_CPP_EXCEPTIONS=y`，代价是 flash 和 RAM。MCU 上不划算。

### 12.3 为什么 `REGISTER_THREAD` 不带 stop/join

早期设计曾给线程注册项加 `stop` / `join` 回调，用于系统级收尾。后来确认：

- MCU 没有「进程退出」语义，运行期不存在停机
- 没有任何调用者，等于死代码

于是删除。线程控制改为 `Pause` / `Resume`（保留现场），通过 `thread pause/resume` 命令使用。

### 12.4 为什么 `rollback` 只在初始化失败时用

`InitEntry.rollback` 的语义是「本项初始化失败时，把已经申请到一半的资源还回去」。

- **不用于**正常运行期（没有停机流程）
- **不用于**线程退出（线程常驻）

所以只有 `buzzer`（关 PWM）和 `flash`（进掉电模式）有真实实现，其余传 `nullptr`。
