## 一、阅读范围与比较方法

### 1.1 比较对象

本文比较四个当前工作区中具有代表性的项目：

```text
temp/basic_framework-master
temp/COD_H7_Template_CLion-main
temp/Dust_SentinelRobot_L_Game
当前仓库 tflm
```

此前所说的 `temp/COD-H7`，在当前工作区中的实际目录名是：

```text
temp/COD_H7_Template_CLion-main
```

后文统一使用 `COD_H7` 作为简称。

### 1.2 本次为什么要重写比较方式

旧版对比主要关注：

- `bsp / module / app`；
- 固定任务；
- Robot 总控；
- `project/`；
- Kconfig/CMake；
- 消息中心。

这些内容仍然重要，但已经不足以描述当前 `tflm`。

现在的 `tflm` 不是简单增加了几个目录，而是把不同层的责任进一步明确了：

```text
drivers
    硬件访问和异步传输

modules
    设备能力和设备状态

algorithm
    纯计算和状态更新

topic
    线程间数据契约

project
    板级装配、启动和业务线程

cmd
    横切型运行期辅助执行

scripts
    主机侧实验、回放和验证
```

此外，`drivers/usb` 和 `cmd/` 都不是普通目录：

```text
drivers/usb
    不是普通的单一外设包装
    而是外部 USB 协议栈与项目 Stream 的桥接层

cmd
    不是普通的业务模块
    而是可以被多层调用的运行期控制面
```

如果仍然只用“层数越多越复杂”来评价，就会把这些有意设计的特殊边界误判成架构混乱。

因此本文使用三条主线比较：

1. **系统组织中心**：项目到底围绕什么组织；
2. **职责边界**：变化应该被限制在哪一层；
3. **特殊机制**：线程、USB、调试、消息和编译装配如何归属。

### 1.3 本文关注的不是目录数量

一个目录是否有价值，不取决于它是否看起来独立，而取决于它是否拥有稳定责任。

比较一个嵌入式框架时，真正应该问：

```text
谁拥有硬件访问？
谁拥有设备状态？
谁拥有控制周期？
谁拥有跨模块策略？
谁定义线程间数据？
谁负责项目差异？
谁负责运行期调试？
谁负责主机侧实验？
```

如果这些问题都能得到稳定答案，分层才是真正成立。

### 1.4 五个统一评价维度

为了避免四个项目各用一套标准，本文统一观察以下五个维度。

#### 维度一：系统组织中心

项目主要围绕什么组织：

- 层级和实例；
- 单板外设；
- Robot 对象；
- 项目装配；
- 消息契约；
- 运行期控制面。

#### 维度二：职责边界

关注：

- 驱动是否只做硬件访问；
- 设备模块是否只做设备能力；
- 算法是否保持计算独立；
- 线程是否拥有明确业务责任；
- 项目差异是否集中；
- 特殊基础设施是否有清晰归属。

#### 维度三：编译和运行装配

关注：

- 是否能按功能裁剪；
- 是否能按板卡切换；
- 初始化是否集中或注册；
- 线程是否固定或本地装配；
- 依赖是否由构建系统表达。

#### 维度四：迁移和维护

关注：

- 换板子需要改什么；
- 换设备需要改什么；
- 换协议需要改什么；
- 新增功能是否会牵动旧代码；
- 后来者是否能沿着边界继续维护。

#### 维度五：真实业务闭环

关注：

- 输入；
- 设备采集；
- 状态估计；
- 目标生成；
- 控制计算；
- 输出通信；
- 故障保护；
- 整机策略。

业务闭环和平台化能力必须分开评价。

## 二、先给结论

### 2.1 四个项目的一句话定位

| 项目 | 最准确的定位 |
| --- | --- |
| `basic_framework-master` | 以 `bsp / module / app`、实例和消息契约为中心的队伍级 STM32 基础框架 |
| `COD_H7` | 以 STM32H723、CubeMX、FreeRTOS、固定任务和 C 组件为中心的单板电控模板 |
| `Dust_SentinelRobot_L_Game` | 以 `Robot` 对象、设备拓扑和总控任务为中心的具体机器人整机工程 |
| `tflm` | 以职责分层、项目装配、配置裁剪和注册机制为中心的 Zephyr 模块化平台 |

### 2.2 四种不同的系统组织中心

```text
basic_framework-master
    -> 层级、实例、消息契约和队伍规则

COD_H7
    -> 单板外设、固定任务和 C 组件

Dust
    -> 整机对象、设备拓扑和总控策略

tflm
    -> 框架层职责、项目装配和编译期注册
```

它们分别优先回答：

```text
如何让队伍长期复用？
如何从一块 H7 控制板快速开始？
如何把一台机器人真正做完整？
如何让新项目主要修改 project/？
```

### 2.3 如果只评价框架架构能力

按当前代码快照，我会给出：

```text
tflm
    >
basic_framework-master
    >
COD_H7
    >
Dust_SentinelRobot_L_Game
```

这条排序主要依据：

- 层职责是否稳定；
- 项目差异是否有明确归属；
- 编译期是否可以裁剪；
- 初始化和注册是否可以扩展；
- 新功能是否容易限制修改范围；
- 维护者是否能从边界进入系统。

### 2.4 如果只评价单台比赛整机

排序应该是：

```text
Dust_SentinelRobot_L_Game
    >
basic_framework-master
    >
tflm
    >
COD_H7
```

原因：

- Dust 已经将一台机器人的输入、设备、控制和策略连成完整闭环；
- basic 已经有成熟的机器人应用和模块底座；
- tflm 的平台边界更强，但具体整机仍在持续装配；
- COD_H7 当前更接近控制板模板和控制骨架。

### 2.5 最短结论

- `basic_framework-master` 把经验整理成了队伍规则。
- `COD_H7` 把单板能力整理成了可复用模板。
- `Dust` 把设备和策略整理成了一台能工作的机器人。
- `tflm` 把这些经验进一步拆成了框架层、项目层和运行期工具。

## 三、当前 tflm 的真实架构

### 3.1 tflm 不是“所有层都长得一样”

当前 `tflm` 的层不是简单的平行目录。

它们承担的责任不同，运行方式也不同：

```text
drivers
    面向硬件访问

modules
    面向设备能力

algorithm
    面向纯计算

topic
    面向数据契约

project
    面向项目装配和业务线程

cmd
    面向运行期控制、提示和持久化

scripts
    面向主机侧实验和验证
```

这意味着“分层”不要求每一层都满足同一种形式规则。

例如：

- `algorithm` 和 `topic` 不创建线程；
- `modules` 中 IMU 和 Remote 可以拥有线程；
- `drivers` 不创建业务线程；
- `cmd/shell` 可以拥有独立线程；
- `drivers/usb` 可以桥接一个外部协议栈。

这些不是规则互相打架，而是每一层解决的问题不同。

### 3.2 当前 tflm 的完整关系

```text
board overlay / SoC / device tree
                ↓
drivers
    GPIO / PWM / SPI / CAN / UART / RS485 / USB Stream
                ↓
modules
    IMU / Remote / Motor / PowerMeter
                ↓
algorithm
    PID / EKF / Filter / RLS / PowerCtrl / TFLM
                ↓
topic
    imu_to / remote_to / to_can_tx
                ↓
project
    apps / boards / thread
                ↓
具体机器人业务
```

旁路的运行期工具是：

```text
cmd
    shell 调试变量
    buzzer 状态提示
    flash 持久化
    linker 注册段
```

主机侧验证是：

```text
scripts
    采集
    回放
    辨识
    拟合
    性能分析
```

### 3.3 每层回答的问题

| 层 | 它回答的问题 |
| --- | --- |
| `drivers/` | 如何访问硬件和异步传输 |
| `modules/` | 一个设备如何变成稳定能力 |
| `algorithm/` | 数据如何被计算、滤波和估计 |
| `topic/` | 线程之间传什么，语义是什么 |
| `project/` | 当前项目用哪些板、设备、线程和业务 |
| `cmd/` | 运行时如何调试、提示和持久化 |
| `scripts/` | 如何在主机上验证和辨识 |

### 3.4 tflm 的边界不是“绝对隔离”

低耦合不等于所有层之间没有任何关系。

当前合理的关系包括：

```text
modules -> drivers
modules -> algorithm
modules -> topic
project -> drivers
project -> modules
project -> algorithm
project -> topic
project -> cmd
scripts -> 固件输出和硬件接口
```

需要避免的是反向业务依赖：

```text
drivers -X-> chassis
algorithm -X-> project/thread
topic -X-> 具体设备实例
modules -X-> 某个具体机器人策略
```

USB 和 cmd 的“特殊”也不是无边界。

它们仍然要服从一个原则：

> 特殊机制可以跨越普通目录边界，但必须拥有明确的所有权和调用接口。

## 四、四个项目的整体画像

### 4.1 组织方式总表

| 对比项 | `basic_framework-master` | `COD_H7` | `Dust` | `tflm` |
| --- | --- | --- | --- | --- |
| 主要语言 | C | C | C/C++，以 C++ 为主 | C/C++ |
| 运行时 | STM32 HAL + FreeRTOS | STM32 HAL + FreeRTOS | STM32 HAL + FreeRTOS | Zephyr |
| 组织中心 | 层级、实例、消息 | 单板、任务、组件 | Robot、成员对象、总控 | 层职责、项目、注册项 |
| 初始化 | 集中式 `RobotInit` | `main` + `MCU_Init` + `freertos.c` | `Init` + 对象自建任务 | `.user_init` 阶段遍历 |
| 任务创建 | 集中任务初始化 | `freertos.c` 集中创建 | 对象初始化时分散创建 | 项目和模块按职责注册 |
| 应用通信 | `message_center` | 全局状态和直接包含 | 成员对象直接读写 | zbus、k_msgq、接口调用 |
| 硬件抽象 | BSP + 实例 | BSP + HAL + 全局设备 | 具体对象 + 设备 ID | drivers + DTS + modules |
| 调试工具 | 应用或 BSP 内实现 | 任务和全局变量 | 工程内业务工具 | 独立 `cmd` 横切层 |
| USB 位置 | 工程/BSP 关联 | CubeMX USB Device | 通信和设备工程内 | drivers Stream + 外部 USB 栈 |
| 编译裁剪 | 宏和工程约定 | 固定目录和手工配置 | 复制工程后改造 | Kconfig + CMake |
| 项目差异 | `app`、参数和宏 | 单板工程内部 | Robot 和设备拓扑 | `project/` |
| 当前强项 | 队伍传承 | 单板快速启动 | 整机闭环 | 平台边界和项目迁移 |

### 4.2 四个项目不在同一抽象层级

`basic_framework-master` 更接近队伍 SDK。

`COD_H7` 更接近控制板模板。

`Dust` 更接近具体产品工程。

`tflm` 更接近平台中的项目单元。

因此不能直接问“哪个目录更干净”。

应该先问：

```text
这个项目是在优化下一个赛季？
下一块控制板？
当前机器人？
还是多个项目之间的公共能力？
```

### 4.3 复杂度被放在了不同位置

#### basic

复杂度主要放在：

- 分层规则；
- 实例注册；
- `message_center`；
- 多板切换；
- 任务频率约定；
- 文档和队伍纪律。

#### COD_H7

复杂度主要放在：

- CubeMX 外设；
- BSP 回调；
- 全局设备对象；
- 固定任务；
- CAN/UART 拓扑；
- 组件间头文件依赖。

#### Dust

复杂度主要放在：

- `Robot` 成员对象；
- 设备 ID 和回调分发；
- 跨模块策略；
- 对象内部任务；
- 整机模式和故障处理。

#### tflm

复杂度主要放在：

- Kconfig；
- CMake；
- DTS 和 board；
- 初始化注册；
- topic；
- 设备模块；
- cmd 特殊执行层；
- 外部 USB 模块装配。

这也是为什么 tflm 初次阅读成本可能更高。

它把原来隐藏在工程文件、全局对象和作者经验中的关系显式化了。

## 五、basic_framework-master：队伍级基础框架

### 5.1 定位

`basic_framework-master` 的第一目标是长期复用和团队传承。

它不是围绕一台具体机器人，而是围绕多个机器人和多个赛季共同需要的底座。

它的核心组织方式是：

```text
bsp
    ↓
module
    ↓
application
```

应用之间再通过消息中心交换数据。

### 5.2 它如何理解“层”

在 basic 中，目录层级本身就是开发规则：

```text
BSP
    板级硬件

Module
    可复用设备和功能

Application
    具体机器人行为
```

它用文档、命名和目录约定维持依赖方向。

这套思路对 STM32/HAL/FreeRTOS 项目很有效，因为它解决了很多团队项目最容易失控的问题：

- 所有代码都塞在 `Core/Src`；
- 每个人使用不同的初始化习惯；
- 应用互相直接包含；
- 新人找不到系统入口；
- 多机器人参数散落在多个文件；
- 模块无法稳定复用。

### 5.3 消息中心的价值

basic 的 `message_center` 是它最有代表性的边界。

典型关系是：

```text
robot_cmd
    -> chassis_cmd
    -> gimbal_cmd
    -> shoot_cmd

chassis
    -> chassis_feed

gimbal
    -> gimbal_feed

shoot
    -> shoot_feed
```

应用之间依赖消息结构，而不是直接持有对方对象。

这使得：

- 底盘不必包含云台；
- 云台不必包含发射；
- `robot_cmd` 不必知道所有对象布局；
- 不同成员可以围绕消息契约并行开发。

### 5.4 它的优势

#### 队伍规则成熟

它把代码规范、任务、分层、消息和文档放在一起考虑。

#### 多机器人复用意识强

通过参数和板卡角色切换，可以服务多种机器人。

#### 应用边界清楚

底盘、云台、发射和机器人指令拥有相对稳定的职责。

#### 传承成本较低

新人可以沿着：

```text
README
    -> 架构文档
        -> robot.c
            -> app
                -> module / bsp
```

进入系统。

### 5.5 它的局限

#### 平台仍然绑定 STM32 生态

它的跨项目能力主要发生在：

```text
STM32
    + HAL
    + CubeMX
    + FreeRTOS
```

内部，而不是跨 RTOS、跨芯片族的平台。

#### 编译期边界不够强

很多规则依赖：

- 宏；
- 命名；
- 目录；
- 开发纪律；
- 人工维护。

编译器不会完整阻止错误依赖。

#### 消息机制需要持续维护

随着项目增大，需要关注：

- 队列容量；
- 数据覆盖；
- 并发保护；
- 消息生命周期；
- 注册顺序；
- 状态和事件的区分。

### 5.6 它适合什么

适合：

- 队伍级基础平台；
- 多机器人共底座；
- 多成员协作；
- STM32/HAL/FreeRTOS；
- 需要长期传承的项目。

不一定适合：

- 跨 RTOS 平台；
- 需要大量编译期裁剪；
- 需要外部协议栈独立装配；
- 只想快速验证一块新板。

### 5.7 一句话评价

> `basic_framework-master` 最强的地方，是把队伍经验整理成了分层、消息、参数和文档规则。

## 六、COD_H7：STM32H7 单板电控模板

### 6.1 定位

`COD_H7` 面向 STM32H723 高性能控制板。

它的第一目标是：

```text
把一块 H7 控制板的外设、设备、算法和任务骨架提前准备好
```

它不是以跨芯片平台为目标，也不是以某一台完整机器人为目标。

### 6.2 目录组织

典型结构是：

```text
Core/
    CubeMX 生成的初始化

Drivers/
    HAL、CMSIS

Middlewares/
    FreeRTOS、USB Device、DSP

USER/
├── BSP/
├── Components/
│   ├── Device/
│   ├── Controller/
│   └── Algorithm/
└── Application/Task/
```

它已经比普通 CubeMX 工程更有组织性。

但需要注意：

```text
目录分区
    不等于
编译依赖和运行时职责已经完全隔离
```

### 6.3 启动模型

COD_H7 的启动主要由：

```text
main.c
    -> HAL / 时钟 / CubeMX 外设
        -> MCU_Init()
            -> BSP / USB / BMI088 等初始化
                -> MX_FREERTOS_Init()
                    -> osKernelStart()
```

`MCU_Init()` 同时涉及：

- 板级能力；
- 外设；
- USB；
- 具体设备。

所以它的边界更像：

```text
单板初始化中心
```

而不是：

```text
框架层和项目层分离的启动装配器
```

### 6.4 任务模型

`freertos.c` 集中创建固定任务：

```text
INS_Task
Control_Task
CAN_Task
Detect_Task
```

这种模型的优势是直接：

- 任务清单集中；
- 优先级集中；
- 栈空间集中；
- 第一次接手容易定位。

代价是：

- 新增任务要修改中心文件；
- 任务是否参与编译主要靠手工调整；
- 任务和全局状态容易形成强依赖；
- 项目变复杂后，`freertos.c` 成为集中装配点。

### 6.5 设备和算法组织

COD_H7 已经有：

- BMI088；
- DJI/DM 电机；
- 遥控器；
- 裁判系统；
- PID；
- LPF；
- Kalman；
- Quaternion；
- RLS；
- Ramp；
- CRC。

这些能力在单板工程内复用很方便。

但是很多数据路径仍然是：

```text
中断回调
    -> 全局状态
        -> 任务直接读取
```

或者：

```text
Control_Task
    -> 直接包含设备和控制头文件
```

它的优势是路径短。

它的代价是边界更多依赖作者约定。

### 6.6 USB 在 COD_H7 中的位置

COD_H7 使用 CubeMX 生成的 USB Device 和 CDC 相关代码。

USB 更接近：

```text
CubeMX / Middleware / USER 应用
```

它没有当前 tflm 这种：

```text
drivers/usb Stream 适配
    + 外部 UsbDevPort
    + 外部 UsbHalHpm
    + CDC 配置
```

的独立边界。

这不代表 COD_H7 的 USB 不完整。

它代表的是另一种工程选择：

```text
USB 作为当前单板工程的一部分被集成
```

而 tflm 更强调：

```text
USB 协议栈和项目通信接口可以分别演进
```

### 6.7 它的优势

- H7 外设覆盖完整；
- FDCAN、UART DMA、SPI、USB、PWM、ADC 都比较容易开始；
- CMake、Ninja、CLion 工具链体验较好；
- 设备、控制器、算法、任务目录已经形成基本分区；
- 固定任务对单板联调很直接。

### 6.8 它的局限

- 绑定 STM32H723；
- 任务集合固定；
- 全局状态较多；
- BSP 和设备初始化有穿透；
- 缺少明确 topic 契约；
- 缺少独立项目装配层；
- 依赖和功能裁剪主要靠工程结构和人工修改。

### 6.9 一句话评价

> `COD_H7` 是一套硬件覆盖完整、适合快速搭建 H7 电控项目的单板模板，但还不是配置驱动的跨项目框架。

## 七、Dust：具体机器人整机工程

### 7.1 定位

Dust 的第一目标是把一台真实机器人做完整。

它围绕：

```text
Robot
    -> McuComm
    -> Chassis
    -> Gimbal
    -> Reload
    -> Imu
    -> Supercap
    -> Referee
```

组织整机。

它的核心问题不是：

```text
如何让下一个项目只修改 project/
```

而是：

```text
这台机器人现在应该怎么运行？
```

### 7.2 组织中心是 Robot 对象

Dust 的 `Robot` 对象拥有整机主要成员。

这让跨模块策略非常直接：

```text
Robot::Task()
    -> 读取 McuComm
    -> 判断裁判系统
    -> 判断遥控器
    -> 设置 Gimbal
    -> 设置 Chassis
    -> 设置 Reload
```

对于一台具体机器人，这种写法非常有效。

读者可以沿着 Robot 找到整机关系。

### 7.3 任务模型

Dust 的功能对象往往在自己的 `Init()` 中创建线程：

```text
Chassis::Init()
    -> chassis_task

Gimbal::Init()
    -> gimbal_task

Reload::Init()
    -> reload_task

Imu::Init()
    -> ImuTask
```

这贴近 C++ 对象模型：

```text
对象拥有状态
对象拥有初始化
对象拥有任务
对象拥有运行方法
```

优点是功能对象完整。

代价是任务创建点分散，系统任务清单不再集中。

### 7.4 通信和设备拓扑

Dust 的 CAN 接收通常直接按 ID 分发到具体对象：

```text
CAN1
    -> 0x201
        -> chassis motor

CAN2
    -> 0x07
        -> gimbal motor

CAN2
    -> 0x30
        -> supercap
```

这种链路非常短：

```text
CAN 回调
    -> 具体对象
        -> Robot 直接读取
```

它适合快速联调和问题定位。

但设备 ID、设备归属和业务对象绑定较深。

### 7.5 USB 和调试工具的位置

在 Dust 这类具体整机工程里，通信工具通常更容易直接进入：

- Communication；
- Bsp；
- Interaction；
- Robot；
- 具体任务。

因为项目第一目标是快速闭环。

这和 tflm 的 `cmd` 设计不同：

```text
Dust
    更容易把辅助能力放进整机工程内部

tflm
    把调试、提示、持久化抽成跨项目工具层
```

### 7.6 它的优势

- 整机业务闭环最强；
- 设备拓扑直观；
- 总控策略集中；
- 控制链路径短；
- 真实故障和保护逻辑丰富；
- 适合比赛中快速联调和迭代。

### 7.7 它的局限

- `Robot` 容易变重；
- 多模块策略集中在总控；
- 设备 ID 和当前机器绑定；
- 新机器人迁移时需要重组对象拓扑；
- 目录分区有帮助，但依赖最终仍要沿代码理解；
- 不以跨项目公共层为第一目标。

### 7.8 一句话评价

> Dust 最像一台机器人沉淀出来的产品工程，整机闭环最强，但它的复用边界主要围绕当前机器人。

## 八、tflm：项目装配型平台

### 8.1 定位

当前 `tflm` 的目标不是简单地把机器人做出来，而是把不同项目中反复出现的能力逐渐沉淀成稳定层。

它希望做到：

```text
换板子
    -> 主要改 project/boards

换项目
    -> 主要改 project/thread 和 project/apps

换设备
    -> 增加或替换 modules 实现

换算法
    -> 替换 algorithm

换线程通信
    -> 调整 topic

做实验
    -> 使用 project/thread/test 和 scripts
```

### 8.2 当前层职责

#### drivers

硬件访问和异步传输：

- GPIO；
- PWM；
- SPI；
- CAN；
- UART DMA；
- RS485；
- USB Stream 适配。

#### modules

设备能力：

- IMU；
- Remote；
- Motor；
- PowerMeter。

模块可以根据运行模型拥有线程：

```text
IMU
    周期采样、温控和姿态

Remote
    UART 流接收、协议探测和发布
```

但被动 CAN 设备不创建线程：

```text
Motor / PowerMeter
    回调更新 + 快照读取
```

#### algorithm

纯计算：

- PID；
- 滤波；
- EKF；
- 四元数；
- RLS；
- 功率控制；
- TFLM。

算法不持有 UART、SPI、PWM、CAN 等硬件对象。

#### topic

数据契约：

- IMU 状态；
- Remote 状态；
- CAN TX 帧；
- zbus；
- k_msgq。

Topic 不拥有设备实例，也不创建线程。

#### project

项目装配：

- 启动；
- 板级 overlay；
- Kconfig；
- 业务线程；
- 设备实例；
- 项目参数；
- 整机策略。

#### cmd

运行期辅助执行：

- shell 调试变量；
- buzzer 启动提示和错误停机；
- W25Q128 Flash；
- 分区布局；
- 链接段支持；
- 构建脚本。

#### scripts

主机侧验证：

- 温控辨识；
- IMU 回放；
- PID 扫描；
- UART 性能；
- 阶段拟合；
- 数据分析。

### 8.3 tflm 的启动模型

当前入口是：

```text
src/main.c
    -> System_Startup()
        -> RunStage(PreInit)
        -> RunStage(PreThread)
        -> RunStage(EarlyInit)
        -> RunStage(EarlyThread)
        -> RunStage(MidInit)
        -> RunStage(MidThread)
        -> RunStage(LateInit)
        -> RunStage(LateThread)
        -> RunStage(AppInit)
        -> RunStage(AppThread)
```

组件在自己的 `.cpp` 里写：

```cpp
REGISTER_INIT(thread_init, MidInit, Mid, "chassis_init");
REGISTER_INIT(thread_start, MidThread, Mid, "chassis_start");
```

然后由 linker 收集到 `.user_init`。

这使启动项不需要集中追加到 `main.c`。

### 8.4 tflm 的特殊机制不是分层失败

当前 tflm 有两个明显特殊点：

```text
drivers/usb
    通过 Stream 适配外部 USB 协议栈

cmd
    作为横切运行期工具层
```

它们看起来不像普通的“纯一层”，但它们的责任仍然清楚。

特殊边界的意义是把复杂度放在正确的所有者中，而不是把所有代码都塞进普通层。

## 九、启动与运行时模型对比

### 9.1 basic：集中编排

典型形式：

```text
main
    -> RobotInit
        -> 各模块初始化
        -> 任务创建
            -> FreeRTOS
```

优点：

- 入口集中；
- 阅读顺序短；
- 任务清单容易查看；
- 适合固定工程。

代价：

- 新增组件要修改中心文件；
- 装配点容易变成集中式大文件；
- 初始化关系主要靠人工维护。

### 9.2 COD_H7：CubeMX 加固定任务

典型形式：

```text
main.c
    -> HAL / 外设
        -> MCU_Init
            -> MX_FREERTOS_Init
                -> 固定四任务
```

优点：

- 对单板非常直接；
- 任务优先级和栈集中；
- CubeMX 与用户初始化链清楚。

代价：

- 任务数量和职责固定；
- 设备初始化和 BSP 容易穿透；
- 改项目时往往复制工程。

### 9.3 Dust：对象拥有任务

典型形式：

```text
main
    -> Init
        -> Robot.Init
            -> 每个对象 Init
                -> 对象创建自己的线程
```

优点：

- 对象完整；
- 设备和任务靠近；
- 当前整机调试直观。

代价：

- 任务创建点分散；
- Robot 和对象之间耦合高；
- 迁移时需要重组对象拓扑。

### 9.4 tflm：注册式阶段启动

典型形式：

```text
组件本地实现
    -> REGISTER_INIT
        -> .user_init
            -> System_Startup 遍历
```

优点：

- 新增初始化项不扩大中心入口；
- 阶段、失败等级、名字一起声明；
- 模块和项目可以本地拥有启动实现；
- Kconfig 关闭后初始化项自然消失。

代价：

- 链接段和阶段机制需要学习；
- 条目执行顺序必须有明确规则；
- 失败策略和依赖关系需要文档化；
- 初次阅读不如集中式初始化直观。

### 9.5 四者的核心差异

```text
basic
    先建整机骨架，再运行应用

COD_H7
    先由 CubeMX 建立单板，再创建固定任务

Dust
    初始化对象时让对象拥有任务

tflm
    组件本地注册，启动器按阶段装配
```

## 十、编译期装配与配置裁剪对比

### 10.1 basic

主要依赖：

- 宏；
- 头文件；
- 工程配置；
- 目录约定；
- 手工选择源文件。

它的优点是简单。

它的代价是配置容易散落。

### 10.2 COD_H7

主要依赖：

- CubeMX 工程；
- CMake；
- 固定用户目录；
- `Config.h`；
- 手工维护任务和组件。

CMake 提供了较好的工具链体验，但还不是以 Kconfig 选择模块为核心。

### 10.3 Dust

主要依赖：

- 完整工程复制；
- CMake 源文件收集；
- 设备对象和 ID；
- 当前机器人业务。

更像：

```text
复制一套能工作的产品工程
    -> 按新机器人改造
```

### 10.4 tflm

主要依赖：

- Kconfig；
- CMake；
- DTS；
- board overlay；
- `REGISTER_INIT`；
- `.user_init`；
- `.imu`；
- `.remote`；
- `.shell_var`；
- `.can_rx1/2/3`。

典型链路：

```text
Kconfig
    -> select 功能和依赖
        -> CMake 加入源文件
            -> linker 收集注册项
                -> 启动器或运行时遍历
```

这使配置、编译、链接和运行时形成一条完整链路。

### 10.5 评价

在编译期装配能力上：

```text
tflm
    >
basic_framework-master
    >
COD_H7
    >
Dust
```

但编译期机制越强，学习成本也越高。

因此 tflm 需要把：

- Kconfig 入口；
- CMake 入口；
- board 目录；
- linker 段；
- 初始化阶段；

写得足够清楚。

## 十一、层职责和特殊边界对比

### 11.1 basic 的职责模型

basic 的核心职责模型是：

```text
bsp
    硬件基础

module
    设备和公共能力

app
    机器人行为
```

它的边界优势来自规则和文档。

### 11.2 COD_H7 的职责模型

COD_H7 的核心职责模型是：

```text
Core / Drivers
    芯片和 HAL

USER/BSP
    板级能力

USER/Components
    设备、控制器和算法

USER/Application/Task
    固定任务
```

它的边界优势来自功能分区。

但很多运行时依赖仍然通过全局对象和直接包含连接。

### 11.3 Dust 的职责模型

Dust 的核心职责模型是：

```text
Bsp / Communication
    外设和通信

Device / Modules
    设备对象

Interaction / Robot
    整机对象和业务策略
```

它的边界优势来自整机对象拓扑。

### 11.4 tflm 的职责模型

tflm 现在更接近：

```text
drivers
    硬件访问

modules
    设备能力

algorithm
    纯计算

topic
    数据契约

project
    项目装配和业务线程

cmd
    运行期辅助执行

scripts
    主机侧验证
```

它的边界优势不只是目录，而是每层对变化的归属。

### 11.5 “特殊”不代表“没有边界”

`drivers/usb` 和 `cmd` 看起来都跨越了普通层级，但两者的特殊原因不同。

```text
drivers/usb
    复杂度来自外部 USB 协议栈、硬件 HAL 和 Stream 适配的组合

cmd
    复杂度来自运行期调试、提示、持久化和可选能力的横切性
```

USB 是“基础设施桥接特殊”。

cmd 是“运行期控制面特殊”。

不能把它们混为普通设备模块，也不能因为特殊就让它们随意依赖业务。

## 十二、设备、线程和数据通信对比

### 12.1 basic

设备通常以实例形式进入 module，再由 app 组合。

应用之间使用 message center。

线程更多由应用和统一任务初始化管理。

### 12.2 COD_H7

设备通常通过全局数组或全局对象暴露给任务。

中断回调直接更新全局状态。

任务之间通过直接包含和全局结构体交互。

这种路径短，调试快，但数据所有权需要人工维护。

### 12.3 Dust

设备对象属于 Robot 或其成员。

CAN 回调按 ID 直接分发到成员对象。

对象初始化时可以创建自己的线程。

跨模块策略集中在 Robot 或 Interaction 层。

### 12.4 tflm

tflm 把数据路径拆成几种形式：

#### 设备回调和快照

适合 Motor、PowerMeter：

```text
CAN 回调
    -> 更新对象状态
        -> seqlock
            -> project/thread ReadAll()
```

#### 模块内部线程

适合 IMU、Remote：

```text
驱动数据
    -> 模块线程
        -> 设备状态机
            -> topic
```

#### topic

适合跨线程状态和队列：

```text
Remote
    -> remote_to
        -> chassis / gimbal
```

```text
chassis / gimbal
    -> to_can_tx
        -> CAN TX thread
```

#### 直接接口

适合项目线程调用算法和设备对象：

```text
chassis thread
    -> motor.ReadAll()
    -> PID.Calc()
    -> power_ctrl.Allocate()
```

### 12.5 tflm 的线程规则更细

当前 tflm 不是“模块都不能有线程”，也不是“所有对象都自己有线程”。

它采用：

```text
主动产生连续数据
    -> 模块可以拥有线程

被动响应硬件事件
    -> 回调 + 快照

多个设备共同决策
    -> project/thread
```

这比统一规定“线程只能在某一层”更接近实际设备运行模型。

## 十三、USB 与 cmd 的特殊性

这是当前四个项目比较中最需要单独说明的一部分。

### 13.1 为什么普通 drivers 和 USB 不一样

GPIO、PWM、SPI、CAN 的典型职责是：

```text
设备树对象
    -> Zephyr API
        -> 简单 C++ 方法
```

例如：

```text
Spi::Send()
Spi::Read()
Pwm::SetDuty()
Can::Send()
```

USB 不只是一次硬件读写。

它需要处理：

- USB 枚举；
- EP0 控制传输；
- 标准请求；
- CDC ACM 类请求；
- 描述符；
- 配置状态；
- 端点打开和关闭；
- Bulk IN/OUT；
- reset/disconnect；
- DMA；
- cache；
- HPM EHCI 控制器；
- IRQ 和端点完成事件。

因此当前 tflm 没有把所有 USB 代码都塞进普通 `drivers/communication/stream/usb/`。

### 13.2 当前 USB 的两层结构

项目侧适配位于：

```text
drivers/communication/stream/usb/
    usb.hpp
    usb.cpp
    usb_rx_queue.hpp
```

外部 USB 模块位于：

```text
D:/Zephyr/modules/user/usb
```

外部模块包括：

```text
core/
    usb_dev_port
    usb_cdc_acm
    usb_descriptor

interface/
    usb_hal
    usb_types

hal/
    usb_hal_hpm
```

职责关系是：

```text
drivers/communication/stream/usb
    Usb
        继承 Stream
        管理接收队列
        管理发送忙状态
        连接 CDC 数据回调

external user/usb
    UsbDevPort
        USB 设备状态机
        EP0
        标准请求
        CDC ACM
        端点生命周期

    UsbHalHpm
        HPM USB 控制器
        PHY
        IRQ
        DMA
        QHD/qTD
```

### 13.3 USB 的真实数据流

接收：

```text
HPM USB IRQ
    -> UsbHalHpm
        -> UsbDevPort
            -> UsbCdcAcm
                -> Usb::OnDataEvent()
                    -> UsbRxQueue::Push()
                        -> Stream::sem_
                            -> 上层 Usb::Read()
```

发送：

```text
上层 Usb::Send()
    -> 检查 configured
        -> 检查 CDC 是否允许发送
            -> 抢占 tx_busy
                -> EpStartTx
                    -> IN completion
                        -> 必要时发送 ZLP
                            -> 清 tx_busy
```

### 13.4 USB 特殊性的价值

当前拆分有三个价值。

#### 协议栈可以独立维护

USB 枚举和 CDC 协议不应被 PC 业务线程直接理解。

#### HPM 硬件细节可以独立替换

以后换控制器或芯片族时，主要替换 HAL，而不是修改 Stream 使用者。

#### 项目上层只看到字节流

PC 线程或测试线程只需要：

```cpp
usb.Read(...)
usb.Send(...)
```

它不需要知道 EP0、MPS、端点地址和 qTD。

### 13.5 USB 和其他三个项目的区别

#### basic

USB 更可能作为 BSP、板级中间件或应用通信的一部分存在。

它的重点通常是：

```text
当前板子如何使用 USB
```

而不是：

```text
USB 协议栈、硬件 HAL 和项目 Stream 如何独立演进
```

#### COD_H7

USB 主要由 CubeMX 和 USB Device 中间件组成。

它已经具备实际能力，但协议栈、板级初始化和应用使用更集中在单板工程。

#### Dust

USB 或上位机通信通常属于 Communication、Interaction 或具体项目通信对象。

它的边界服从整机工程，不一定需要独立成跨项目基础设施。

#### tflm

tflm 把 USB 视为：

```text
外部复杂协议基础设施
    + drivers 侧统一 Stream 适配
    + project 侧决定如何使用
```

这是 tflm 当前更平台化的地方，同时也带来外部模块路径和构建装配成本。

### 13.6 USB 特殊性的代价

特殊边界不是只有好处。

当前需要维护：

- 外部模块；
- 根 CMake 装配；
- SDK glue；
- HPM HAL；
- USB 协议栈；
- `Stream` 接口；
- 接收队列；
- cache 和 DMA 约束。

所以 USB 的判断应该是：

```text
比普通 SPI/GPIO 驱动复杂
但复杂度被放进了正确的基础设施所有者
```

### 13.7 为什么 cmd 不是普通驱动层

`cmd/` 负责的是：

- shell 调试变量；
- buzzer 启动提示；
- 错误停机提示；
- Flash 持久化；
- 链接段注册；
- 构建辅助脚本。

它既不只是硬件访问，也不只是设备能力，更不是具体机器人业务。

更准确地说，`cmd` 是：

```text
横切型运行期辅助执行层
```

### 13.8 shell 的特殊性

shell 不是 Zephyr 业务 shell 的简单命令目录。

当前 `cmd/shell` 使用：

```text
UartDma
    + Thread
    + semaphore
    + .shell_var
    + l/g/s/?
```

它允许业务文件写：

```cpp
REGISTER_SHELL_VAR("gain", gain);
```

然后由链接器收集。

shell 自己拥有线程，是因为它是调试控制面：

```text
串口输入
    -> 变量查找
        -> 读写变量
            -> 日志输出
```

它不是底盘、云台或 IMU 的业务线程。

如果把 shell 放进 `project/thread/`，每个项目都要重复维护调试线程。

### 13.9 buzzer 和 flash 的特殊性

buzzer 和 flash 提供执行宏：

```cpp
EXEC_BUZZER_SHORT();
EXEC_BUZZER_ERR(nullptr);
EXEC_FLASH_READ(...);
EXEC_FLASH_WRITE(...);
```

宏的目的不是隐藏复杂业务，而是把条件编译收回 cmd 内部。

功能开启时：

```text
宏
    -> 真实对象和实现
```

功能关闭时：

```text
buzzer
    -> 空提示或保留停机语义

flash
    -> false
```

调用方不需要到处写：

```cpp
#ifdef CONFIG_CMD_BUZZER
#ifdef CONFIG_CMD_FLASH
```

这让初始化和模块调用点保持稳定。

### 13.10 cmd 为什么允许头文件常包含

因为 cmd 的头文件提供的是“能力入口”，不是“实现保证”。

例如：

```text
w25q128.hpp
    功能关闭时 EXEC_FLASH_* 返回 false

buzzer.hpp
    功能关闭时 EXEC_BUZZER_* 进入降级行为

shell.hpp
    功能关闭时 REGISTER_SHELL_VAR 为空宏
```

这形成：

```text
接口可以被看见
实现可以被裁剪
调用方不被 CONFIG 污染
```

### 13.11 cmd 与其他项目工具的区别

#### basic

调试和辅助能力通常更容易落在：

- app；
- BSP；
- message center；
- 具体模块。

它的优势是直接。

但跨项目复用时，调试能力可能跟着应用复制。

#### COD_H7

调试、检测和参数通常位于：

- Task；
- BSP；
- 全局变量；
- `Config.h`；
- `printf`。

它适合固定单板快速验证。

#### Dust

辅助能力容易进入：

- Robot；
- Interaction；
- Communication；
- 具体设备对象。

它适合当前整机。

#### tflm

把这类能力单独放进 `cmd`，因为它们具有横切性：

```text
多个层都可能调用
但不属于任何一个具体业务
```

### 13.12 USB 和 cmd 的共同点

USB 和 cmd 看起来完全不同，但架构上有一个共同点：

```text
它们都不是普通的“被动目录”
而是对多个层提供稳定入口的基础设施
```

区别是：

```text
USB
    复杂度来自协议栈和硬件生命周期

cmd
    复杂度来自运行期控制和可选能力
```

它们都需要：

- 稳定公共接口；
- 清晰实现边界；
- Kconfig/CMake 裁剪；
- 明确所有权；
- 不反向依赖具体业务。

## 十四、复用、迁移和维护成本对比

### 14.1 新增一个普通设备

#### basic

通常需要：

- 新增 BSP 或 module；
- 调整配置；
- 可能修改应用；
- 维护实例和消息关系。

#### COD_H7

通常需要：

- 新增 Device 组件；
- 加入 BSP；
- 修改任务；
- 配置具体外设；
- 检查全局状态和回调。

#### Dust

通常需要：

- 新增设备类；
- 加入 Robot；
- 修改 Interaction；
- 绑定 ID 和任务；
- 修改总控策略。

#### tflm

理想路径是：

```text
drivers
    -> 新硬件访问

modules
    -> 新设备能力

project/boards
    -> 设备树和板级绑定

project/thread
    -> 当前项目是否使用
```

如果设备是纯计算能力，还可以只进入 `algorithm`。

### 14.2 替换 IMU

#### basic

可能改：

- BSP；
- IMU module；
- app；
- 任务；
- 参数。

#### COD_H7

通常替换 BMI088 组件和 INS 任务中的调用。

#### Dust

需要检查 Robot、Imu、设备拓扑和初始化链。

#### tflm

主要变化应该集中在：

```text
modules/imu/devices/
    新设备子类

REGISTER_IMU()
    注册设备

board overlay
    提供 SPI 设备
```

`CalibSource`、`ImuManager` 和姿态处理尽量不改。

### 14.3 替换 Remote 协议

#### basic

可能修改遥控器模块、协议表和应用配置。

#### COD_H7

通常修改 Remote 组件和任务解析逻辑。

#### Dust

需要看当前通信对象、Robot 输入和业务映射。

#### tflm

主要增加：

```text
modules/remotes/xxx/xxx.cpp
    Validate
    Decode
    line_cfg
    REGISTER_REMOTE
```

Remote 核心线程和协议状态机保持不变。

### 14.4 新增 USB 功能

#### basic / COD_H7 / Dust

通常需要进入当前工程的 USB、通信或应用路径。

#### tflm

需要区分：

```text
USB 协议栈功能
    -> 外部 user/usb 模块

项目字节流使用
    -> drivers/communication/stream/usb

具体 PC 业务
    -> project/thread/pc 或 test
```

这使责任更清楚，但构建和外部依赖更多。

### 14.5 新增调试功能

#### basic / COD_H7 / Dust

常见方式是：

- 在任务里加打印；
- 加全局参数；
- 加调试命令；
- 加 BSP 或通信代码。

#### tflm

可以考虑：

```text
变量查看和修改
    -> cmd/shell

启动提示
    -> cmd/buzzer

参数保存
    -> cmd/flash

主机采集和辨识
    -> scripts
```

这使调试能力不再侵入业务模块。

## 十五、业务闭环能力对比

### 15.1 统一判断标准

本文把整机闭环拆成：

1. 输入；
2. 设备采集；
3. 状态估计；
4. 目标生成；
5. 控制计算；
6. 输出通信；
7. 故障保护；
8. 跨模块策略。

### 15.2 basic

典型链路：

```text
遥控器
    -> robot_cmd
        -> message_center
            -> chassis / gimbal / shoot
                -> 电机和外设
                    -> feedback
                        -> message_center
```

它的优势是应用组织和反馈链完整。

### 15.3 COD_H7

典型链路：

```text
遥控器
    -> remote_ctrl
        -> Control_Task
            -> PID
                -> Control_Info
                    -> CAN_Task
                        -> FDCAN
```

IMU 链路：

```text
BMI088
    -> INS_Task
        -> 滤波
            -> Quaternion
                -> INS_Info
```

它具备真实控制开发价值，但整机模式和跨模块策略相对轻。

### 15.4 Dust

典型链路：

```text
遥控器 / 视觉 / 裁判系统
                ↓
          Robot::Task()
           ↙    ↓    ↘
       Gimbal Chassis Reload
           ↓    ↓    ↓
           CAN / 电机 / 外设
```

它的目标生成、模式切换、保护和输出已经压实在整机工程里。

### 15.5 tflm

当前 tflm 的链路分成多个稳定边界：

```text
Remote
    -> remote_to
        -> chassis / gimbal
            -> to_can_tx
                -> CAN thread
                    -> drivers/Can
```

```text
IMU device
    -> CalibSource
        -> ImuManager
            -> Processor
                -> imu_to
```

```text
Motor callback
    -> Snapshot
        -> project/thread
            -> PID / PowerCtrl
                -> to_can_tx
```

这使平台边界更强。

但复杂整机策略仍需要在项目层继续沉淀。

### 15.6 两种能力不能混为一谈

```text
Dust 的优势
    是当前一台机器人的策略闭环

tflm 的优势
    是跨项目能力和边界
```

不能因为 tflm 当前策略还在装配，就说它的框架能力弱。

也不能因为 Dust 整机闭环强，就说它应该立刻改造成平台。

## 十六、按不同目标分别评分

### 16.1 评分说明

分数只表达当前代码快照下的相对位置。

它不是绝对质量认证，也不是对项目作者的评价。

### 16.2 框架架构能力

| 项目 | 职责边界 | 编译装配 | 硬件抽象 | 项目迁移 | 维护传承 | 总分 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 当前 `tflm` | 20 | 20 | 19 | 20 | 18 | **97** |
| `basic_framework-master` | 18 | 15 | 17 | 16 | 18 | **84** |
| `COD_H7` | 15 | 15 | 16 | 13 | 14 | **73** |
| `Dust_SentinelRobot_L_Game` | 13 | 11 | 14 | 10 | 13 | **61** |

这里 tflm 的职责边界得分高，不是因为层数多，而是因为当前已经明确了：

```text
drivers
    硬件访问

modules
    设备能力

algorithm
    纯计算

topic
    数据契约

project
    项目装配

cmd
    横切运行期能力
```

USB 作为外部协议栈桥接，cmd 作为运行期控制面，都有明确理由，而不是任意越层。

### 16.3 为什么 tflm 得分最高

#### 职责边界

当前每一层已经开始回答不同问题。

#### 编译装配

Kconfig、CMake、DTS、linker 和注册宏已经连成一条链。

#### 硬件抽象

普通外设和异步通信已经分开，USB 还进一步拆出外部协议栈。

#### 项目迁移

在公共能力覆盖需求的前提下，主要修改：

```text
project/apps
project/boards
project/thread
```

#### 没有拿满分的原因

当前仍有：

- 少量文档与代码需要持续同步；
- USB 外部模块增加了构建装配成本；
- 某些设备拓扑仍写在 project/thread；
- 线程生命周期和错误策略还在收敛；
- 部分 CMake 路径和旧接口需要维护。

### 16.4 为什么 basic 第二

它的职责和文档已经成熟。

特别是：

- `bsp/module/app`；
- message center；
- 多机器人；
- 队伍传承；
- 开发规则。

它的限制主要来自：

- STM32/HAL/FreeRTOS 绑定；
- 编译期配置较弱；
- 项目层隔离不如 tflm 明确；
- 仍有人工约束。

### 16.5 为什么 COD_H7 居中

它的硬件底座和工具链都很强。

但它的本质仍然是：

```text
结构化单板模板
```

而不是：

```text
项目装配型框架
```

### 16.6 为什么 Dust 框架分低但业务分高

Dust 的主要复杂度集中在具体机器：

- Robot；
- 成员对象；
- CAN ID；
- 设备拓扑；
- 总控任务；
- 当前业务策略。

这使它非常适合整机交付。

但迁移到新机器人时，通常需要重新组织这些核心关系。

### 16.7 单台比赛整机能力

| 项目 | 单台比赛整机分 | 主要原因 |

### 16.8 单板快速启动能力

如果目标是快速验证一块板：

```text

    >
```

因为 tflm 需要先理解：

- board；
- DTS；

- project。

这是平台化带来的学习成本。

### 16.9 跨项目迁移能力

如果目标是保留公共能力并新建项目：

```text
tflm
    >

    >
COD_H7

```

前提是 tflm 已经覆盖新项目需要的底层能力。

如果需要新芯片或新协议，仍然需要补：

```text
driver
    -> module
        -> topic
            -> project
```

## 十七、tflm 应该吸收什么，还要补什么

### 17.1 吸收 basic 的内容

#### 继续强化文档和传承

每层都应该说明：

- 职责；
- 不负责什么；
- 依赖谁；
- 被谁调用；
- 一个最小示例；
- 一个真实数据路径；
- 常见错误边界。

#### 继续强化消息契约

需要明确：

- 数据是状态还是事件；
- 发布频率；
- 数据所有权；
- 队列满时策略；
- 时间戳语义；
- 失联判定；
- 消费者是否允许丢帧。

#### 继续强化队伍级规则

平台不仅是代码，也包括：

- 新模块放哪里；
- 新线程怎么接入；
- 新板卡怎么组织；
- 新项目怎么复制；
- 旧模块怎么废弃。

### 17.2 吸收 COD_H7 的内容

#### 板级能力覆盖

继续积累：

- CAN；
- UART DMA；
- SPI；
- USB；
- PWM；
- ADC；
- IMU；
- 电机；
- 调试接口。

#### 快速联调路径

平台层不能只追求抽象。

还需要保证：

```text
收到一帧数据
    -> 能快速定位驱动
        -> 模块
            -> 线程
                -> 业务
```

#### 工具链一致性

继续保持：

- CMake；
- Ninja；
- 命令行；
- CLion；
- compile commands；
- 脚本化实验。

### 17.3 吸收 Dust 的内容

#### 设备拓扑可视化

虽然 tflm 不必复制 `Robot` 总控，但每个项目仍然需要明确：

```text
当前有哪些设备？
每个设备在哪条总线？
谁拥有它？
谁消费它？
谁发送控制？
```

可以通过：

- project 架构文档；
- 设备实例表；
- topic 数据流图；
- board 拓扑表；
- 线程关系图。

#### 跨模块策略的集中位置

完全拆成消息以后，复杂策略可能分散。

需要给项目层保留明确的策略位置：

- 项目协调线程；
- 状态机；
- 行为管理器；
- 整机策略模块。

不一定复制 `Robot::Task()`，但不能让跨模块策略无处可找。

#### 热路径直线

控制核心应保持：

```text
输入
    -> 目标
        -> 控制
            -> 限幅
                -> 输出
```

抽象和消息不能让 1 ms 控制路径变得不可追踪。

### 17.4 tflm 还应该继续补的内容

#### 项目模板

新项目最好有最小模板：

```text
project/
├── apps/
├── boards/
└── thread/
```

并说明：

- 必须文件；
- 可选文件；
- 默认开关；
- 最小 board；
- 最小启动链；
- 最小测试线程。

#### 初始化依赖

注册式启动需要继续明确：

- 同一阶段内的顺序；
- 线程依赖哪个模块；
- High/Mid/Low 的实际语义；
- 失败后哪些功能允许继续；
- 线程能否重复启动；
- 模块 ready 和 thread ready 的区别。

#### 外部基础设施装配

USB 说明了一个新问题：

```text
当基础设施超过普通驱动复杂度时，
它应该如何作为外部模块接入？
```

后续需要持续维护：

- 外部模块路径；
- Kconfig；
- CMake；
- 版本；
- HAL 适配；
- 项目 Stream 接口。

#### cmd 能力边界

cmd 已经承担：

- 调试；
- 提示；
- 持久化；
- 链接段；
- 构建辅助。

后续需要避免它变成新的业务总控。

判断标准是：

```text
是否服务多个项目？
是否属于运行期辅助？
是否可以提供稳定宏或对象接口？
是否不需要理解机器人业务策略？
```

如果答案是否定的，就应该放回 modules 或 project。

#### 当前代码同步

架构文档必须持续和以下内容同步：

- Kconfig；
- CMake；
- linker；
- 线程阶段；
- 外部 USB 模块；
- 设备目录；
- 当前真实源文件路径。

文档不能把规划中的边界写成已经落地的能力。

## 十九、最终结论

### 19.1 四个项目各自最强的地方

#### basic_framework-master

```text
把队伍经验变成规则。
```

#### COD_H7

```text
把一块 STM32H7 控制板变成可直接开发的单板底座。
```

#### Dust

```text
把设备、任务和策略真正连成一台机器人。
```

#### tflm

```text
把硬件、设备、算法、数据、项目和运行期工具拆成不同责任。
```

### 19.2 tflm 当前最重要的变化

tflm 的变化不只是增加了 `cmd` 或 `drivers/usb`。

真正的变化是：

```text
架构不再要求所有层都遵循同一种形式，
而是要求每种复杂度都有明确的所有者。
```

例如：

```text
普通 SPI
    -> drivers/Spi

IMU SPI 寄存器协议
    -> modules/imu/devices

USB 控制器和协议栈
    -> external user/usb

USB 字节流适配
    -> drivers/stream/usb

调试变量控制台
    -> cmd/shell

蜂鸣器错误停机
    -> cmd/buzzer

校准参数持久化
    -> cmd/flash

机器人策略
    -> project/thread
```

这比“所有东西都必须塞进普通 drivers 或 modules”更符合真实工程。

### 19.3 最终双排名

#### 框架架构能力

```text
tflm
    >
basic_framework-master
    >
COD_H7
    >
Dust_SentinelRobot_L_Game
```

#### 单台比赛整机能力

```text
Dust_SentinelRobot_L_Game
    >
basic_framework-master
    >
tflm
    >
COD_H7
```

### 19.4 对当前 tflm 的准确评价

当前 tflm 还不是一个所有边界都完全收敛的平台。

但它已经形成了平台化的主要骨架：

```text
drivers
    硬件访问

modules
    设备能力

algorithm
    纯计算

topic
    数据契约

project
    项目装配

cmd
    横切运行期能力

scripts
    主机侧验证
```

并且已经开始处理传统嵌入式框架最容易忽略的两个问题：

```text
复杂基础设施如何独立装配？
横切运行期工具如何不污染业务？
```

USB 和 cmd 正是在回答这两个问题。

### 19.5 最后一句话

如果只问“哪个项目最好”，问题仍然不准确。

更准确的说法是：

- 想学习队伍级传承，看 `basic_framework-master`；
- 想从 H7 控制板快速开始，看 `COD_H7`；
- 想学习整机业务闭环，看 Dust；
- 想继续发展自己的模块化嵌入式平台，看当前 `tflm`。

四个项目放在一起，呈现的是：

```text
借鉴成熟规则
    -> 整理单板底座
        -> 完成整机闭环
            -> 提炼项目型平台
                -> 让复杂度拥有明确的归属
```
