# 线程初始化层规划：init hook 与启动期处理

> 日期：2026-10-19
> 前置：`doc/线程编写指南.md`（运行期：Task / TaskResult / RecoveryHook / 统计）
> 本文范围：**启动期**——从 `System_Startup()` 到线程跑起来之前，所有能出错、能等待、能回滚的地方。
> 结论先行：当前 init 层只有「失败就停机 / 警告后继续」两种处理，缺少**阶段级**的失败策略、**初始化超时**、**依赖声明**和**启动期可观测性**。

---

## 1. 现状盘点

### 1.1 现有机制

| 机制 | 位置 | 说明 |
|---|---|---|
| `InitFailPolicy` | `Init_entry.hpp` | `HaltOnFail` / `ContinueOnFail`，逐条声明 |
| `InitLevel` | `Init_entry.hpp` | `High/Mid/Low`，同阶段执行顺序 |
| `cleanup` | `Init_entry.hpp` | 初始化失败时回滚本项资源 |
| `startup_aborted` | `Init_entry.cpp` | 线程启动失败置位，后续阶段全部跳过 |
| `System_StartupAborted()` | `System_startup.h` | 查询中止状态（**无调用者**） |
| 阶段间 `k_msleep(500)` | `Init_entry.cpp` | 留硬件上电稳定时间 |
| 蜂鸣提示 | `EXEC_BUZZER_SHORT/ERR` | 阶段完成 / 致命失败 |

### 1.2 现存问题

| # | 问题 | 现象 | 影响 |
|---|---|---|---|
| P1 | **`HaltOnFail` 直接 `while(1){}`** | 死循环里没有蜂鸣、没有日志刷新、没有复位 | 现场静默；看门狗若被喂则永久卡死 |
| P2 | **失败只影响本项** | `cleanup` 只回滚自己，前面已成功的项不回滚 | 停机时外设停在不确定状态（PWM 还在输出、电机可能持续通电） |
| P3 | **无初始化超时** | `thread_init()` 里 `while(!device_ready()){}` 会静默卡死 | 启动彻底停住，日志停在上一行，无任何线索 |
| P4 | **阶段间固定 500ms** | 每阶段都等，共 4.5 秒 | 慢速启动；且等多久是拍脑袋定的 |
| P5 | **无依赖声明** | 靠阶段+等级隐式表达 | 同阶段同等级的顺序不确定（链接顺序），依赖靠运气 |
| P6 | **`System_StartupAborted()` 无调用者** | 死接口 | 启动失败后 `main.py` 仍进入空转循环 |
| P7 | **`cleanup` 只在失败时调用** | 成功项永不清理 | 当前无停机语义，属于设计选择，但需要写清楚 |
| P8 | **启动期无统计** | 无法知道每个 init 花了多久 | 无法定位「哪个初始化拖慢了启动」 |
| P9 | **`RunStage(ThreadStage)` 失败即全局中止** | 任一线程 `start()` 返回 false 就中止全部 | 一个非关键线程失败会拖垮整个系统 |

---

## 2. 目标

### 2.1 要做

1. **启动期 hook**：让每个 init 项可以声明「失败后做什么」，而不只是「停机/继续」
2. **初始化超时**：init 卡住时能发现、能记录、能按策略处理
3. **依赖声明**：让「A 必须在 B 之后」变成显式契约，而不是靠阶段碰运气
4. **阶段级失败策略**：区分「基础阶段失败必须停机」与「应用阶段失败可降级」
5. **启动期统计**：每个 init / thread 项耗时，通过 shell 查看
6. **停机前收尾**：`HaltOnFail` 之前先逆序 `cleanup` 已成功项，把硬件放回安全态

### 2.2 不做

- 不引入 `System_Shutdown`（MCU 无停机语义，已否决）
- 不做看门狗（属于运行期，单独规划）
- 不做 `Fatal` 后自动重启
- 不改 `TaskResult` / `RecoveryHook`（运行期已定稿）

## 3. 设计

### 3.1 启动期 hook：`InitFailHook`

当前 `InitFailPolicy` 只有两个枚举值，且 `HandleInitFail()` 内部写死行为。改成「策略 + 可选钩子」：

```cpp
/**
 * @brief 初始化失败钩子：在 cleanup 之后、失败策略执行之前调用
 *
 * 用于记录现场、关闭相关外设、上报等。钩子内不得阻塞超过 10ms。
 *
 * @param entry 失败的注册项
 * @param stage 当前初始化阶段
 * @return true=本次失败已自行处理，可按 ContinueOnFail 继续；false=按原策略处理
 */
using InitFailHook = bool (*)(const InitEntry& entry, InitStage stage);
```

`InitEntry` 增加字段：

```cpp
struct InitEntry
{
    InitFunc          function;    // 初始化函数
    CleanupFunc       cleanup;     // 失败回滚与退出清理
    InitFailHook      on_fail;     // 失败钩子（可为 nullptr）
    InitStage         stage;
    InitLevel         level;
    InitFailPolicy    fail;
    const char*       name;
};
```

注册宏从 6 参数变 7 参数：

```cpp
REGISTER_INIT(fn, stage, level, fail, cleanup, on_fail, name)
```

**为什么用返回值而不是 void**：钩子可能已经完成了降级处理（比如切到备用传感器），这时应该允许继续启动；返回 `true` 表示「我处理好了，按 `ContinueOnFail` 走」。

### 3.2 初始化超时

**问题**：`init()` 内部如果阻塞，框架完全不知道。

**方案**：框架不强制超时（无法安全打断一个正在执行的函数），但提供**看护接口**：

```cpp
/**
 * @brief 启动期看护：init 长时间未返回时的处理
 */
class StartupWatchdog
{
public:
    /**
     * @brief 开始监视某个 init 项
     * @param name 项名（日志用）
     * @param budget_ms 允许的执行时间；0=不监视
     */
    static void Begin(const char* name, uint32_t budget_ms);

    /**
     * @brief 结束监视
     */
    static void End();
};
```

**实现方式**：起一个低优先级看护线程，在 `System_Startup()` 开始前创建：

```cpp
void StartupWatchdogThread()
{
    for (;;)
    {
        if (!active_) { k_msleep(10); continue; }

        if (k_uptime_get_32() - start_ms_ > budget_ms_)
        {
            DUST_LOG_ERR("[boot] %s timeout (>%ums)", name_, budget_ms_);
            // 按预算策略处理：见 §3.2.1
        }
        k_msleep(10);
    }
}
```

#### 3.2.1 超时后能做什么

**不能**强杀 init 函数（Zephyr 没有安全的跨栈终止）。可选：

| 选项 | 行为 | 代价 |
|---|---|---|
| A 只记录 | 打 ERR，继续等 | 启动永久卡住，但现场有记录 |
| B 记录 + 蜂鸣 | 打 ERR + 长鸣 | 同上，但人耳能听见 |
| C 记录 + 中止启动 | 打 ERR，`startup_aborted = true`，`HaltOnFail` 路径 | init 仍卡在原函数里，后续阶段不会执行（主线程被占住，实际上也执行不了） |
| D 记录 + 复位 | `sys_reboot()` | 需要确认板卡支持 |

**建议**：默认 B（记录 + 蜂鸣），Kconfig 可选 D。

**为什么不做 C**：init 卡在原函数里，主线程根本回不到 `RunStage`，`startup_aborted` 写不写都没用。看护线程唯一能做的就是**留下证据**。

> **关键认知**：超时机制的价值不是「恢复」，而是「让你知道卡在哪」。真正防止卡死要靠 init 函数自己写超时（见 §3.2.2）。

#### 3.2.2 init 函数的超时契约（写入文档）

```cpp
bool thread_init()
{
    constexpr uint32_t kTimeoutMs = 1000;
    const uint32_t start = k_uptime_get_32();

    while (!device_.IsReady())
    {
        if (k_uptime_get_32() - start > kTimeoutMs) {
            DUST_LOG_ERR("device not ready within %ums", kTimeoutMs);
            return false;                       // ← 必须返回，不能死等
        }
        k_msleep(10);
    }
    return true;
}
```

**原则**：init 函数里任何阻塞等待都必须有上限，超时后返回 `false` 交给框架处理。

### 3.3 依赖声明

**问题**：同阶段同等级的项顺序由链接器决定，A 依赖 B 只能靠「B 写在 A 前面」碰运气。

**方案**：给 `InitEntry` 加一个「依赖项名」字段，启动器在调用前检查依赖是否已成功：

```cpp
struct InitEntry
{
    ...
    const char* depends_on;    // 依赖的注册项名（nullptr=无依赖）
};
```

检查逻辑：

```cpp
if (e->depends_on != nullptr && !IsInited(e->depends_on))
{
    DUST_LOG_ERR("[boot] %s skipped: dependency %s not ready", e->name, e->depends_on);
    RunCleanup(e->cleanup);
    HandleInitFail(*e);
    continue;
}
```

`IsInited()` 遍历**已完成项**列表（需要一个 `inited_entries[]` 数组，之前删掉了，此处重新引入）：

```cpp
constexpr uint8_t kMaxInitedEntries = 32;
const InitEntry* inited_entries[kMaxInitedEntries];
uint8_t inited_count = 0;

static bool IsInited(const char* name)
{
    for (uint8_t i = 0; i < inited_count; ++i) {
        if (std::strcmp(inited_entries[i]->name, name) == 0) return true;
    }
    return false;
}
```

**命名要求**：`depends_on` 填的是 `REGISTER_INIT` 的 `name` 参数（如 `"w25q128"`），不是函数名。

**优点**：显式、可检查、失败有明确日志
**缺点**：多一个字段、多一张表、名字可能拼错（编译期不检查）

**替代方案**：不引入依赖字段，只用阶段。当前项目 5 个 init 项，阶段足够表达。**建议先不做，等出现真实的跨阶段依赖需求再说**。

### 3.4 阶段级失败策略

**问题**：`RunStage(ThreadStage)` 里任一线程失败就 `startup_aborted = true`，把后面所有阶段全废掉。

**方案**：线程项也加失败策略，复用 `InitFailPolicy`：

```cpp
struct ThreadEntry
{
    InitFunc         start;
    ThreadStage      stage;
    InitFailPolicy   fail;      // 新增
    const char*      name;
};
```

```cpp
REGISTER_THREAD(fn, stage, fail, name)    // 从 3 参数变 4 参数
```

`RunStage(ThreadStage)`：

```cpp
if (!e->start())
{
    DUST_LOG_ERR("[boot] %s start fail", e->name);
    if (e->fail == InitFailPolicy::HaltOnFail) {
        startup_aborted = true;
        return;                          // 立即停止本阶段后续
    }
    continue;                            // 继续启动其它线程
}
```

**谁用哪个**：

| 线程 | 建议 |
|---|---|
| shell（调试台） | `HaltOnFail` — 没了就没法调试 |
| imu | `HaltOnFail` — 控制环的基础 |
| remote | `ContinueOnFail` — 遥控器可以没有 |
| test | `ContinueOnFail` — 测试线程不影响系统 |
| gpio 心跳 | `ContinueOnFail` |

### 3.5 停机前收尾

**问题**：当前 `HaltOnFail` 直接 `while(1){}`，之前已成功初始化的项（PWM 输出、CAN 控制器、Flash）停在不确定状态。

**方案**：停机前逆序调用已成功项的 `cleanup`：

```cpp
static void HaltWithRollback(const InitEntry& failed)
{
    DUST_LOG_ERR("[boot] %s fail, rolling back %u entries", failed.name, inited_count);

    for (int i = static_cast<int>(inited_count) - 1; i >= 0; --i)
    {
        if (inited_entries[i]->cleanup != nullptr)
        {
            inited_entries[i]->cleanup();
            DUST_LOG_WRN("[boot] %s rolled back", inited_entries[i]->name);
        }
    }

    EXEC_BUZZER_ERR(nullptr);
    for (;;) {
        k_msleep(1000);       // 改为休眠循环，保证不再是死等空转
    }
}
```

**效果**：

- PWM 停止输出
- Flash 进入掉电
- CAN 控制器可以被 reset（如果 cleanup 实现）

**代价**：`cleanup` 必须支持「成功初始化后调用」场景，不能再假设是「部分初始化回滚」。

> 当前 buzzer 的 `Off()` 和 flash 的 `PowerDown()` 都满足这个要求。其余传 `nullptr` 的项无影响。

**同时修掉 P1**：`while(1){}` 改 `for(;;) k_msleep(1000)`——空转会把 CPU 占满，休眠循环不会，而且看门狗（若将来引入）能看到线程在跑。

### 3.6 启动期统计

在 `InitEntry` 执行前后计时，累计到一张表：

```cpp
struct StartupTiming
{
    const char* name;
    uint32_t    ns;
};

constexpr uint8_t kMaxTimings = 32;
StartupTiming startup_timings[kMaxTimings];
uint8_t       timing_count = 0;
```

执行处：

```cpp
const uint64_t begin = k_cycle_get_64();
const bool ok = e->function();
const uint32_t ns = static_cast<uint32_t>(k_cyc_to_ns_floor64(k_cycle_get_64() - begin));
RecordTiming(e->name, ns, ok);
```

shell 命令：

```text
boot timing                启动期各项耗时，按耗时降序
```

输出：

```text
BOOT TIMING (total 4.62 s)
  imu_init        1203.4 ms   ok
  w25q128         402.1 ms    ok
  dbg_init        88.6 ms     ok
  buzzer          2.3 ms      ok
  output_init     0.1 ms      ok
  --- init 5, thread 4 ---
```

**价值**：直接看出哪个 init 拖慢启动。

### 3.7 `System_StartupAborted()` 接线

`main()` 当前：

```c
int main(void)
{
    System_Startup();
    while (1) { k_msleep(1000); }
}
```

改为：

```c
int main(void)
{
    System_Startup();

    if (System_StartupAborted())
    {
        DUST_LOG_ERR("[boot] startup aborted");
    }

    while (1) { k_msleep(1000); }
}
```

或者更进一步——中止后蜂鸣并停机（与 `HaltOnFail` 一致），避免系统在半启动状态下运行。

**建议**：`startup_aborted` 时蜂鸣 + 停机，因为「线程起不来」和「init 失败」同样严重。

## 4. 优先级与阶段划分

| 阶段 | 内容 | 优先级 | 依赖 |
|---|---|---|---|
| **A** ✅ | 停机前逆序 `cleanup` + `while(1)` 改休眠循环 | **高** | 无 |
| **B** ✅ | 线程项失败策略（`REGISTER_THREAD` 加 `fail`） | **高** | 无 |
| **C** ✅ | 启动期统计 + `boot timing` 命令 | **中** | 无 |
| **D** ✅ | `main.cpp` 检查 `System_StartupAborted()` 后蜂鸣 + 停机 | **中** | 无 |
| **E** | `InitFailHook`（失败钩子） | **中低** | 无 |
| **F** | 启动期看护（超时记录 + 蜂鸣） | **低** | 需起线程 |
| **G** | 依赖声明 `depends_on` | **低** | 需重建已完成项表 |

**建议执行顺序**：A → B → C → D →（视需求）E → F → G

A、B 是「修 bug」性质，C、D 是「补可观测性」，E 是「扩展表达能力」，F、G 在当前项目规模下收益有限。

## 5. 详细改动（阶段 A）

### 5.1 `Init_entry.cpp`

**改动 1**：增加已完成项表

```cpp
namespace {
constexpr uint8_t kMaxInitedEntries = 32;
const InitEntry*  inited_entries[kMaxInitedEntries];
uint8_t           inited_count = 0;
}
```

**改动 2**：`RunStage(InitStage)` 成功时登记

```cpp
if (!e->function()) {
    if (e->cleanup != nullptr) e->cleanup();
    HandleInitFail(*e);
    continue;
}

if (inited_count < kMaxInitedEntries) {
    inited_entries[inited_count++] = e;
} else {
    DUST_LOG_ERR("[boot] init table full, %s not tracked", e->name);
}

DUST_LOG_OK("[boot] %s init", e->name);
```

**改动 3**：`HandleInitFail` 增加回滚

```cpp
static void HandleInitFail(const InitEntry& entry)
{
    const bool halt = (entry.fail == InitFailPolicy::HaltOnFail);

    if (halt) DUST_LOG_ERR("[boot] %s fail", entry.name);
    else      DUST_LOG_WRN("[boot] %s fail", entry.name);

    if (!halt) return;

    // 停机前逆序回滚已成功项
    for (int i = static_cast<int>(inited_count) - 1; i >= 0; --i)
    {
        if (inited_entries[i]->cleanup != nullptr)
        {
            inited_entries[i]->cleanup();
            DUST_LOG_WRN("[boot] %s rolled back", inited_entries[i]->name);
        }
    }

    EXEC_BUZZER_ERR(nullptr);

    for (;;) {
        k_msleep(1000);     // 休眠停机，不再空转
    }
}
```

### 5.2 验证

1. 编译通过；
2. 上板启动，日志顺序不变；
3. 临时把某 `HaltOnFail` 项的 init 改成 `return false`，观察：
   - `[boot] xxx fail`
   - 后续项的 `rolled back` 日志（如果有 cleanup）
   - 蜂鸣
   - CPU 不再满载（休眠循环）

## 6. 详细改动（阶段 B）

### 6.1 `Init_entry.hpp`

```cpp
struct ThreadEntry
{
    InitFunc         start;
    ThreadStage      stage;
    InitFailPolicy   fail;      // 新增
    const char*      name;
};

#define REGISTER_THREAD(fn, stage_, fail_, name_)                              \
    static const ThreadEntry kThreadEntry_##fn = {                             \
        fn, ThreadStage::stage_, InitFailPolicy::fail_, name_                  \
    };                                                                         \
    static const ThreadEntry* const kThreadEntryPtr_##fn                       \
        __attribute__((used, __section__(".user_thread"),                      \
                       aligned(sizeof(void*)))) = &kThreadEntry_##fn
```

### 6.2 `Init_entry.cpp` 的 `RunStage(ThreadStage)`

```cpp
if (!e->start())
{
    DUST_LOG_ERR("[boot] %s start fail", e->name);

    if (e->fail == InitFailPolicy::HaltOnFail) {
        startup_aborted = true;
        return;                          // 立刻停止本阶段后续项
    }
    continue;
}
```

### 6.3 所有 `REGISTER_THREAD` 调用点

| 文件 | 当前 | 新 |
|---|---|---|
| `shell.cpp` | `REGISTER_THREAD(thread_start, PreThread, "dbg_start")` | `REGISTER_THREAD(thread_start, PreThread, HaltOnFail, "dbg_start")` |
| `trd_gpio.cpp` | `REGISTER_THREAD(thread_start, PreThread, "output_start")` | `REGISTER_THREAD(thread_start, PreThread, ContinueOnFail, "output_start")` |
| `trd_imu.cpp` | `REGISTER_THREAD(thread_start, EarlyThread, "imu_start")` | `REGISTER_THREAD(thread_start, EarlyThread, HaltOnFail, "imu_start")` |
| `trd_remote.cpp` | `REGISTER_THREAD(thread_start, EarlyThread, "remote_start")` | `REGISTER_THREAD(thread_start, EarlyThread, ContinueOnFail, "remote_start")` |
| `trd_test.cpp` | `REGISTER_THREAD(thread_start, LateThread, "test_start")` | `REGISTER_THREAD(thread_start, LateThread, ContinueOnFail, "test_start")` |

## 8. 详细改动（阶段 D）

`framework/init/startup/main.cpp`（由 `main.c` 改名，以便使用 `DUST_LOG_*` 等 C++ 宏）：

```cpp
int main(void)
{
    System_Startup();

    if (System_StartupAborted())
    {
        DUST_LOG_ERR("[boot] startup aborted, halting");
        EXEC_BUZZER_LONG();
        for (;;) { k_msleep(1000); }
    }

    for (;;) { k_msleep(1000); }
}
```

**为什么改 `.cpp`**：`DUST_LOG_*` / `EXEC_BUZZER_*` 都是 C++ 宏，`main.c` 用不了。改名后策略可以留在入口处，`Init_entry.cpp` 只管启动流程本身。

## 9. 阶段 E：`InitFailHook`

### 9.1 使用场景

```cpp
/**
 * @brief IMU 初始化失败时可以尝试的降级路径
 * @return true=已降级，可以继续启动
 */
static bool imu_fail_hook(const InitEntry& entry, InitStage stage)
{
    (void)entry;
    (void)stage;

    DUST_LOG_WRN("imu init failed, trying backup source");
    if (backup_imu_.Init()) {
        return true;                 // 降级成功
    }
    return false;                    // 降级失败，按原策略处理
}
```

### 9.2 与 `cleanup` 的调用顺序

```text
init() 返回 false
    ↓
cleanup()             ← 先回滚本项资源
    ↓
on_fail(entry, stage) ← 再尝试降级（此时环境是干净的）
    ↓
返回 true  → 按 ContinueOnFail 继续
返回 false → 按 fail 策略（可能停机 + 全体回滚）
```

**为什么 cleanup 在前**：降级路径需要一个干净的起点，避免半初始化的资源干扰。

### 9.3 是否需要

当前 5 个 init 项都没有降级需求。**建议暂时不做**，等出现「主传感器坏了要切备用」这类真实需求再加。

## 10. 阶段 F：启动期看护

### 10.1 结构

```cpp
class StartupWatchdog
{
public:
    static void Start();                        // 在 System_Startup 开头创建看护线程
    static void Begin(const char* name, uint32_t budget_ms);
    static void End();
    static void Stop();                         // 启动完成后停止看护
};
```

线程体：

```cpp
static void Task(void*, void*, void*)
{
    for (;;)
    {
        if (!active_) { k_msleep(20); continue; }

        if (k_uptime_get_32() - start_ms_ > budget_ms_)
        {
            DUST_LOG_ERR("[boot] %s stuck (>%ums)", name_, budget_ms_);
            EXEC_BUZZER_LONG();
            active_ = false;            // 只报一次
        }
        k_msleep(20);
    }
}
```

### 10.2 预算从哪来

三个阶段：

| 方案 | 说明 |
|---|---|
| 全局统一预算 | 如 2 秒，超了都报警 |
| 逐项声明 | `REGISTER_INIT` 再加一个 `budget_ms` 参数 |
| Kconfig | `CONFIG_DUST_BOOT_TIMEOUT_MS` |

**建议**：全局统一预算（`CONFIG_DUST_BOOT_ITEM_TIMEOUT_MS`，默认 2000），简单够用。

### 10.3 代价

- 多一个线程（栈 512 B）
- 启动完成后要停止看护（`Stop()`），或让它进入空转

## 12. 阶段间 sleep 的处理

当前固定 500ms × 9 = 4.5 秒。改进方向：

| 方案 | 说明 |
|---|---|
| 保持现状 | 简单，已被验证 |
| Kconfig 可调 | `CONFIG_DUST_BOOT_STAGE_DELAY_MS`，默认 500 |
| 仅 PreInit 后等待 | 只有上电稳定需要，后续阶段可以缩短 |

**建议**：加 Kconfig 可调，默认保持 500。不改变默认行为，但让调试时可以缩短。

```kconfig
config DUST_BOOT_STAGE_DELAY_MS
    int "Delay between boot stages (ms)"
    default 500
    range 0 5000
```

## 14. 风险与回退

| 风险 | 影响 | 应对 |
|---|---|---|
| 回滚调用 `cleanup` 后硬件状态不确定 | 停机现象与之前不同 | `cleanup` 必须能处理「成功初始化后调用」；buzzer/flash 已满足 |
| `REGISTER_THREAD` 改签名 | 所有调用点必须同步改 | 编译期发现，不会静默 |
| 已完成项表容量不足 | 超出项不参与回滚 | 打 ERR；容量可调 |
| 看护线程本身占栈 | +512 B RAM | 仅在启用时编译 |
| `boot timing` 输出过长 | 命令响应通道拥堵 | 只输出前 16 项 |

**回退**：阶段 A/B/C/D 都是独立改动，任一阶段回退只需恢复对应文件。
